# Правила для Codex — Furniture Delivery

## Контекст и границы

Проект — тестовое задание для управления доставкой мебели и сборкой на дому.
Есть диспетчерский интерфейс и мобильный интерфейс сотрудников.
Потенциальное дальнейшее использование компанией не превращает тестовый MVP в production-систему.

Перед изменениями прочитай `docs/PROJECT_SPEC.md`, `docs/DOMAIN_RULES.md`,
`docs/MILESTONES.md`, `docs/DECISIONS.md` и `docs/PROGRESS.md`.
Выполняй только запрошенный этап. Полная спецификация — контекст, а не команда реализовать всё сразу.

## Архитектура

- TypeScript strict; pnpm workspace; один Next.js frontend; один NestJS modular monolith.
- PostgreSQL и TypeORM. Не заменять на Prisma, SQLite, Supabase или frontend-only хранилище.
- `apps/web`, `apps/api`, `packages/contracts`. Дополнительные пакеты — только при реальной необходимости.
- Бизнес-правила, права доступа и транзакции принадлежат NestJS.
- Next.js не обращается к БД и не дублирует серверную бизнес-логику.
- `packages/contracts` содержит браузер-совместимые API-контракты, без TypeORM entities,
  Nest decorators, секретов и импортов серверных модулей.
- TypeScript-типы не заменяют runtime-валидацию входящих запросов.
- Не создавать микросервисы, Kafka, Redis, Kubernetes, CQRS/event sourcing или универсальные
  repository-абстракции «на будущее».
- Внутренние импорты не должны образовывать циклы. Модули экспортируют небольшой публичный API.

## Модель предметной области

`Crew` — команда. `CrewMember` — связь сотрудника с командой, а не ещё одна команда.
`Order` — обязательство перед клиентом; `Appointment` — визит;
`CrewAssignment` — участие команды в визите; `Task` — работа конкретного назначения.
Один заказ имеет несколько визитов, один визит — несколько назначенных команд.
Перенос не создаёт новый заказ и не уничтожает предыдущую историю.
Оплата, операционное выполнение, проблемы и необходимость повторного визита — разные измерения.
Не объединять их в один гигантский enum.
Подробные правила и ограничения MVP находятся в `docs/DOMAIN_RULES.md`.

## Данные и безопасность

- Схема меняется миграциями; `synchronize: false` во всех окружениях.
- Seed — отдельная команда, только для development/test. Повторный запуск не дублирует
  записи и не сбрасывает пользовательские изменения или пароли.
- Секреты — только из окружения. `.env.example` содержит безопасные placeholders, не рабочие секреты.
- Пароли хешировать; не выводить пароли, токены, connection strings или персональные данные в логи.
- Временные точки хранить как UTC instants; бизнес-зона по умолчанию `Europe/Rome`.
  Дневные границы и переходы летнего времени считать в этой зоне, не через фиксированный UTC offset.
- Деньги — целое число минимальных единиц валюты; для MVP EUR/cents.
  Проверять диапазоны и целочисленность, не считать суммы через дробные евро.
- После M2 проверять права на backend на каждом бизнес-действии и каждой читаемой записи.
  Сотрудник видит только назначения своих разрешённых команд.
- Не отдавать платежи, внутренние заметки и файлы через незащищённые URL.
- Изменение расписания должно проверять конфликты внутри транзакции и учитывать конкуренцию;
  одна проверка на frontend или перед транзакцией недостаточна.
- События realtime отправлять только после commit. После переподключения клиент перечитывает БД через API.

## Работа с инструментами и зависимостями

Сначала осмотри файлы, Git diff и доступные команды. Не перезаписывай чужие изменения.
Проверь актуальную совместимость Node, pnpm, Next, Nest и TypeORM по официальным источникам
и метаданным пакетов. Зафиксируй выбранные версии, `packageManager` и один `pnpm-lock.yaml`.
Не выбирай prerelease без необходимости и не оставляй версии `latest` в итоговых manifests.
Не копируй устаревшие CLI-флаги и команды из памяти без проверки установленной версии.
Не добавляй premium-плагины календаря или платные сервисы без согласования лицензии.

Не выполняй deploy/publish/push, удаление данных или разрушительные Git-команды без разрешения.
Не отключай sandbox и не запрашивай избыточные права ради удобства.
Не меняй тесты только для сокрытия ошибок; не используй пустые проверки или fake success scripts.

## Проверка результата

Эти команды должны быть реализованы в M1, но в стартовом пакете ещё не существуют:
`pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`,
`pnpm db:migrate`, `pnpm db:seed`, `pnpm test:integration`.
Запускай применимые проверки после изменений. Интеграционные проверки используют отдельную тестовую БД.
Для UI проверяй загрузку, пустой список, ошибку API и экран телефона.
Сложные правила проверяй позитивными, негативными и конкурентными тестами по текущему этапу.

Если среда не позволяет запустить проверку, обозначь BLOCKED и причину;
не выдавай непроверенные команды за успешно выполненные.
Обновляй `docs/PROGRESS.md` фактическими результатами, а решения — `docs/DECISIONS.md`.
Финальный отчёт: изменения; команды и результаты; ограничения; локальные шаги проверки.
Объяснения для разработчика — по-русски, идентификаторы кода — по-английски.
