# Furniture Delivery — M8

Тестовый проект доставки и сборки мебели. Реализованы M1–M8: заказы/платежи,
планирование Europe/Rome, исполнение команды, количества, защищённые файлы и issues.
Добавлены оценки окончания, риски, предложения окон, подтверждаемый перенос и повторные визиты.
Добавлены неизменяемые результаты визитов, фиксация подписей и явное закрытие/переоткрытие заказа.
Добавлены авторизованные SSE-сигналы и отдельное синтетическое демо. Пользовательская
приёмка M5–M8 и реальные устройства остаются отдельной финальной проверкой.

```text
apps/
  web/                  Next.js App Router, порт 3000
  api/                  NestJS, порт 3001
packages/
  contracts/            Browser-safe health, identity, orders, planning, execution/evidence, rescheduling/return, acceptance/completion/realtime contracts
docs/
prompts/
docker-compose.yml
pnpm-workspace.yaml
package.json
pnpm-lock.yaml
```

Нужны Node.js **24.22.1 LTS**, pnpm **10.34.8**, Docker Engine/Desktop с Compose v2.
Версии Node указаны в `.nvmrc` и `.node-version`; приложения работают отдельными процессами.

## Стили dashboard и страницы входа

Dashboard, общая рамка backoffice и login используют **Tailwind CSS 4.3.3** через
**@tailwindcss/postcss 4.3.3 / PostCSS 8.5.32**. Версии закреплены в web manifest и
единственном lockfile; установка входит в обычный `pnpm install --frozen-lockfile`.
Отдельная команда генерации CSS не нужна: PostCSS работает в Next dev/build.

Конфигурация — `apps/web/postcss.config.mjs`, входной stylesheet —
`apps/web/app/tailwind.css`, импортированный корневым layout. Utilities имеют префикс
`tw:`; классы задаются полными строками в TSX. Для динамических ширин и долей диаграмм
остались только inline значения/CSS variables. Preflight не импортируется, чтобы
сохранить существующие формы и календарь остальных разделов. Старые shared styles
продолжают обслуживать ещё не перенесённые страницы; отдельный `dashboard.css` удалён.

На login кнопка с глазом показывает/скрывает введённый пароль. При отправке пароль снова
маскируется; вход и password manager используют прежние поля. На Service status кнопка
**Back** возвращает по истории, при прямом открытии ведёт на login. Иконка Refresh
на dashboard обновлена; источник данных и действие обновления не менялись.

## Первый запуск

Из корня проекта:

```bash
nvm install
nvm use
npm install --global pnpm@10.34.8
pnpm install --frozen-lockfile
if [ ! -e .env ] && [ ! -L .env ]; then
  cp .env.example .env
fi
```

В `.env` замените оба password-placeholder на собственные локальные пароли.
Если `.env` уже существует, сохраните его настройки, не копируйте поверх него пример.
Все приложения и команды API читают один корневой `.env`; переменные процесса имеют
приоритет. Файл игнорируется Git. Пароли не нужны frontend-коду.

```bash
docker compose up -d --wait postgres
pnpm db:migrate
```

Перед первым seed задайте `SEED_PASSWORD` локально, без записи в историю терминала.
Например, в Bash (ввод скрыт):

```bash
read -r -s -p 'Local demo password (12–128 characters): ' SEED_PASSWORD
printf '\n'
export SEED_PASSWORD
pnpm db:seed
unset SEED_PASSWORD
pnpm db:seed
pnpm dev
```

Seed создаёт `demo.admin`, `demo.dispatcher` и сотрудников
`demo.crew01.member01` … `demo.crew10.member04`: 42 отдельных аккаунта,
по четыре сотрудника в каждой из десяти команд. Начальный пароль берётся только
из `SEED_PASSWORD`; у каждого аккаунта отдельная соль хеша. Повторный seed сохраняет
пароли, роли, disabled-состояния, ручные изменения и историю членства. Если все
аккаунты уже существуют, пароль не нужен. Изменение `SEED_PASSWORD` не сбрасывает
существующие пароли — для этого есть форма ADMIN.

Откройте [вход](http://127.0.0.1:3000/login). ADMIN и DISPATCHER получают
`/backoffice`; сотрудник — `/crew`. Только ADMIN управляет аккаунтами.
Диспетчер управляет командами, составом и внешними контактами без аккаунтов.
Команды, членство и контакты отключаются без удаления истории.

Откройте [frontend](http://127.0.0.1:3000). Прямой
[health API](http://127.0.0.1:3001/api/health) делает настоящий `SELECT 1`.
Успех — HTTP 200, недоступность БД — HTTP 503. API запускается и при выключенной БД.
Страница различает недоступный API и недоступную БД; кнопка Retry повторяет запрос.
Из Next.js браузер обращается к `/api/health`; server-side rewrite направляет запрос
на `API_ORIGIN`. Публичные CORS-разрешения не нужны. При изменении `API_ORIGIN`
перезапустите dev server или пересоберите production frontend.

Порт PostgreSQL и API по умолчанию привязаны к `127.0.0.1`. Порты 3000, 3001, 5432,
5433 должны быть свободны. `API_PORT` и `DATABASE_PORT` можно изменить в `.env`;
при изменении `API_PORT` также измените `API_ORIGIN`.

## Сессии и права M2

- Cookie `fd_session`: HttpOnly, SameSite=Lax, Path=/, без Domain. Secure по умолчанию
  включён при `NODE_ENV=production`, выключен в development/test. Production login
  предполагает HTTPS; для локальной проверки используйте `pnpm dev`.
- Cookie содержит случайный opaque token из 32 bytes. В PostgreSQL хранится только
  SHA-256-хеш; JSON API, SSR HTML и browser storage токен не получают.
- Абсолютный срок — 8 часов (`SESSION_TTL_SECONDS=28800`), без продления на запросах.
  Logout отзывает сессию в БД и очищает cookie; повтор старой cookie даёт 401.
- Каждый запрос проверяет актуальные User и CrewMember в БД. Отключение аккаунта,
  смена роли/пароля через ADMIN отзывает все его сессии. Повторное включение не
  возвращает старую сессию. Смена членства действует со следующего запроса без logout.
  Чужая или более недоступная команда возвращает 404; запрет административного действия — 403.
- Все POST/PATCH требуют точный `Origin`, совпадающий с `WEB_ORIGIN`, и
  `X-CSRF-Protection: 1`, включая login/logout. Отсутствующий/чужой Origin отклоняется.
  Открывайте локальный UI именно через настроенный origin (по умолчанию 127.0.0.1:3000).
- Next proxy `/api/:path*` передаёт Cookie, Set-Cookie и Origin. SSR layouts читают
  текущую сессию через API с no-store; Nest остаётся местом проверки всех прав.
  CORS не включён: браузер использует один origin. Нет доверия произвольному X-Forwarded-For.
- Login ограничен 10 попытками на аккаунт за 60 секунд и 100 на socket IP;
  429 содержит Retry-After. Лимитер ограничен по памяти и работает в одном процессе;
  после рестарта его счётчики сбрасываются. Сессии сохраняются в PostgreSQL.

Подробная политика и источники: [docs/DECISIONS.md](docs/DECISIONS.md).

## Crew: мобильное рабочее место

`/crew` сохраняет четыре серверных представления **Today / Upcoming / Open / Completed**,
пагинацию и размер страницы. Карточки показывают реальные назначения разрешённой команды,
клиента/город, услугу, команду, плановое окно Europe/Rome, исполнение и согласование клиента.
Счётчик относится ко всему выбранному представлению API, а не ко всем работам сразу.
Today использует businessDate сервера. Предупреждение о возможной задержке не меняет план.
Навигация **My work / My team** отмечает текущий раздел, кнопки и поля рассчитаны на телефон.

В деталях визита есть переходы по разделам: выполнение, контакт/доступ, товары, checklist,
подтверждения и материалы. План, фактические этапы и оценка окончания показаны раздельно.
Телефон/email остаются обычными защищёнными данными визита с `tel:`/`mailto:` ссылками.
Доставка и сборка учитываются отдельно; количества общие для заказа, включая другие команды
и предыдущие визиты. Saved finish report показывает неизменный снимок на момент завершения.

**Update task / Update quantities / Finish my team's visit** открывает одну боковую форму.
Она хранит исходный снимок/версию, сохраняет ввод при refresh/503 и блокирует закрытие при
pending или неизвестном результате. **Retry original request** повторяет прежний запрос
с тем же ключом. После перехода назначения в terminal новый результат запрещён, но черновик
остаётся для чтения и подтверждения старого запроса. Потеря доступа убирает все приватные
данные; другой визит открывается без предыдущего редактора. Кнопки действий и возможность
добавления материалов определяет API, права на backend не менялись.

Acceptance, evidence и подписной canvas остаются смонтированными при переходах по разделам,
refresh и открытии редактора. Загрузки/защищённое чтение, подписи, согласия и отчёты используют
прежние операции. Завершение своей команды не завершает другие команды или весь Order.
Визуальная проверка 390/1280, реальная камера/файловый диалог и рисование на физическом
телефоне требуют отдельной приёмки; component tests не заменяют эти проверки.

### My team: состав и контакты

`/crew/team` показывает только разрешённые API команды текущего сотрудника. Участники и
внешние специалисты представлены отдельными карточками: имя/username, отметка **You**,
Active/Inactive member и отдельно Account disabled. Для специалистов видны имя,
специализация, Enabled/Disabled и крупные кнопки звонка/письма по реальным `tel:`/`mailto:`.
У сотрудников телефон/email не выдумываются; пустые контактные поля не создают ссылок.

Поиск по именам, username, специализации и общим контактным данным работает сразу и
локально по уже разрешённой карточке команды, без дополнительных запросов. Счётчики
включают возвращённые API активные и неактивные записи; это не online/доступность для
назначения. **Refresh my team** перечитывает список разрешённых команд и их детали.
Временный сбой сохраняет карточки и поиск; потеря доступа убирает приватные сведения,
а переход в другую команду не возвращает поздний ответ прежней. Страница остаётся
только для чтения: состав и контакты меняет диспетчер/администратор в backoffice.

## Task templates: библиотека задач

`/backoffice/task-templates` доступен ADMIN/DISPATCHER. Полный каталог показывает название,
стабильный code, описание, применимость, severity/priority, обязательность и Enabled/Disabled.
Таблица становится карточками на узком экране. Поиск по названию/code/описанию и Filters
по статусу, обязательности, применимости и важности работают локально по полному ответу
API. **Search templates** и **Apply template filters** применяются отдельно; Escape/Close
отменяют несохранённый выбор. Фильтр применимости выбирает именно настройку шаблона:
**All-service templates** отличается от отсутствия фильтра. Счётчики показывают полный
каталог, Showing — текущий отфильтрованный список. Порядок — priority, затем code.

**Create a task template**, название задачи или **Edit** открывает одну боковую форму.
Поля сгруппированы по содержанию, настройкам задачи и применению. Code задаётся только
при создании и при редактировании доступен только для чтения. Pending блокирует закрытие
и повторное нажатие; ошибки сохраняют ввод. Создание закрывает форму, повторное открытие
начинает новый шаблон; редактирование сохраняет контекст. Обновление того же каталога
не перезаписывает черновик, другой шаблон открывает чистый редактор. Временный сбой API
сохраняет форму; потеря доступа удаляет приватный каталог и черновик.

Прежние POST/PATCH, ограничения и серверные правила сохранены. Изменение или отключение
шаблона не переписывает уже созданные task snapshots и не удаляет историю. Required
шаблоны применяет сервер к новым подходящим назначениям; повторные приезды сохраняют
свой отдельный workflow явно выбранной оставшейся работы.

## Return requests: повторные приезды

`/backoffice/return-requests` доступен ADMIN/DISPATCHER. Реестр показывает заказ/клиента,
оставшуюся работу и причину, статус потребности, готовность к проверке и текущий визит.
На узком экране таблица становится карточками. **Filters** открывает статус и размер
страницы, **Apply request filters** применяет их вместе. Chips/Clear сбрасывают статус,
сохраняя размер страницы. Фильтры и пагинация серверные; порядок — от старых запросов
к новым. Matching requests — весь результат фильтра, остальные счётчики относятся
только к текущей странице. Готовность к разрешению сообщает API.

**Details** открывает полную страницу с разделами Overview, Plan & review, Quantities,
Attempt history и Source report. Переходы по разделам не размонтируют формы. Текущие
количества отделены от неизменного исходного отчёта; история сохраняет принятый scope
каждой попытки. Планирование сгруппировано по командам, задачам, абсолютным целям товаров,
поиску времени и подтверждению preview. Сам поиск не бронирует окно; сохранение снова
проверяет доступность на сервере. Ошибка или фоновое обновление сохраняет draft и исходную
revision, смена запроса открывает чистую форму, потеря доступа убирает приватные данные.

**OPEN** и **PLANNED** оба означают незакрытую потребность. Новый план создаёт отдельный
визит того же заказа. **RESOLVED** требует явной проверки диспетчером после выполнения
условий сервера; разрешение issue или одно планирование не закрывает запрос. Прежние
version/review/Retry и operation keys сохранены. Количества общие для заказа, повторный
приезд не прибавляет уже выполненную работу ещё раз и не меняет исходный отчёт.

## Issues: проблемы и их разрешение

`/backoffice/issues` доступен ADMIN/DISPATCHER. Реестр показывает тип проблемы с иконкой,
описание, статус, доступность для команд, источник, дату и количество связанных материалов.
На узком экране таблица становится карточками. **Filters** открывает статус, тип и размер
страницы: изменения применяются вместе через **Apply issue filters**. Chips/Clear сбрасывают
условия, сохраняя размер страницы. Фильтры и пагинация выполняются прежним backend API.
Matching issues — весь результат фильтра; Open/Resolved on this page — только текущая страница.

**Details** или описание открывает боковую панель с актуальным заказом, товарами, защищёнными
файлами, решением и историей. Подробности загружаются только при открытии. Add issue note,
Resolve/Reopen используют прежние серверные операции, версии и ключи повторного запроса.
Обновление той же проблемы сохраняет черновик и исходную revision; потеря доступа удаляет
приватные детали. Пока сохранение выполняется или его результат неизвестен, закрытие панели
и внутренние переходы заблокированы; используйте **Retry same request**. Материалы открываются
через защищённые API URL, отозванные файлы не имеют ссылки скачивания. Ссылка в полный заказ
сохраняет привязку к конкретной проблеме. Разрешение issue не меняет количества, отчёт команды
или необходимость повторного приезда и не закрывает заказ автоматически.

## Accounts: личные учётные записи

`/backoffice/accounts` доступен только ADMIN: прежний SSR redirect, клиентский guard
и backend `/users` authorization сохранены. Полный каталог показывает имя/username,
роль, Enabled/Disabled и активные членства команды. На узком экране строки становятся
карточками. Поиск по имени/username и Filters по роли, доступу и членству применяются
локально к полному GET `/users`; дополнительных запросов на каждую строку нет.
Сводка отражает исходный каталог, Showing — выбранный срез. Unassigned team members
включает отключённые аккаунты; доступ и членство остаются отдельными измерениями.

**Create an account** и **Edit** открывают одну боковую форму. Username при создании:
3–64 символа по прежнему lowercase pattern; display name до120; пароль12–128.
При редактировании username read-only, пустой New password сохраняет текущий пароль.
Пароль очищается после успешного сохранения; не хранится в browser storage. Ошибка
оставляет ввод, pending блокирует повторную отправку/закрытие. Фоновое обновление
не меняет выбранного пользователя или его черновик; закрытие/другой аккаунт открывает
новый редактор. Потеря доступа удаляет каталог, drawer и парольный draft.

Изменение роли/доступа/пароля отзывает сессии по прежним правилам API, в том числе свою.
Имя само по себе сессии не отзывает. Создание Team member не назначает команду:
используйте **Teams → Members → Add employee**; после создания активного сотрудника
интерфейс предлагает переход к Teams. Реальные аккаунты/пароли при UI-проверках агентом
не изменялись.

## Teams: команды, состав и доступность

`/backoffice/crews` показывает полный защищённый каталог в таблице, на узком экране —
в карточках. Поиск по названию/коду/service area и Filters по активности/среде применяются
локально к полному ответу `/crews`, без дополнительных запросов на каждую команду.
Сводка показывает реальные totals каталога; Showing — результат текущего выбора.
Численность состава видна в детали команды. **Add a team** открывает боковую форму с
прежними полями; ошибки сохраняют ввод, во время создания закрытие заблокировано.

В карточке `/backoffice/crews/[id]` доступны **Overview / Members / Availability /
Specialists**. Вкладки сохраняют формы, выбранного сотрудника, рабочие окна и их
исходную revision. Переход к другой команде открывает новый редактор. Membership
и активность аккаунта показаны отдельно; состав можно искать по имени/username и
фильтровать по активному/историческому членству. Счётчики Members/Specialists показывают
отдельные наборы: внешний контакт не создаёт учётную запись и не входит в состав команды.
Если кандидатов нет, администратор создаёт CREW_MEMBER в Accounts; существующий сотрудник
может быть добавлен после отключения его прежнего активного членства.
Добавление, отключение и реактивация
используют прежние API, сервер проверяет актуальные условия и конфликты.

Availability содержит недельные окна, travel buffer, недоступность и затронутые визиты;
время по-прежнему Europe/Rome. Specialists — внешние контакты без аккаунтов. После
временного сбоя503 формы сохраняются, после401/403/404 прежние данные доступности
удаляются из интерфейса. Auth, CSRF, права, история, seed и схема не менялись.

## Заказы и ручные платежи M3

После обновления исходников выполните `pnpm db:migrate` и отдельно `pnpm db:seed`.
Миграция добавляет таблицы заказов, товаров, платежей и истории; прежние таблицы и данные
сохраняются. Seed добавляет 10 вымышленных заказов Inbox с двумя товарами каждый,
разными состояниями оплаты и примером VOIDED. Существующие заказы и их дочерние записи
не изменяются, даже если пользователь убрал товар, аннулировал платёж или изменил стоимость.
Пароль не требуется, если все demo-аккаунты M2 уже существуют; новый seed его не сбрасывает.

ADMIN и DISPATCHER видят dashboard `/backoffice`, команды `/backoffice/crews`, список
`/backoffice/orders`, создание `/backoffice/orders/new` и карточку `/backoffice/orders/[id]`.
CREW_MEMBER сохраняет интерфейс M2: новые заказы, финансы, внутренние заметки и история
ему недоступны. Прогресс M4 вычисляется по визитам: INBOX без активных визитов,
PLANNED, если есть визит без команды, ASSIGNED, если у всех активных визитов есть команды.
Оплата не завершает доставку и не определяет прогресс планирования.

Dashboard показывает количество и денежные итоги **всех** заказов. Фильтры списка на него
не влияют; это суммы обязательств и записанных платежей, а не бухгалтерская выручка.
Поиск списка ищет подстроку номера, клиента или города без учёта регистра; `%` и `_`
считаются обычными символами. Фильтры услуги, оплаты и планирования применяются сервером.
Сортировка: `createdAt DESC, id DESC`; UI предлагает 10/25/50 записей на страницу.
По умолчанию API возвращает 20 записей, допустимый pageSize — 1–100.
Это offset pagination: при новых записях между запросами состав страниц может сдвигаться.

Orders показывает таблицу с отдельными статусами работы, оплаты и проблем; на узком
экране те же строки расположены как карточки. В колонке **Teams** перечислены команды
неотменённых назначений неотменённых визитов (включая законченное участие). Одна команда
показывается один раз; это не единственный «владелец» заказа. Пустое значение — Not assigned.
В quick preview и полной карточке видны все такие команды. Номер заказа или клик по строке открывает
боковой **Order preview** с реальными контактами, товарами и суммами. Escape / Close preview
закрывает панель и возвращает фокус; список, страница и введённые фильтры остаются на месте.
**Open** / **Open full order** открывает полную карточку с вкладками **Overview / Visits /
Execution / Files / Payments / History**. Обзор содержит контакты, доступ, команды,
товары и раздельные количества. Выполнение/готовность/явное закрытие находятся в Execution,
платёжный журнал — в Payments. Вкладки сохраняют смонтированные формы и canvas;
переключение не сбрасывает черновики, базовую редакцию или ключи Retry. Edit возвращает
Overview; до сохранения/отмены редактирования Visits/Payments заблокированы как прежде.
При открытии другого заказа старый редактор не переносится. История показывает понятную
сводку, подробные изменения раскрываются отдельно.
Компактная панель содержит поиск (Enter / **Search**) и кнопку **Filters** со счётчиком.
Работа, оплата, услуга и проблемы выбираются в shadcn Popover и применяются через
**Apply filters**. Escape / Close отменяет неподтверждённый выбор. Активные условия
видны отдельными метками: каждую можно удалить, **Clear filters** очищает их все и
возвращает первую страницу. **Per page** находится рядом с пагинацией, применяется
сразу и сохраняется при очистке фильтров. Фоновые обновления сохраняют введённый поиск.

Для списка используются локально адаптированные shadcn/ui Table, Sheet, Button, Badge,
Input, Native Select и Popover (`apps/web/components/ui`, MIT attribution рядом). Sheet основан
на Radix Dialog **1.3.1**; helpers — clsx **2.1.1** / tailwind-merge **3.7.0** с префиксом
`tw`. Фильтры используют Radix Popover **1.3.1**; остальные зависимости и серверные операции сохранены.

Стоимость и платежи — целые EUR cents, максимум **2 000 000 000** (€20 000 000) на
заказ/платёж. Поле UI принимает `650,50` или `650.50`, без разделителей тысяч и округления;
`1.005` отклоняется. Оплачено учитывает только RECORDED, остаток = total − paid.
Статусы NOT_REQUIRED/UNPAID/PARTIALLY_PAID/PAID рассчитывает API. Переплата, положительный
платёж при нулевой стоимости и уменьшение total ниже paid запрещены.

Платёж содержит календарную дату, способ, сумму и необязательную заметку. CARD — ручная
отметка уже полученного платежа; карточные реквизиты не вводятся. Сумма/дата/способ после
записи не редактируются. Исправление: **Void entry** с причиной, затем новая запись.
VOID исключает ошибочную запись из расчёта и **не означает возврат денег клиенту**.
Повторный VOID не меняет баланс и историю ещё раз.

Повтор платежа с тем же ключом и нормализованными данными возвращает ту же запись,
включая VOIDED; другой payload с тем же ключом даёт 409. При сетевой ошибке форма
сохраняет ключ и исходные данные для Retry. Для намеренно нового платежа перечитайте
журнал и начните новую попытку. Данные формы не сохраняются в browser storage.
После reload сначала загрузится актуальный журнал. Успешные изменения перечитываются
из API; история сохраняется в одной транзакции с действием.

Редактирование передаёт `expectedVersion`. Изменение заказа/товаров, новый платёж и
первый VOID увеличивают версию; replay её не меняет. При 409 перечитайте карточку перед
повторным редактированием. Снятые товары остаются в БД и истории. DELIVERY_ONLY не
допускает товары с requiresAssembly; DELIVERY_AND_ASSEMBLY допускает смешанный состав.

Ручная проверка M3:

1. Войти диспетчером, открыть Orders → New order, заполнить клиента, адрес, доступ,
   длительность, стоимость и несколько товаров. Сохранить и перезагрузить карточку.
2. Записать часть оплаты, проверить остаток после reload и изменение dashboard.
3. Аннулировать ошибочную запись с причиной; проверить баланс, VOIDED и History.
4. Проверить поиск, фильтры, пустой результат, страницы и экран 390 px.
5. После Logout войти сотрудником: прямой `/backoffice/orders` переводит в `/crew`,
   API `/api/orders` и `/api/dashboard` возвращают 403 без финансовых данных.

## Визиты и календарь M4

После обновления: `pnpm install --frozen-lockfile`, `pnpm db:migrate`, отдельно
`pnpm db:seed`, затем `pnpm dev`. Новая миграция сохраняет M1–M3 и добавляет шесть таблиц
планирования. Seed создаёт только отсутствующие настройки команд и шесть шаблонов задач;
он **не назначает визиты прежним заказам** и не заменяет пользовательские окна/буфер/шаблоны.

В карточке заказа откройте **Visits → Plan a visit**. Введите местные начало
Europe/Rome и длительность, выберите ноль/одну/несколько команд и optional templates.
Один заказ может иметь несколько визитов; несколько команд визита работают в одном окне.
Сервер вычисляет конец и UTC instants. Новый визит — Needs confirmation; клиентское
согласование отмечается отдельной кнопкой **Confirm client agreement**. Сообщения клиенту
не отправляются. Unassigned не занимает команду; Needs confirmation с командой резервирует её.

`/backoffice/planning`: Day / Week с часами, Month и List, дата, Today, назад/вперёд,
All teams или явный выбор команд, независимый Unassigned. Один многокомандный визит
отображается одним событием. На телефоне используется List; клик открывает боковой Visit preview с ссылкой полной карточки.
Выключенные команды со старыми назначениями остаются в фильтрах. Drag-and-drop выключен.
Календарь читает отдельный endpoint всего диапазона, а не первую страницу заказов.
Максимум 42 местных дня и 1000 визитов; превышение явно просит сузить диапазон.

Календарь оформлен с Tailwind и локальными shadcn components. Мини-календарь на широком
экране и Planning date позволяют быстро выбрать дату; Month загружает все шесть недель
с понедельника, включая соседние даты, в пределах прежнего лимита 42 дня. Today следует
Rome-дате; выбор даты вручную прекращает автоматическое переключение дня.
В Display settings доступны сетка 15/30/60 минут и Show weekends. Скрытые выходные
остаются в итогах/Complete visit list; доступен весь 24-часовой день. Цвет определяется
первой командой, многокомандный визит остаётся одним событием; остальные команды видны
в preview и полной карточке. Month +more раскрывает наложенные события.

Teams & filters содержит поиск команд, All teams, Include unassigned и отдельные
Confirmation / Attention / Service / Work progress. Apply подтверждает выбор,
Escape/Close отменяет черновик, chips/Clear убирают применённые условия. Диапазон,
команды и Unassigned проверяются сервером; Search и четыре остальных фильтра применяются
локально к **полному** ответу этого диапазона, не ко всем заказам. Если диапазон слишком
плотный, прежняя явная ошибка API предлагает сузить выбор. Сводка показывает исходный
диапазон, строка Showing — число после локальной фильтрации.

Visit preview показывает план, команды, независимые actual/estimated времена, буферы
и предупреждения; Open full visit ведёт в карточку с Overview / Execution /
Acknowledgements / Reschedule / Files / History. Поля, версии, Retry и canvas сохраняются
между вкладками; другой Appointment открывает новый редактор. Подтверждение/изменения
выполняются прежними защищёнными формами. Calendar не пересоздаётся при refresh или
навигации; черновики поиска/фильтров не запускают запросы. Complete visit list строится
только при раскрытии. Component tests проверяют эти границы обновлений; реальную
плавность, геометрию и touch/canvas нужно подтвердить в браузере и на устройстве.

**Edit visit** переносит тот же Appointment с причиной и expectedVersion. ID, сохранённые
назначения и их снимки задач остаются прежними. Изменение времени сбрасывает подтверждение;
смена только команды сохраняет согласованное время. Снятая команда остаётся в истории,
повторное добавление создаёт новое назначение. Cancel visit с причиной освобождает резерв,
не удаляя визит/задачи/историю. Повтор создания с прежним ключом возвращает прежний визит,
даже отменённый. Retry после сетевой ошибки сохраняет исходные данные и ключ; при неизвестном
результате изменения сначала перечитайте визит. 409 версии отличается от конфликта команды.

В карточке команды редактируются рабочие окна (в том числе выходные и перерывы),
default buffer и интервалы недоступности. Defaults: Пн–Пт 08:00–18:00, buffer 30 минут.
Резерв `[start, end + buffer)` целиком должен помещаться в одно окно одной Rome-даты
и не пересекаться с недоступностью/резервом той же команды. Буфер учитывается у обоих
визитов: после 09:00–11:00 +30 следующий возможен в 11:30; вставка 08:00–08:45 +30
перед 09:00 конфликтует. Настройка buffer 0–180 действует на новые назначения;
снимок старого назначения сохраняется при переносе.

Изменение доступности или отключение команды сохраняется, даже если затрагивает бронь.
Визит остаётся на месте с **Needs attention**. Отмените или переназначьте его явно;
новые/изменяемые резервы проверяются по текущим правилам. Простой комментарий можно
изменить, не устраняя сначала весь конфликт. Ночных/многодневных визитов в M4 нет:
разбейте длительную работу на несколько визитов. Неоднозначное/несуществующее время
при DST отклоняется; часовой пояс устройства не меняет бизнес-слот.

`/backoffice/task-templates`: создание, правка, отключение шаблонов. Обязательные
подходящие шаблоны включаются сервером; assemble products — только для услуги со сборкой.
Текст/required/severity/priority копируются в назначение. Шаблон не переписывает старые
снимки. В форме визита можно менять severity/priority, добавлять шаблоны и снимать optional
задачи; required-снимки убрать нельзя. Unassigned-визит не имеет задач: optional задачи
добавляются после назначения команды. Задачи здесь только планируются, без выполнения.

Правка адреса/услуги/мебели и условий доступа сбрасывает клиентское согласование
активных визитов с историей, сохраняя время, команды и задачи. Стоимость, платёж и VOID
не меняют confirmation или Appointment.version. Правка оценочной длительности заказа
не передвигает визиты: диспетчер должен проверить длительность отдельно.

Добавлены MIT-зависимости: backend Luxon **3.7.2** (`@types/luxon` **3.7.6**),
frontend FullCalendar Standard React **7.1.3**, обязательный `temporal-polyfill` **1.0.1**.
В v7 named-zone встроен; старый `@fullcalendar/luxon3` и Premium plugins не используются.
Остальные закреплённые версии сохранены. Подробные контракты/лимиты — в DECISIONS.

Ручная приёмка: создать визит с двумя командами → посмотреть Day/Week/Month/List и фильтры →
попытаться занять одну команду другим заказом → выбрать корректный слот → подтвердить
клиента → перенести с причиной → после reload проверить Needs confirmation, задачи и
историю → добавить недоступность и проверить Needs attention → отменить визит и
проверить освобождение резерва. Повторить на 390 px; сотрудник не должен получать новые API.

## Работа команды и результаты M5

После обновления выполните `pnpm install --frozen-lockfile`, `pnpm db:migrate`, отдельно
`pnpm db:seed`, затем `pnpm dev`. Новые миграции добавляют execution defaults и evidence
таблицы без сброса прежних данных. Обычный seed не создаёт фактическую работу, фотографии,
issues или завершения и не меняет сохранённые результаты/согласование/пароли.

`/crew` и `/crew/assignments` показывают **Today / Upcoming / Open / Completed**.
Today рассчитывается сервером по плановой Rome-дате; timezone телефона не меняет выборку.
Open включает прошлые незавершённые и partial/blocked попытки. Completed — успешно
завершённые участия команды, а не окончательно закрытые заказы. Карточка своей команды
сохранена по `/crew/team`. Все чтения и действия проверяют текущее членство.

В назначении последовательно **Depart → Arrive → Start work**. Depart требует
CONFIRMED, сегодняшнюю дату, active Crew и актуальный план; другая активная работа
той же команды блокирует новый выезд. После выезда разрешены фактические действия за
пределами планового времени и на следующий день. Отключённую команду можно закончить,
отключённый пользователь доступа не имеет. План не переписывается по факту опоздания.

В IN_PROGRESS команда меняет только свой checklist и **накопленные итоги всего заказа**.
Delivered и assembled вводятся отдельно целыми количествами; оба поля отправляются
вместе. Assembled ≤ delivered ≤ ordered, для товара без сборки assembled=0. Коррекция
вниз требует причину. Required task нельзя пропустить, optional SKIPPED и возврат
в PENDING требуют причину. Цена/платёж не делают checklist-форму устаревшей.

**Finish my team's visit** сохраняет только участие этой команды. COMPLETED требует
закрытых required и DONE/SKIPPED optional задач, но не полного объёма всех команд.
PARTIALLY_COMPLETED/BLOCKED требуют причину и remaining work. BLOCKED допустим уже
после выезда, без фиктивного начала работ. Отчёт фиксирует свои задачи и снимок общих
количеств, автора и actual times. Новые дополнения его не переписывают. Потребность
нового приезда хранится отдельно; resolve issue её не снимает. В M6 диспетчер планирует новый визит того же заказа с явным остаточным scope и отдельно
подтверждает закрытие потребности. Исходный частичный отчёт остаётся неизменным.

После первого Depart обычные перенос/отмена/смена команд и задач визита запрещены.
Материальные условия заказа и состав мебели тоже заморожены; контакты, заметки и
платежи остаются доступны. При отказе черновик сохраняется. Повтор действия использует
сохранённый ключ; при 409 нужно перечитать данные и осознанно открыть новую редакцию.
Фоновые refresh не подменяют версию открытой формы. Offline-сохранения нет: неизвестный
результат отображается ошибкой с безопасным Retry, а не успешным сохранением.

Backoffice показывает actual times, checklist/quantities, finish reports, issues и
return requests в заказе/визите и календарные badges. Есть `/backoffice/issues` и
независимый фильтр Issues в Orders. Прогресс исполнения отделён от оплаты/проблем:
IN_PROGRESS, PARTIALLY_COMPLETED, REQUIRES_ATTENTION либо AWAITING_REVIEW. Последний
означает готовность физической работы к проверке. В M7 подписи/исключения проверяются
отдельно, а Order.COMPLETED появляется только после явного решения диспетчера.
Неоплата не препятствует записи выполненной работы. Финансовые суммы не суммируются
повторно по визитам, задачам или фото.

### Файлы, заметки и проблемы

В Evidence доступны append-only notes, фотографии, документы и issues. Crew добавляет
фото/заметки/issues после Depart, в том числе после finish; читает CREW_VISIBLE материалы
заказа через своё доступное назначение. Backoffice выбирает visibility, default
BACKOFFICE_ONLY. Документ CREW_VISIBLE должен содержать только рабочую информацию:
автоматического обнаружения финансовых данных в пользовательском файле нет.

Один файл на HTTP request, несколько выбранных файлов загружаются последовательно.
JPEG/PNG/WebP до **10 MiB**, только backoffice PDF до **20 MiB**, изображение до **40 MP**.
До **100** READY/неотозванных файлов и **250 MiB** на заказ. Перекодирование WebP удаляет
исходные EXIF/GPS и нормализует ориентацию. SVG/HTML/архивы/исполняемые и повреждённые
изображения не принимаются; HEIC не поддерживается. При неизвестном результате форма
удерживает original File/metadata/key и повторяет только не подтверждённый файл.
После reload сначала прочитайте сохранённую галерею; browser storage не используется.

Байты/thumbnail доступны только через защищённый API с проверкой каждого GET/HEAD,
private/no-store и nosniff. PDF скачивается attachment, не встраивается активным preview.
Range не поддерживается. Backoffice может отозвать файл с причиной, без уничтожения
истории; crew больше не читает его контент. Logout/потеря членства закрывают новый запрос
по старому URL. Уже полученные bytes технически не отзываются. PDF header/EOF validation
не является AV/CDR; антивируса и content disarm нет. Это локальный тестовый storage,
без заявления о готовности к публичному production.

Default private root — `uploads/` в корне workspace, вне public/build и Git. Файлы
переживают build/restart API. `.env` не требуется менять; опциональные STORAGE\_\* описаны
в `.env.example`, limits можно только понизить. Добавлены Sharp 0.35.5 и scoped Multer
2.5.0 security fix; остальные версии сохранены. Next proxy пропускает файл до 20 MiB
с overhead, backend отдельно проверяет тип/размер/квоту.

Для backup остановите записи приложений, сделайте PostgreSQL dump и копию всего
`uploads/` (или своего STORAGE_ROOT) как согласованный комплект. При восстановлении
нужны оба. Не храните backup в Git. Безопасная диагностика:

```bash
pnpm storage:inspect --dry-run
```

Команда ничего не удаляет. Unreferenced файл может быть in-flight; перед ручным
разбором остановите writes и сохраните backup. Автоочистки development storage нет.
Для проверки restart загрузите фото, запишите его ID/URL, перезапустите только API,
снова войдите/обновите карточку и проверьте тот же файл **без seed**.

Ручной сценарий M5: диспетчер создаёт и подтверждает визит с двумя командами →
сотрудник A проходит Depart/Arrive/Start, записывает часть общих количеств и checklist,
фото и finish → сотрудник B видит свои задачи и общие количества, завершает остаток →
диспетчер проверяет actuals/отчёты/готовность. Отдельно проверьте damage issue, partial
finish с return reason, resolve без удаления return need, private/crew-visible PDF,
Retry и две формы с устаревшей version. Refresh/focus перечитывают сервер; в M5 realtime ещё не было; M8 добавляет его по описанию ниже.

**Физический телефон и камера требуют отдельной ручной проверки.** Экран 390 px и
file chooser в браузере не подтверждают съёмку реальной камерой, orientation/формат
конкретного устройства или мобильный браузер. Capture — только необязательный hint;
обычный выбор файла остаётся доступен, getUserMedia не используется.

Ручной smoke test:

1. При запущенных сервисах страница показывает API Reachable и Database Connected.
2. Выполните `docker compose stop postgres`, нажмите Check again: API Reachable,
   Database Unavailable; прямой health возвращает 503.
3. Выполните `docker compose start postgres`, дождитесь healthcheck и нажмите Retry:
   снова Connected без перезапуска API.
4. Остановите только API: Retry показывает API Unavailable и Database Unknown.
5. Проверьте loading и retry, ширину телефона 390 px и отсутствие горизонтального скролла.

Проверка seed выполняется до проверки сохранности: повторный `pnpm db:seed`
должен оставить 10 команд на свежей БД и сохранить существующие значения.
В production seed запрещён. Схема изменяется только миграциями, `synchronize: false`.

Для проверки persistent volume используйте уже подготовленную development БД.
Выполняйте следующие блоки из корня проекта в одной отдельной Bash-сессии.
Не меняйте Compose project name, `.env`, compose-файл или данные команд во время проверки.
После контрольной правки и до её восстановления **не запускайте миграции и seed**:
они могли бы скрыть потерю данных. Снимки сохраняются в приватной игнорируемой `.tmp/`.

```bash
set -euo pipefail
umask 077
mkdir -p .tmp
m1_dir=$(mktemp -d .tmp/m1-persistence.XXXXXX)
printf 'Persistence snapshot: %s\n' "$m1_dir"

# Credentials берутся из окружения контейнера и не выводятся.
m1_psql() {
  docker compose exec -T postgres sh -c '
    PGPASSWORD="$POSTGRES_PASSWORD" PGOPTIONS="-c timezone=UTC" \
      exec psql -X -w -v ON_ERROR_STOP=1 \
      -U "$POSTGRES_USER" -d "$POSTGRES_DB" "$@"
  ' sh "$@"
}

m1_snapshot() {
  m1_psql -qAt -c "SELECT to_jsonb(c) FROM public.crew AS c WHERE code = 'DEMO-01';"
}

m1_wait_postgres() {
  for ((m1_attempt = 0; m1_attempt < 30; m1_attempt++)); do
    if [ "$(docker inspect --format '{{.State.Health.Status}}' "$(docker compose ps -q postgres)")" = healthy ]; then
      return 0
    fi
    sleep 2
  done
  printf '%s\n' 'PostgreSQL healthcheck did not become healthy.' >&2
  return 1
}

m1_volume_name() {
  docker inspect --format '{{range .Mounts}}{{if and (eq .Type "volume") (eq .Destination "/var/lib/postgresql/data")}}{{.Name}}{{end}}{{end}}' \
    "$(docker compose ps -q postgres)"
}

# Сохраняем UUID, исходное name и все остальные значения выбранной команды.
m1_snapshot > "$m1_dir/original.json"
test -s "$m1_dir/original.json"
m1_psql -qAt -c 'SELECT count(*) FROM public.crew;' > "$m1_dir/count.original.txt"

# Подтверждаем фактический named-volume mount нужного каталога данных.
m1_volume=$(m1_volume_name)
test -n "$m1_volume"
printf '%s\n' "$m1_volume" > "$m1_dir/volume-name.txt"
docker inspect --format '{{range .Mounts}}{{if eq .Destination "/var/lib/postgresql/data"}}{{.Type}} {{.Name}} {{.Source}} -> {{.Destination}}{{end}}{{end}}' \
  "$(docker compose ps -q postgres)"
docker volume inspect --format '{{.Name}} {{.Mountpoint}}' "$m1_volume"

# Меняем только name, если строка всё ещё совпадает с исходным снимком.
m1_psql -qAt --set=original="$(cat "$m1_dir/original.json")" <<'SQL' > "$m1_dir/changed.json"
WITH original AS (SELECT :'original'::jsonb AS value)
UPDATE public.crew AS c
SET name = 'M1 persistence ' || substr(md5(clock_timestamp()::text), 1, 12)
FROM original
WHERE c.id = (original.value->>'id')::uuid
  AND to_jsonb(c) = original.value
RETURNING to_jsonb(c);
SQL
test -s "$m1_dir/changed.json"
```

Проверьте сохранение той же строки и всех её значений после обычного restart:

```bash
docker compose restart postgres
m1_wait_postgres
test "$(m1_volume_name)" = "$m1_volume"
m1_snapshot > "$m1_dir/after-restart.json"
cmp "$m1_dir/changed.json" "$m1_dir/after-restart.json"
m1_psql -qAt -c 'SELECT count(*) FROM public.crew;' > "$m1_dir/count.after-restart.txt"
cmp "$m1_dir/count.original.txt" "$m1_dir/count.after-restart.txt"
printf '%s\n' 'PASS: restart preserved the UUID, control name, all values and crew count.'
```

Затем пересоздайте только контейнер `postgres` с тем же существующим volume.
Сравнение container ID подтверждает пересоздание, сравнение volume name — повторное
подключение прежнего хранилища. Между командами ниже миграции и seed также не нужны:

```bash
m1_old_container=$(docker compose ps -q postgres)
docker compose up -d --no-deps --force-recreate --wait postgres
test "$(docker compose ps -q postgres)" != "$m1_old_container"
test "$(m1_volume_name)" = "$m1_volume"
docker volume inspect --format '{{.Name}} {{.Mountpoint}}' "$m1_volume"
m1_snapshot > "$m1_dir/after-recreate.json"
cmp "$m1_dir/changed.json" "$m1_dir/after-recreate.json"
m1_psql -qAt -c 'SELECT count(*) FROM public.crew;' > "$m1_dir/count.after-recreate.txt"
cmp "$m1_dir/count.original.txt" "$m1_dir/count.after-recreate.txt"
printf '%s\n' 'PASS: container recreation preserved the UUID, control name, all values and crew count.'
```

Восстановите исходное `name`. Проверка полного контрольного снимка предотвращает
перезапись параллельной пользовательской правки:

```bash
m1_psql -qAt --set=original="$(cat "$m1_dir/original.json")" \
  --set=changed="$(cat "$m1_dir/changed.json")" <<'SQL' > "$m1_dir/restored.json"
WITH original AS (SELECT :'original'::jsonb AS value),
     changed AS (SELECT :'changed'::jsonb AS value)
UPDATE public.crew AS c
SET name = original.value->>'name'
FROM original, changed
WHERE c.id = (original.value->>'id')::uuid
  AND to_jsonb(c) = changed.value
RETURNING to_jsonb(c);
SQL
test -s "$m1_dir/restored.json"
cmp "$m1_dir/original.json" "$m1_dir/restored.json"
printf '%s\n' 'PASS: original name and all original row values restored.'
```

Если команда или сравнение завершились ошибкой, остановите проверку и сохраните
путь к `.tmp/m1-persistence.XXXXXX`. Не создавайте новый исходный снимок поверх
контрольной правки. После восстановления доступности прежнего volume используйте
сохранённые `original.json` / `changed.json` для последнего блока восстановления;
при новой Bash-сессии снова определите `m1_psql` и установите `m1_dir` в сохранённый
путь. При несовпадении снимка выясните причину до изменения данных. Эта процедура
не удаляет volumes, базы, таблицы или записи.

## Перепланирование и повторные визиты M6

Для существующей development-базы остановите приложения, примените добавочные миграции
`pnpm db:migrate`, затем запустите `pnpm dev`. Повторный seed не нужен для обновления схемы.
Миграции `1792886405000` и `1792886405100` добавляют оценки и return lifecycle, сохраняя
старые значения, IDs, отчёты и файлы. Настройки БД, proxy и сессий M1–M5 используются прежние.

В Planning панель Risks показывает время расчёта, источник риска и затронутую команду;
Refresh перечитывает сервер. Оценка окончания с причиной доступна своему сотруднику и
диспетчеру только после выезда и до finish. Очистка оценки выполняется явно с причиной.
Plan, estimate и actual показываются отдельно. Опоздание сохраняется как факт, план не
переписывается. После finish оценка остаётся историей, расчёт использует actualEnd.

Find available time предлагает общее окно выбранным командам либо альтернативную команду
для одиночного назначения. Поиск: Europe/Rome, 15 минут, 14 дней по умолчанию, максимум
42 дня и 20 предложений с пометкой ограничения. Учитываются рабочие интервалы, перерывы,
недоступность, сохранённые буферы с обеих сторон и другие визиты этого же заказа.
Неизвестное окончание активной просроченной работы блокирует выбираемые предложения
для этой команды до новой оценки или finish. Можно выбрать другой набор команд.
Предложение не резервирует время: выбор открывает preview, отдельное подтверждение и
причина отправляют запрос. Сервер повторяет проверку под блокировками в одной транзакции.
409 сохраняет draft; Refresh не подставляет новую version в старый запрос автоматически.
Начавшийся визит не переносится, его остаток оформляется новым Appointment.

В Return requests диспетчер открывает исходный отчёт, оставшиеся задачи, общие количества
и историю попыток. Plan return visit создаёт новый Appointment того же Order: новые
назначения NOT_STARTED, NEEDS_CONFIRMATION, только явно принятый scope. Выполненные
задачи и optional SKIPPED не копируются; required pending переносится ровно одной команде
со связью sourceTaskId. Новая дополнительная задача требует пояснения. Цели товаров —
абсолютные накопленные количества, не добавление результата ещё раз. Неудачная попытка
не позволяет потерять её обязательные задачи или недостигнутые цели в следующем плане.
Прежняя optional/PENDING работа тоже не исчезает: пока она не перенесена и не выполнена
либо явно пропущена с причиной, потребность остаётся OPEN для следующей попытки.

OPEN → PLANNED означает только назначенный повторный визит. Отмена неначатого визита
возвращает OPEN, сохраняя историю. Частичная/блокированная попытка или новый return-флаг
возвращают OPEN после завершения всех команд этой попытки. Успешная попытка остаётся
PLANNED до явного Resolve диспетчером с причиной: все команды COMPLETED, required scope
DONE, item targets достигнуты, нового return-флага нет. Issue и return request разрешаются
независимо. Исходные finish reports не меняются. Разрешённая цепочка может покрыть старую
partial/blocked работу для AWAITING_REVIEW, но не скрывает другие потребности, issues,
неполные количества, будущие визиты или непокрытые задачи. Финальный Order.COMPLETED
и подписи не входят в M6.

Браузерные проверки M6 отложены пользователем. В конце разработки проверить на 390/1280:
оценка → риск → поиск → preview → перенос/NEEDS_CONFIRMATION; поздний finish с прежним
планом; partial → новый follow-up → выполнение → явный resolve; конфликт занятого после
поиска окна с сохранением draft; отмена и повторная неудача follow-up с полной историей.
M5 B/C, реальная камера/телефон и пользовательская приёмка остаются в том же финальном списке.

## Подтверждение результата и закрытие M7 — решения MVP

Это фиксация подписей в тестовом приложении: без сертификации, проверки личности,
внешнего провайдера и заявления о юридической силе. Подпись подтверждает конкретный
датированный снимок визита, включая частичное выполнение; она не закрывает задачи,
issues, return requests и весь заказ автоматически. Finish по-прежнему сохраняется
без подписей и не блокируется отсутствием клиента.

После терминального результата всех команд и хотя бы одного реального выезда откройте
Visit acknowledgement из карточки назначения или backoffice-визита. Prepare создаёт
серверный общий снимок: отдельные отчёты команд, их собственные накопленные количества,
причины, remaining work и разрешённые рабочие материалы. Количества отчётов не суммируются.
Последующие события не переписывают снимок. В нём нет финансов и внутренних заметок.
Повторный приезд имеет отдельный снимок и отдельные подтверждения.

Нужны один customer slot и по одному staff slot на каждое фактически участвовавшее
назначение. Сотрудник подписывает только свою команду; имя берётся из его актуального
аккаунта. Клиент/представитель вводит заявленные имя/отношение и явно подтверждает
показанный результат на том же устройстве. Client mode скрывает рабочую навигацию,
но не создаёт публичный доступ или роль клиента. Рисование — мышью/пальцем/стилусом,
Clear, Preview и отдельное Save; поле имени не создаёт изображение автоматически.
Рисунок хранится только в памяти до сохранения, черновики не записываются в browser storage.
Недоступный canvas означает честный путь отсутствия подписи, а не искусственный росчерк.

Refused / Absent / Unable to sign записываются для одного требования с причиной.
Диспетчер отдельно Approve/Reject exception с пояснением: исключение остаётся отсутствием
подписи. Pending/rejected блокирует окончательное закрытие. В этом MVP одна подпись
или декларация отсутствия и одно решение review неизменяемы; исправление требует
явно Invalidate общего снимка с причиной, затем Prepare новой редакции и новых подтверждений.
Старые PNG, отчёты, решения и причины остаются историей, не переносятся на новую редакцию.

PNG хранится в PostgreSQL bytea, вне обычных DTO и SSR. Лимиты: исходный и сохранённый
файл до 256 KiB, максимум 2048×1024 / 2 097 152 pixels. Сервер декодирует и перекодирует
PNG без метаданных, отвергает animation, неверный формат, пустое/прозрачное/однотонное
изображение. Непустота не проверяет подлинность почерка. Для узкого MVP multipart-запрос
имеет Content-Length до 272 KiB; неизвестная длина/chunked отвергается 411 до парсера.
Frontend использует конечный Blob/FormData, без ручной установки Content-Length.
Штатный Next proxy сохранён; реальная браузерная проверка этого пути отложена.
На каждом чтении content снова проверяются права, no-store и nosniff; сотрудник видит
customer image и staff image своего назначения. После перевода/отключения/logout доступ
не сохраняется. Уже просмотренную человеком копию технически отозвать нельзя.

В карточке заказа Completion показывает physical readiness и confirmations отдельно,
конкретные blockers и preview revision. Сохраняется покрытие M6: успешный resolved follow-up
может покрыть старую partial/blocked работу, но подтверждения нужны каждому реальному
визиту. Неполные товары/задачи, active/future/unassigned визиты, issues и OPEN/PLANNED
return requests продолжают блокировать закрытие. Исключение подписи их не обходит.
Complete order выполняется явно диспетчером с причиной. Задолженность не блокирует
физически готовый заказ: COMPLETED и UNPAID/PARTIALLY_PAID могут быть одновременно.
Платежи, VOID, допустимая цена и контактные/внутренние заметки остаются отдельными.

Reopen with reason сохраняет прежний CompletionRecord и подписи, не обнуляет результаты.
Новое закрытие создаёт новый record. Новое планирование/return scope требует сначала
явного reopen; материальные поля начавшегося заказа остаются защищены правилами M5.
Новая/reopened issue автоматически и атомарно открывает закрытый заказ, не мешая сохранить
реальную проблему. UI запрашивает подтверждение этого последствия. Resolve issue не
закрывает заказ снова. Invalidate подписанного документа закрытого заказа тоже открывает
его. Старые Retry не воскрешают invalidated документ или прежнее завершение.

Для существующей локальной базы: `pnpm db:migrate`, затем `pnpm dev` на прежних Node/pnpm.

Подтверждённые программные результаты и точные логи перечислены в docs/PROGRESS.md.

## Сигналы изменений и финальная демонстрация M8

Это однопроцессный тестовый MVP. Один EventSource на авторизованный layout/tab читает
`/api/realtime/events` через тот же Next proxy. Сохранение по-прежнему выполняется
прежними HTTP-командами с Origin/CSRF, версиями и idempotency keys. Только внешний
commit разрешает уведомление; rollback/savepoint/audit failure не публикуют изменения.
Сбой доставки не отменяет сохранённую работу. SSE несёт только короткие topics/event ID,
без объектов, денег, адресов, private metadata или PNG. Crew получает лишь разрешённый
scope; private/финансовая правка не создаёт ему отдельный сигнал. Права перечитываются
на batch/heartbeat (15 s), отзыв session/смена scope закрывает прежнее соединение.

Однопроцессный in-memory hub — best effort: событие может потеряться при остановке
между commit и отправкой. Нет durable Last-Event-ID replay/exactly-once/нескольких replicas.
Лимиты: 32 streams включая setup, 4/user, 128 pending hints/stream, packet до 2 KiB;
slow client закрывается. Учитывайте и browser HTTP/1 connection limits нескольких вкладок.

Frontend перечитывает обычный API, не применяет поля из событий. Изменения coalesced
250 ms; один GET на key в полёте и один отложенный повтор. Автоматические reads одного
ресурса не чаще 2 s, dashboard — 5 s. Ручной Refresh присоединяется к уже идущему GET.
Reconnect проверяет `/auth/me` перед чтениями, control sync выполняется раз в 60 s и
восстанавливает пропущенные hints/Today/риски без записи в БД. Скрытые/offline вкладки
не запускают тяжёлый polling; после возвращения сначала проверяется session.

Live / Reconnecting / Periodic refresh / Unavailable показывают транспорт и реальные
результаты чтений. Время — самый старый успешный GET среди активных ресурсов, а не
heartbeat/ready. Временная ошибка API не выдаётся за logout. При подтверждённой потере
прав отменяются старые reads и очищаются private drafts/имена/canvas/Object URLs.
Обычный фон сохраняет поля, исходные revisions, ключи, unknown Retry и рисунок;
изменившийся документ не получает старую подпись. В форме появляется предупреждение
о новых данных, без автоматической подстановки свежей версии в старый payload.

Корневые `pnpm dev`, `pnpm test` и `pnpm test:integration` сначала собирают contracts:
его runtime exports должны соответствовать src types и не зависеть от старого dist.
Проверочные команды добавлены без изменения dependency pins/lockfile/десяти миграций:

```bash
pnpm test:proxy
pnpm test:load --run qa-load-new-id
```

Первая собирает отдельный production Next и проверяет настоящий streaming/cookies/Origin
на изолированном API. Вторая создаёт новый owned набор из 40 заказов, проверяет реальный
HTTP/SSE → coordinator → canonical GET при серии изменений и очищает свой fixture при PASS.
Это программные проверки с platform adapters, не два настоящих браузера. При FAIL load
оставляет собственную безопасную диагностику и fixture; он не перезаписывается повтором.

### Отдельное демо

Обычный `db:seed` остаётся прежним. Opt-in demo использует **postgres-test 5433**, свою
schema/private storage с owner markers и 40 вымышленных заказов разных стадий, 10 команд,
40 сотрудников + ADMIN/DISPATCHER. Оно не меняет development-заказы, файлы или пароли.
Для нового run baseDate = Rome Today, даты/IDs записаны в manifest; повтор возвращает
те же данные и не двигает визиты/не сбрасывает ручные правки. Новый день — новый run.
Частично неудачная подготовка не возобновляется автоматически: диагностика и явный cleanup.

Сначала штатно остановите обычные Next/Nest (Ctrl+C в их терминале). PostgreSQL development
останавливать не нужно. CLI откажется от занятых 3000/3001, не завершит чужой процесс.

```bash
docker compose --profile test up -d --wait postgres-test
pnpm demo:prepare --run furniture-demo-today
pnpm demo:start --run furniture-demo-today
# В другом терминале:
pnpm demo:stop --run furniture-demo-today
# Только когда синтетические данные этого run больше не нужны:
pnpm demo:cleanup --run furniture-demo-today
pnpm dev
```

42 случайных начальных пароля доступны только локально в
`.demo-runs/<run>/credentials.local.json` (0600). Откройте файл своим редактором;
не вставляйте его в чат, скриншоты, логи или Git. Prepare выводит только путь, не значения.
Ручная смена пароля не исправляется повторным prepare, поэтому начальный файл может устареть.
По запросу пользователя видимый demo-баннер убран. Изоляция окружения сохранена.
Manifest содержит стабильные ссылки трёх историй.
Start — foreground supervisor с отдельным `.next-demo/<run>`; stop проверяет PID/start
identity/cwd/run, cleanup — точные DB/storage owner markers. Никаких down -v/prune/reset.
