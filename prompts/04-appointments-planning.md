## 2. Основные продуктовые решения

Ниже — конкретизация допущений MVP. Запиши её в DECISIONS, не называй её
подтверждёнными требованиями работодателя.

Order — обязательство перед клиентом. Appointment — конкретный визит по Order.
Перенос изменяет тот же Appointment; Order.id и платежи сохраняются.
Несколько команд одного визита работают в одинаковом временном окне.
Разные окна — отдельные Appointment одного заказа. Команда бронируется целиком.

Разрешён визит без команды: диспетчер может сначала согласовать время с клиентом.
Такой визит виден как Unassigned, но не занимает ресурс команды.
Клиентское подтверждение и наличие команды — независимые признаки.

В M4 разрешена работа только с ещё не начатыми визитами/назначениями.
Не предоставляй произвольный PATCH execution status. Отмена — отдельная операция.
Отменённый визит остаётся в истории, не резервирует время и не восстанавливается
неявно при повторе запроса. Новый приезд после фактической работы относится к M6.

Новый или перенесённый визит по умолчанию NEEDS_CONFIRMATION. Диспетчер отдельно
подтверждает, что клиент согласовал показанное время. Отправки email/SMS нет.
NEEDS_CONFIRMATION с назначенной командой резервирует её так же, как CONFIRMED:
это не бесплатное окно и не предложение из будущего механизма рекомендаций.

## 3. Модель данных и версии

Адаптируй имена полей к существующим conventions; не дублируй сущности.

### Appointment

Минимально: id, orderId, plannedStartAt, plannedEndAt, confirmationStatus,
confirmedAt/confirmedBy nullable, cancelledAt/cancelledBy/cancelReason nullable,
version, createdAt/updatedAt. Статус планирования может быть SCHEDULED/CANCELLED
или эквивалентным; не смешивай его со стадиями выполнения будущего M5.

Вход формы: локальные дата/время Europe/Rome и durationMinutes. Сервер преобразует
начало и вычисляет конец. Не принимай три независимо противоречащих друг другу
поля start/end/duration. В ответе верни canonical start/end/duration/version.

Оценка Order.estimatedDurationMinutes только подставляет первоначальную
длительность; уже сохранённый визит имеет собственное окно. Изменение оценки
заказа не переносит существующие визиты. Нельзя молча обрезать длительный заказ,
чтобы он поместился в смену: предложи диспетчеру разбить работу на несколько визитов.

### CrewAssignment

id, appointmentId, crewId, состояние ASSIGNED/CANCELLED в пределах M4,
travelBufferMinutes как снимок, timestamps/причина снятия.
Один активный CrewAssignment на пару appointmentId + crewId: DB uniqueness.
Снятие назначения логическое; его задачи и история не удаляются.
Повторное добавление ранее снятой команды создаёт новое назначение, не стирает старое.
При неизменной команде обычный перенос сохраняет assignment ID и снимки задач.

Не копируй клиента и финансовую часть в назначения. plannedStart/end — у визита;
если выбран отдельный DB booking record для ограничения пересечений, его интервалы
обновляются только атомарно вместе с визитом и не становятся вторым источником истины.

### TaskTemplate / Task

Шаблон: stable code, название/описание, active, required, severity LOW/MEDIUM/HIGH,
defaultPriority, applicability для услуги доставки / доставки со сборкой.
Диспетчер может создавать/редактировать/отключать шаблоны; hard delete не нужен.

Task принадлежит конкретному назначению. Копируются текст, required, severity и
priority; templateId можно сохранять как ссылку на происхождение. Это snapshot:
редактирование/отключение шаблона не меняет уже подготовленные задачи.

При назначении выбираются подходящие active-шаблоны, обязательные для услуги
включаются сервером. Диспетчер может менять порядок и severity подготовленных
задач и добавлять задачи из шаблонов. Required-задачи нельзя убрать обходом UI.
Не реализуй произвольный конструктор workflow. Не применяй сборку к DELIVERY_ONLY.
В M4 задачи только планируются; выполнение и checklist interactions — M5.

Существующее назначение не получает новые задачи автоматически при изменении
справочника. Смена команды создаёт снимок задач для нового назначения; перенос
только времени не регенерирует задачи и не возвращает удалённые optional-задачи.

### Защита от устаревшей формы

У Appointment собственная version. Обновление времени/состава/задач, подтверждение
и первая отмена требуют expectedVersion, проверенную после получения блокировки.
Новый платёж меняет Order.version как раньше, но не Appointment.version.
Не заставляй диспетчера заново вводить перенос только потому, что кто-то внёс оплату.

Effective mutation визита и его задач повышает Appointment.version один раз;
идемпотентный replay — не повышает. Визит включён в карточку заказа: логируй изменение
и повышай Order.version согласованно с существующей политикой версии M3. Не ослабляй
expectedVersion M3. Не возвращай клиенту устаревший снимок заказа после mutation.

## 4. Рабочее время, недоступность и буфер

Добавь простую редактируемую конфигурацию на команду в PostgreSQL:
- weekly working windows по дням недели, локальное время Europe/Rome;
- zero или несколько непересекающихся окон за день, что позволяет отразить перерыв;
- default travelBufferMinutes, по умолчанию 30, допустимы целые 0–180;
- датированные интервалы недоступности с причиной, автором и timestamps.

Начальные рабочие окна: Пн–Пт 08:00–18:00. Создавай defaults только для отсутствующей
конфигурации, не заменяй пользовательскую. Должно быть возможно настроить выходной
рабочим днём через UI. Не добавляй календарь государственных праздников и HR-систему.

Рабочее окно не пересекает местную полночь; несколько окон явно описывают смены.
Визит M4 занимает одно рабочее окно в пределах одной местной даты. Многодневный
заказ разбивается на визиты; ночные смены пока не поддерживаются и отклоняются явно.
Недоступность может занимать несколько дней; её начало строго раньше конца.

Резерв назначения: [plannedStart, plannedEnd + travelBufferMinutes).
Сравнивай полные резервы ОБОИХ назначений, в том числе вставляемый визит перед
существующим. Для MVP резерв целиком, включая буфер, должен помещаться в рабочее
окно и не пересекать недоступность. Исключение «без буфера после последнего заказа»
не добавлять скрыто. Буфер — фиксированное допущение, не реальное дорожное ETA.

Новая настройка default buffer применяется к новым назначениям. Снимок уже
существующего назначения не меняется при правке defaults и сохраняется при переносе.
В UI покажи резервируемый буфер; не рисуй его как время сборки у клиента.

Примеры, при условии подходящих рабочих окон:
- A 09:00–11:00 + 30 минут: B той же команды в 11:00 — конфликт.
- B в 11:29 — конфликт; B в 11:30 — допустимая граница.
- A другой команды в 09:00–11:00 — допустим.
- Новый визит 08:00–08:45 + 30 минут конфликтует с уже имеющимся в 09:00.
- При буфере 0 визиты 09:00–11:00 и 11:00–12:00 не пересекаются.

Не вводи жёсткое правило «в команде обязательно ровно четыре человека»:
это размер demo, а не подтверждённое ограничение планирования. Не резервируй
сотрудников отдельно, не планируй external contacts как самостоятельные ресурсы.

### Недоступность возникла после бронирования

Факт отсутствия нельзя скрывать. Изменение рабочих окон, добавление недоступности
или отключение команды НЕ удаляет/переносит ранее созданные визиты и НЕ освобождает
их резервы молча. Разреши зафиксировать изменение доступности, покажи затронутые
активные визиты как Needs attention и предупреждение диспетчеру.

Новые/изменяемые резервы проверяются по текущей доступности. Уже конфликтующий
визит можно отменить или переназначить; редактирование заметки не требует сначала
устранить весь конфликт. Не запрещай фиксацию реальной недоступности из-за брони.

Отметку Needs attention вычисляй по текущим правилам, не выдавай её за execution
статус или подтверждённое опоздание. Старая disabled-команда с назначениями видна в
истории и фильтре с обозначением inactive; для новых назначений она недоступна.

## 5. Время, временные зоны, DST

В интерфейсе явно показывай Europe/Rome. В PostgreSQL храни моменты как timestamptz,
API отдаёт ISO UTC с Z. Weekly windows остаются местными часами, а не «08:00 UTC».
Не используй системную time zone Node/браузера как бизнес-зону.

Выбери проверенную библиотеку для named time zone и строгого разбора local time.
Запиши её точную версию/назначение. Не делай свою таблицу UTC+1/UTC+2 по месяцам.
Не используй new Date('YYYY-MM-DDTHH:mm') как неявный способ интерпретации Rome.

Для MVP несуществующее или двусмысленное местное время отклоняется с понятной
ошибкой; UI просит другое время. Не нормализуй его молча и не выбирай первый offset.
Проверяй переход к UTC отдельно от ограничения рабочих часов, чтобы DST-тест не
проходил только из-за того, что воскресенье закрыто. Допустим и строгий ISO offset
контракт, если он согласован с Rome и UI не выбирает двусмысленный offset без человека.

Сутки и неделю вычисляй как местные границы, затем перевод в UTC. Не прибавляй
всегда 24 часа к UTC для «завтра». Диапазон API [from,to), end exclusive.
Визиты выбираются по пересечению: start < to AND end > from, а не только start BETWEEN.
Дата/время на другом часовом поясе устройства показывают тот же бизнес-слот.

## 6. Транзакции и конкуренция — ключевой приёмочный критерий

Одна серверная операция изменяет Appointment, активные назначения, снимки задач,
confirmation, версии и order ActivityLog атомарно. Конфликт одной команды откатывает
весь многокомандный визит; недопустима частичная запись свободной команды.

Только предварительный SELECT / frontend overlap check не является защитой.
Блокировка Order из M3 сама по себе тоже недостаточна: два разных заказа используют
одну Crew. Нужно сериализовать изменения общего ресурса команды.

Предпочтительный подход без нового extension:
1. READ COMMITTED transaction через существующий DataSource/manager.
2. Блокировка Order, затем существующего Appointment, если это изменение.
3. Блокировки всех затронутых Crew (объединение старых и новых) в одном порядке по ID.
4. После ожидания блокировок заново прочитать резервы/доступность и проверить invariant.
5. Сохранить весь результат/историю/версии; commit; UI обновляется только после успеха.

Один порядок обязателен во всех путях: создание, перенос, смена команд, отмена,
редактирование доступности и demo seed. M2 уже использует User → Crew для членства:
не добавляй обратный Crew → User row lock. Не меняй эту дисциплину без обоснования.

Изменение доступности держит Crew lock, но НЕ берёт затем Order/Appointment locks:
иначе возможен обратный порядок. Затронутые визиты можно читать и помечать в ответе
через вычисляемые предупреждения. Не добавляй под Crew lock обновление order audit.
Сами изменения справочника отражай в его metadata/существующем журнале, если он есть.

При проверке конфликтов читаются чужие committed-резервы; не блокируй в случайном
порядке Order других визитов. Отменённые/снятые назначения исключаются, переносимый
визит не конфликтует со своим текущим резервом.

Другой корректный DB-backed подход, например exclusion constraint, допустим после
объяснения хранения интервалов и конкурентного теста. Не используй только mutex
в одном Node-процессе. TypeORM repositories — только от текущего transaction manager.

Верни 409 с устойчивым code и безопасными деталями для диспетчера: какая команда,
какой период и какой визит мешает. Не возвращай сырые SQL/errors/credentials.
Устаревшая версия и конфликт расписания должны различаться в UI.

### Повтор создания визита

Создание принимает idempotencyKey в scope заказа и fingerprint нормализованных
входных данных. DB UNIQUE предотвращает двойную запись. Тот же key/payload возвращает
тот же визит, включая уже отменённый, без новых назначений/задач/истории. Другой payload
с тем же ключом — 409. Проверяй существующий ключ до повторной проверки свободного окна.
Не включай изменяемые defaults/текущий текст шаблона в повторный fingerprint запроса.
Сетевой Retry сохраняет key и исходный payload; не создаёт новый ключ автоматически.

Для изменения expectedVersion защищает от повторного действия. При неизвестном
результате сначала перечитай визит, не повторяй изменение с «самой свежей версией»
автоматически. Повтор отмены не дублирует audit; задокументируй согласованное поведение
при replay со старой версией (текущее состояние либо 409 без mutation).

## 7. Подтверждение клиента и изменение заказа

Новый визит: NEEDS_CONFIRMATION. Подтверждение — отдельное действие по конкретной
версии, с автором и временем. После переноса начала/конца подтверждение сбрасывается
атомарно; прежнее согласование сохраняется в истории. Смена только команды не
обязана сбрасывать клиентское время; это допущение явно отобрази в DECISIONS.

Правка адреса доставки/города/страны/индекса, услуги или состава/количества мебели
после подтверждения не должна оставлять незаметно устаревшее согласование.
Расширь соответствующую M3 mutation: под Order lock сбросить подтверждение активных
ещё не начатых визитов с повышением их версий и audit в той же транзакции.
Не меняй их время/команды/задачи автоматически. UI сообщает «условия заказа изменились,
проверьте длительность и задачи и согласуйте визит повторно».

Правка цены, платёж или VOID сами по себе не сбрасывают подтверждение визита.
Правка оценочной длительности не меняет забронированные окна; явное предупреждение
диспетчеру достаточно. Зафиксируй точный список полей, меняющих согласованные условия.
При смене услуги шаблоны новых назначений проверяются по актуальному заказу;
старые task snapshots не переписываются молча.

## 8. Прогресс заказа и dashboard

M3 возвращал read-only INBOX для каждого заказа. В M4 замени константу вычислением
по всем неотменённым визитам, без произвольного ручного PATCH progress:

| Состояние | Правило в пределах M4 |
| --- | --- |
| INBOX | Нет активных визитов |
| PLANNED | Есть активные визиты, хотя бы один без активной команды |
| ASSIGNED | Есть активные визиты и у каждого есть хотя бы одна активная команда |

Confirmation и Needs attention отдельны: ASSIGNED может требовать согласования.
При отмене последнего активного визита заказ возвращается в INBOX. Прошедшее плановое
время не завершает заказ и не отменяет визит. Эти правила расширятся выполнением в M5.

Добавь серверный фильтр progress списка, согласованные counts inbox/planned/assigned
на dashboard и ссылки на планирование. Существующие суммы M3 считаются по заказам и
платежам, НЕ умножаются JOIN-ами на appointments/assignments/tasks. Фильтры списка и
календаря не меняют глобальные финансовые итоги dashboard.

Не хранить общий status заказа вручную в трёх независимых таблицах. Можно использовать
один query/projection service. List/detail/dashboard возвращают согласованные snapshots.

## 9. API и права

Согласуй точные имена с проектом и запиши контракты в packages/contracts.
Минимальные use cases:
- создать визит по заказу; прочитать детали и визиты заказа;
- изменить время/команды/подготовленные задачи ещё не начатого визита;
- подтвердить клиентское согласование; отменить с причиной;
- получить календарь по диапазону и командам;
- читать/редактировать weekly windows, buffer defaults и недоступность;
- CRUD без hard delete для TaskTemplate.

Все M4 endpoints пока ADMIN/DISPATCHER. CREW_MEMBER сохраняет M2-интерфейс, M3 запрет
на финансовые данные и 403 на новые диспетчерские endpoints. Назначенные crew-детали
и выполнение придут в M5 с отдельными response contracts, не через раскрытие всех
данных backoffice. Не раздавай заказ целиком сотрудникам «временно до M5».

Сервер проверяет принадлежность вложенного Appointment/Assignment/Task его заказу,
роль, актуальную активность, CSRF, runtime payload. Отклоняй неизвестные/protected поля,
дубликаты crew IDs, снятые task IDs, неподходящие/disabled шаблоны, недопустимые числа.

У календаря bounded range, например максимум 42 местных дня. Unknown crew ID — ошибка,
а не незаметное снятие фильтра. OR по выбранным командам: визит двух команд возвращается
один раз. Unassigned — независимый видимый переключатель. Явно различи All teams и
конкретный выбор, не делай пустой фильтр двусмысленным.

Не используй первую страницу orders как источник всех событий. Календарный endpoint
должен вернуть весь диапазон или явно сообщить, что диапазон нужно сузить. Если есть
pagination событий, UI загружает все страницы перед показом полной картины; нельзя
молча обрезать события и представить занятое время как свободное.

## 10. Backoffice UI

/backoffice/planning:
- Day / Week с часовой сеткой, List; Today, назад/вперёд, выбор даты;
- multi-select команд, All teams, Unassigned, понятные выбранные фильтры;
- параллельные визиты разных команд видны одновременно;
- событие: номер заказа, клиент/город, начало/конец, команды, confirmation, attention;
- стабильное цветовое различие вместе с названиями, не только цвет;
- click открывает визит/форму; форма позволяет создать, перенести и отменить;
- мультикомандный визит — одно событие с несколькими подписями команд;
- забронированный NEEDS_CONFIRMATION не выглядит свободным.

В карточке Order добавь Appointments, создание, назначенные команды, задачи и историю.
В карточке Crew — рабочие окна, буфер и недоступность. Справочник TaskTemplate должен
иметь доступную диспетчеру страницу/секцию; конфигурируемость не ограничивается seed.

Сначала сделай надёжные формы. Drag-and-drop/resize НЕ обязательны в M4 и по умолчанию
выключены. Не добавляй красивый drag без той же backend-проверки, причины переноса,
подтверждения и отката на 409. Ручной перенос через форму уже даёт нужную динамичность.

Обязательно: loading/empty/error/retry, сохранение draft при ошибке, блокировка двойного
submit, reason при переносе/отмене, понятный 409 без автоматической потери ввода.
Канонический ответ/refetch после commit. При быстром переключении недели/фильтра
поздний ответ старого запроса не заменяет текущий календарь.

На 1280 px day/week/list пригодны для десяти команд. Не обрезай наложившиеся события
без способа открыть полный список. На 390 px допустим List по умолчанию с доступными
фильтрами и формами; не пытайся втиснуть десять ресурсных колонок в ширину телефона.

Realtime пока нет: после своих mutation, явного Refresh и focus обновляй связанные
данные через существующий подход. Не добавляй отдельный microservice/Redis.

### Компонент календаря и зависимости

Предпочтителен FullCalendar Standard с TimeGrid day/week и List; либо обоснованный
эквивалент. Standard multi-team фильтр не требует отдельных resource-колонок.
FullCalendar Premium/resource timeline не подключать без отдельного согласования.
Не использовать trial/non-commercial key для потенциального коммерческого продукта.

Проверь актуальную совместимость с закреплёнными React/Next и документацию именно
выбранной major-версии. Не переноси вслепую импорты v6 в v7. Named-zone поведение и
date API также проверяй для выбранной версии, без фальшивого UTC-сдвига.

Разрешены минимальные необходимые calendar/timezone dependencies с точными версиями
и изменением manifests/единственного lockfile. Не требуй неизменного lockfile и
одновременно установки новой библиотеки. Не обновляй остальные версии без причины.
Укажи добавленные зависимости, их лицензии и зачем они нужны; не притворяйся, что
лицензия Standard распространяется на premium-плагины.

## 11. Seed и сохранность данных

Миграция добавляет M4-таблицы/индексы; существующие строки M1–M3 не очищаются.
Начальные task templates: check products, quantities, integrity, assemble products,
clear area, discard packages. Применимость и required/severity — документированные
редактируемые defaults, не якобы утверждённые работодателем бизнес-правила.

Повторный seed сохраняет изменения/disabled шаблонов, рабочие окна и недоступность.
Не планируй принудительно десять прежних M3-заказов при обычном db:seed.

Для красивой демонстрации допустима отдельная явная команда db:seed:planning:
она создаёт собственные вымышленные M4-заказы/визиты с stable private keys, включая
параллельные визиты разных команд, несколько команд одного визита, unassigned и
NEEDS_CONFIRMATION. Создание нового aggregate атомарно; повтор не меняет его дату,
команды, отмены и историю. Не исправляй пользовательские defaults ради fixture.

Если команды недоступны или слоты заняты, корректно пропусти/сообщи конфликт, не
очищай расписание. Новые demo-даты выбирай относительно business date один раз при
создании; повтор на другой день не сдвигает существующие данные. В тестах clock фиксирован.
Production guard — до DB mutation. Секреты не выводить и не копировать из переписки.

## 12. Приёмочные тесты

Unit/contract tests:
- все правила диапазонов, буфера с обеих сторон, границы полуоткрытых интервалов;
- strict local time, DST gap/fold, local day/week boundaries и другой TZ процесса;
- task snapshots, required/applicability, версии, confirmation reset;
- INBOX/PLANNED/ASSIGNED без смешения со статусом оплаты;
- фильтры, Unassigned, unknown IDs, лимиты query; stale-response UI.

Integration на отдельной настоящей test PostgreSQL, без fallback на development:
1. Один заказ с двумя визитами; новый визит не создаёт второй Order.
2. Две разные команды могут одновременно работать; одна команда не может.
3. Буфер 30: 11:29 запрещено, 11:30 разрешено; буфер 0: касание разрешено.
4. Многокомандный визит откатывается целиком при конфликте одной команды.
5. Рабочие окна, перерыв, недоступность, disabled Crew проверяются сервером.
6. Два разных Order одновременно бронируют одну Crew: один успех, второй 409.
7. Create против reschedule и два переноса в один слот: нет двойной брони.
8. Переносы с несколькими Crew в разном порядке не зависают из-за неверного lock order.
9. Два запроса с одной appointment version: один результат, второй stale 409.
10. Одинаковый idempotencyKey: один визит, один комплект задач/истории; replay после
    отмены не воскрешает бронирование. Тот же key с иным payload даёт 409.
11. Неудачный перенос сохраняет старое окно, команды, confirmation, задачи и историю.
12. Отмена освобождает резерв; повтор не создаёт ещё одну запись отмены.
13. Конкурентная смена доступности/disable и бронирование имеет согласованный результат:
    если блокировка зафиксирована раньше, новое бронирование не проходит; если раньше
    прошла бронь, отсутствие фиксируется, а визит становится Needs attention.
14. Смена времени сбрасывает confirmation; изменение цены/платёж/VOID — нет.
15. Смена адреса/услуги/объёма сбрасывает согласование без молчаливого переноса.
16. Изменение шаблона не меняет task snapshot; перенос не регенерирует задачи.
17. Отмена последнего активного визита возвращает INBOX; dashboard financial totals
    одинаковы при одном и нескольких визитах/назначениях/задачах заказа.
18. CREW_MEMBER получает 403 на каждый новый backoffice endpoint без чужих данных.
19. Ownership вложенных IDs, CSRF, disabled sessions, ошибки audit с rollback.
20. Недеструктивные повторные/конкурентные seeds и повторная миграция.

Конкурентные тесты — отдельные соединения и наблюдаемое перекрытие транзакций,
как в M3. Два последовательных await не доказывают отсутствие гонки.
Ограничь ожидания тестов, чтобы deadlock/зависание не стало бесконечным PASS-ожиданием.

Browser smoke через настоящий Next proxy → Nest → изолированную test-БД:
создать визит → назначить две команды → увидеть в day/week/list → фильтровать по
каждой команде без дублей → попытаться создать конфликт → сохранить правильный слот →
подтвердить клиента → перенести с причиной → увидеть NEEDS_CONFIRMATION после reload →
проверить задачи/историю → отменить → увидеть освобождение времени.
Отдельно проверить доступность/attention, error/retry, 390/1280 px и устройство с
другим timezone. Временные credentials использовать приватно и не публиковать.

## 13. Завершение

Выполни реально: pnpm lint, format:check, typecheck, test, test:integration, build;
примени новую миграцию и повтори её, проверь seed, browser smoke и M1–M3 regression.
Перед development migration сохрани доступную безопасную контрольную информацию,
после проверь сохранность прежних данных. Не запускай destructive QA в development.

Обнови README, DECISIONS, PROGRESS; при необходимости уточни DOMAIN_RULES с явной
записью изменения. Укажи точный набор новых endpoints, limits, UI, dependencies,
правил confirmation/availability и snapshot buffer. Предыдущие PASS не называй новыми.

Финальный отчёт по-русски:
- что реально реализовано и что сознательно осталось M5/M6;
- новые файлы/миграции/dependencies и сохранность старых данных;
- команды и фактические результаты, отдельно concurrent и browser сценарии;
- известные ограничения и ручной сценарий для диспетчера;
- какие процессы остались работать.

BLOCKED — с причиной, не выдавать за PASS. Не отмечай пользовательскую приёмку
автоматически. Не делать commit/push/deploy и не переходить к M5.
