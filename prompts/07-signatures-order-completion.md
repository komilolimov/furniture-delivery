## 1. Цель и границы

Работа команд закончена → подготовлен неизменяемый результат визита → клиент
и представители команд подтверждают именно этот результат либо диспетчер
рассматривает отсутствие подтверждения → сервер показывает условия закрытия →
диспетчер явно закрывает заказ, если все условия выполнены.

Сохранить различия:
- FinishReport / COMPLETED назначения — фактический результат одной команды.
- Подписанный результат визита — подтверждение конкретного исторического снимка.
- Order.COMPLETED — отдельное операционное решение по всему заказу.
- Оплата, issues и потребность повторного приезда остаются отдельными измерениями.

Подписывать можно и частичный/неуспешный результат. Подпись не отмечает задачи DONE,
не увеличивает quantities, не разрешает issue и не снимает return request.
Запись факта finish не зависит от наличия подписей.

Включить: рисунок подписи, имена/роли подписантов, подписываемый снимок, отказ/отсутствие
с причиной и проверкой диспетчера, readiness, явные complete/reopen, историю и права.
Не включать: квалифицированные/сертифицированные подписи, внешнего провайдера,
проверку личности, клиентский аккаунт/публичную ссылку, OTP/SMS/email, PDF-генератор,
биометрический анализ, realtime/offline/PWA, GPS, платежные интеграции и M8.
В UI/README назвать это фиксацией подписей в тестовом приложении; не обещать
юридическую силу, сертификацию или подтверждение личности клиента.

## 3. Что именно подписывается

Решение MVP: один общий подписываемый снимок на Appointment. Он доступен после
терминального результата всех его неотменённых CrewAssignment и хотя бы одного
реального выезда. При активной/неначатой второй команде общий результат ещё не готов;
это не мешает первой команде закончить свой FinishReport по правилам M5.
Неначатый отменённый визит не нуждается в подписях.

Требования к одному снимку:
- одна подпись клиента/его представителя на общий результат визита;
- по одной подписи сотрудника от каждого реально участвовавшего назначения команды,
  а не всех четырёх работников команды;
- недостающее подтверждение рассматривается отдельно для конкретного требования.

Сотрудник подтверждает свою часть, явно выделенную в общем снимке. Клиент видит
все зафиксированные результаты этого визита, включая частичное выполнение/проблемы.
Сотрудники не подписывают за другую команду. Для повторного визита создаётся отдельный
снимок: подписи первоначального выезда не переносятся на follow-up.

Подготовка снимка — явный POST с idempotencyKey, не побочный эффект GET.
Backend строит его из серверных данных в согласованном состоянии. Не принимать
готовый отчёт, автора, actual times, amounts или snapshotHash как доверенные поля клиента.
Пример состава:
- schemaVersion, ID/номер заказа, Appointment ID, серверные createdAt/createdBy;
- имя клиента, адрес, услуга и описания товаров без финансов/внутренних заметок;
- planned/actual time, команды, assignment IDs и immutable FinishReport IDs;
- результаты задач и количеств ИЗ отчётов с указанием времени каждого снимка;
- причина/remainingWork и известные на момент подготовки issues/return scope;
- разрешённые ссылки на доказательства, их ID и доступные checksums;
- текст подтверждения с версией, без формулировки об отказе от прав или отсутствии
  любых претензий, если зафиксированы проблемы.

Количества разных отчётов накоплены по заказу: НЕ складывать их. Явно показать,
например, «команда A зафиксировала 1/2; команда B позднее зафиксировала 2/2».
Не подменять snapshot первой команды текущими totals после второй/повторной работы.
В снимке нет price/paid/balance, internalNotes, сырого ActivityLog, ключей хранения.

Один текущий снимок визита; повтор подготовки возвращает существующий текущий,
а не создаёт лишнюю редакцию. Сохранять canonical serialization и SHA-256 снимка
на сервере как идентификатор содержимого. Хеш не называть цифровой подписью или
доказательством личности; не доверять хешу, присланному браузером.

Содержимое опубликованного снимка неизменно. Новые заметки, последующие результаты
или разрешение issue не переписывают его. В UI рядом могут быть текущие данные,
но с явным разграничением «снимок от ...» / «состояние сейчас».
Новая проблема после подготовки учитывается в текущей карточке и readiness;
подпись под снимком не утверждает, что событий после его даты не было.

Если требуется исправить сам подписываемый документ: ADMIN/DISPATCHER явно
инвалидирует его с причиной; старый документ/подписи остаются историей, новая редакция
готовится отдельно и требует новых подтверждений. Нельзя автоматически перепривязать
старый рисунок к новому snapshot. Не создавать общий редактор произвольного отчёта.

## 4. Подпись, подписант и отсутствие подписи

У каждой подписи: snapshotId/hash, signer kind CUSTOMER или CREW, assignmentId
для CREW, имя на момент подписания, серверное recordedAt, capturedByUserId,
PNG/digest и idempotency metadata. Точные имена сущностей адаптировать к коду.
Одна действующая подпись/одобрённое исключение на обязательное требование снимка;
закрепить уникальность и состояния в БД, не только disabled-кнопкой.

CREW подписывает текущий активный участник соответствующей команды. User ID и имя
получать из сессии/БД, не из произвольного actorId. Проверять актуальное членство
на каждом действии и после ожидания locks. Active user выключенной Crew может
подтвердить её уже выполненную работу по исключению M5; disabled user — не может.
ADMIN/DISPATCHER не выдаёт свой автограф за подпись сотрудника другой команды.

CUSTOMER: имя и при необходимости отношение к заказчику вводятся как заявленные
данные; capturedBy — реальный сотрудник/диспетчер, принимающий подпись на устройстве.
Не создавать фиктивный customer User и не утверждать, что его личность проверена.
Клиенту показываются снимок и отдельное подтверждение согласия с этим результатом;
checkbox не включён заранее. Поле имени само по себе не заменяет рисунок.

Для refusal/absence/unable-to-sign фиксировать конкретный slot, тип и непустую
причину. Нет рисунка — нет SIGNED. Диспетчер отдельным действием одобряет/отклоняет
исключение с пояснением, своим actor/time и audit. Одобрение означает только
«этого подтверждения нет, причина рассмотрена», а не полученную подпись.
Допускается исключение по клиенту или отсутствующему представителю команды;
решение локально для одного slot/snapshot, без кнопки «обойти все проверки».
Pending/rejected исключение блокирует закрытие. При ошибочной подписи/исключении
инвалидировать снимок явно, а не менять его задним числом.

Фактические timestamps — серверные. Не принимать прошедшую дату подписания,
имя другого сотрудника или подпись из предыдущего визита. Старые выполненные визиты
после миграции показывают «подтверждение отсутствует»; только реальное действие
или явно одобренное исключение может закрыть это требование.

## 5. Изображение подписи и приватность

Для этого маленького MVP выбрать небольшое PNG в PostgreSQL bytea вместе с записью
подписи: это отдельная узкая модель, не перенос всех фотографий в БД. Метаданные,
изображение, receipt и audit должны коммититься вместе. Не размножать существующий
file-storage pipeline ради маленького PNG. Не возвращать bytea/base64 в обычных DTO.

Принимать одно PNG на специализированном защищённом endpoint. Defaults решения M7:
не более 256 KiB исходных и сохранённых bytes, габариты не больше 2048×1024 и
не больше 2 097 152 pixels. Отклонять invalid/animated PNG, SVG/HTML, чужие форматы,
пустые/полностью прозрачные/однотонные изображения. Ограничить тело запроса до разбора.
Использовать существующий декодер: проверить фактический формат/размеры, безопасно
перекодировать с удалением метаданных, ограничить результат. Проверка непустоты
не считается проверкой подлинности почерка. Синтетические тестовые штрихи допустимы
только в test fixtures; не генерировать подписи реальным людям/старым заказам.

Ввод для UI — canvas, мышь/палец/стилус через Pointer Events; clear, preview,
явное save, обработка pointercancel, сохранение текущего рисунка при resize/DPR
и rotation, без блокировки прокрутки всей страницы. Назначить CSS touch-action
локально зоне рисования. Не собирать давление, скорость, GPS или биометрические признаки.
Нет автоматического сохранения при каждом движении или подписи при нажатии Finish.

Декодирование выполнять с ограничениями до длинной бизнес-транзакции, но после
декодирования внутри транзакции заново проверить session, права и состояние snapshot.
Session expired/invalidated snapshot не должны разрешать поздний сохранённый upload.

Защищённый GET content: новая проверка role/членства/assignment/order на каждом чтении,
Content-Type image/png, nosniff и Cache-Control:no-store. Не /public, не base64 в SSR,
не общая галерея и не неограниченный доступ любому залогиненному пользователю.
ADMIN/DISPATCHER видит подписи заказа. Текущий участник визита — клиентскую подпись
этого снимка и подпись своего назначения; чужую staff-подпись показывать максимум
как статус без изображения. Другой follow-up той же команды сам по себе не даёт
доступ к росчеркам посторонних старых назначений. Прежний участник после перевода
теряет доступ к контенту. Новое обращение после logout — 401, а не кешированный API PASS.
Не обещать удаление копии, уже просмотренной/сохранённой человеком на устройстве.

Запретить отражение PNG/base64, имён клиента и credentials в error/log/audit payload.
Audit содержит IDs/тип действия/причину и hash, а не сам рисунок. Не хранить рисунки
и sensitive drafts в localStorage/sessionStorage. При logout/потере доступа очищать
чувствительный UI state и object URLs. Сохранять черновик в памяти при допустимом Retry.

## 6. Readiness и финальное Order.COMPLETED

Использовать единый серверный resolver M6 для физической готовности и покрытия
старой partial/blocked работы. Не возвращаться к условию «каждое историческое
назначение обязательно COMPLETED»: оно сломает успешно выполненные return chains.
Не вычислять готовность по надписи в UI или одному cached progress.

GET readiness возвращает canComplete и явные blocker codes с безопасными ссылками:
- неполные quantities или обязательные/неурегулированные задачи;
- активная работа, будущий неначатый либо Unassigned визит;
- непокрытый partial/blocked scope;
- OPEN issue и незакрытые return requests (OPEN и PLANNED);
- отсутствующий/инвалидированный снимок реально выполненного визита;
- отсутствующее подтверждение или pending/rejected exception любого требуемого slot.

Решение M7: подтверждения нужны для каждого фактически выполненного визита, включая
partial/blocked, а не только последнего удачного. Если клиент отсутствовал при
неудачном выезде, предусмотрено явное исключение, а не выдуманная подпись.
M6 coverage разрешает остаток работ, но не переносит подписи между визитами.
Отменённые до начала визиты/назначения не создают требований.

Независимо показать физическую готовность и готовность подтверждений. Пустой заказ,
полный платёж, единственная подписавшая команда и простое наступление plannedEnd
не должны давать canComplete. Неоплата/частичная оплата не блокирует физическое закрытие.

Финальный complete — явное действие ADMIN/DISPATCHER, не следствие последней подписи.
Под Order lock повторно проверить актуальные права, readiness, версии и подтверждения.
Записать неизменяемый CompletionRecord с actor/time, snapshot/signature/exception IDs,
основанием покрытия M6, операционным результатом и audit/receipt. Одновременно указать
текущий действующий completion заказа. Один действующий completion на Order.
Избегать отдельного сервиса/БД или нового универсального движка состояний.

Для формы закрытия использовать ожидаемую revision/fingerprint операционного решения
либо совместимый существующий version pattern. Платёж не аннулирует подписанный снимок;
консервативный version conflict требует обновить preview, но не подписывать всё повторно.
На commit нельзя доверять клиентским canComplete, status, paid, actor или timestamps.

Order.progress показывает COMPLETED только при действующем завершении; в остальных
случаях прежний resolver M6. Обновить detail/list/dashboard/filter/calendar/crew summaries
с явными публичными проекциями. Не создавать второй несогласованный manual status.
Новые JOIN не умножают financial totals, количество issues или return requests.

## 7. Повторное открытие и действия после завершения

CompletionRecord и подписи исторические, их нельзя удалить или переписать.
ADMIN/DISPATCHER может явно reopen с причиной и expected current completion/revision.
Reopen снимает текущую отметку закрытия, сохраняет событие/предыдущее закрытие,
но НЕ сбрасывает task/quantity/FinishReport, не начинает работу заново и не создаёт визит.
Следующее закрытие — новый CompletionRecord; прежний успешный Retry его не подменяет.

Новая или повторно открытая issue после закрытия должна быть принята по прежним правам
M5 и атомарно переоткрыть заказ с причиной «reported/reopened issue <id>» и audit.
В UI заранее указать это следствие и запросить явное подтверждение действия.
Crew не получает универсальный reopen или доступ к backoffice; он лишь сохраняет
реальное сообщение о проблеме своего доступного заказа. Не запрещать сообщать повреждение
ради сохранения зелёного COMPLETED. Resolve issue затем не закрывает заказ автоматически.
Если нужен следующий выезд, диспетчер явно планирует его уже в открытом заказе, сохраняя
существующие правила M4/M6; не редактировать старый finish или RESOLVED request молча.

Инвалидация обязательного подписанного снимка/его исключений завершённого заказа
также атомарно переоткрывает его с причиной. В этом MVP исправление подписи оформлять
через инвалидацию снимка, без физического удаления PNG/истории и без скрытой замены.

Матрица совместимости:
- payment/VOID и допустимая правка цены по M3 — разрешены, не переоткрывают;
- обычные contact/internal notes и append-only evidence — по прежним правам,
  подписанное содержимое не меняется; новая проблема оформляется через Issue;
- новое планирование/return scope/действия, меняющие обязательства, — сначала явное
  reopen, иначе ORDER_COMPLETED_REOPEN_REQUIRED; проверить существующие M4/M6 endpoints;
- материальные поля и исполнение завершённых назначений остаются защищёнными M5;
- чтение истории сохраняется, подписи/финансы не появляются в лишних crew DTO.

## 8. Транзакции, версия, повторные запросы

Переиспользовать порядок auth/User/Session → Order → дочерние locks фактического M6;
не вводить обратные locks и nested transactions. Один transactional manager.
Все mutation paths, влияющие на готовность, должны сериализоваться с complete через
тот же Order lock. После ожидания повторно проверять права и актуальные записи.

Idempotency обязательна для prepare, signature/absence, exception review, complete,
reopen и invalidate. Нормализованный payload fingerprint + durable receipt; один
ключ/одинаковый payload — та же логическая операция без второго audit/изображения.
Другой payload с тем же ключом — 409. Два ключа одной подписи не обходят unique slot.

Особо: старый complete replay после reopen не закрывает заказ снова; replay старой
подписи после инвалидирования не восстанавливает её действительность. Возвращать
исходный operation ID и актуальное разрешённое состояние, а не ложное «сейчас закрыто».
Idempotency не отменяет повторную авторизацию. Не путать version для разных signer slots:
подпись A не должна бесконтрольно затереть/заменить B; определённый conflict допустим.

Ошибки audit/receipt/insert отменяют всю бизнес-транзакцию вместе с PNG.
Для complete против create/reopen issue оба порядка commit согласованы:
issue первой → complete отклонён; complete первой → issue сохранена и заказ переоткрыт.
Не допускается финальное COMPLETED одновременно с неучтённой открытой проблемой.
Аналогично проверить races с новым планом, exception/invalidate/reopen и сменой прав.

## 9. API и UI без нового приложения

Конкретные маршруты адаптировать к проекту; два отдельных набора response DTO.
Нужны операции: prepare/read visit acceptance, sign own staff/customer slot,
report absence/refusal, staff exception approve/reject, invalidate, protected content,
backoffice completion-readiness/complete/reopen/history.
Не открывать backoffice Order API для crew и не принимать произвольный Patch status.

Crew: раздел «Visit acknowledgement» после терминального исхода всех команд,
ссылка из своей карточки, snapshot preview, подтверждение собственной части,
режим клиента на том же устройстве, состояние недостающих подписей и ожидания проверки.
Если другие команды ещё работают, объяснить причину недоступности общего снимка.
Клиентский режим не раскрывает navigation/admin controls/financial/internal content
и не меняет auth роль сотрудника; это presentation, не отдельный публичный доступ.

Backoffice: снимки и их история, отказы, отдельное review исключения, список blockers,
preview закрытия, явное Complete order и Reopen with reason. При наличии недостатков
показать, что сделать, а не только disabled-кнопку. Заказ с долгом после закрытия
показывает оба независимых признака: COMPLETED и UNPAID/PARTIALLY_PAID.

Loading/empty/error/Retry/409; удержание draft и исходной версии, не подставлять новую
version в старую подпись. Неполученный ответ — «результат неизвестен», не успех.
Один frozen key/payload на попытку, безопасный canonical refetch после commit;
доступные labels/кнопки для клавиатуры; рисование недоступно — честное исключение,
а не автоматическая картинка из набранного имени. Не добавлять PDF или print-подсистему.

## 10. Программные проверки

Использовать изолированную существующую test PostgreSQL; signatures только синтетические.
Проверять поведение, не фиксированное число тестов. Минимально покрыть:

1. Один/несколько crew: собственные slots, один customer slot, чужое signing запрещено.
2. Неначатая вторая команда блокирует общий снимок, но не прежний finish первой.
3. Partial/blocked можно подписать честно; quantities/задачи/issue/return не изменились.
4. Snapshot строится сервером, без финансов/private fields; hashes стабильны,
   его содержимое/подписи не переписываются при работе следующего визита.
5. Отсутствующие имя/consent/рисунок, blank/transparent/invalid/oversized PNG отвергаются;
   реальная decode/re-encode обработка, ограничения bytes/pixels, без утечек.
6. Два конкурентных signing одинакового slot и повтор после потерянного ответа:
   одна запись/PNG/audit; другой payload того же key — конфликт.
7. Membership/user/session revoked между decode/ожиданием и commit — отказ;
   cross-order IDs, forbidden role, Origin/CSRF, content после logout/перевода — отказ.
8. Refusal/absence не SIGNED; pending/rejected exception блокирует; approved по одному
   slot не покрывает другие и не обходит физические blockers.
9. Open issue, return OPEN/PLANNED, future/unassigned/active visit, неполный объём,
   непокрытые задачи/partial — complete отклонён с конкретными причинами.
10. M6 resolved return coverage позволяет завершить физически выполненный заказ,
    не меняя старые outcomes; confirmations каждого фактического визита отдельны.
11. Полностью оплаченный, но невыполненный заказ закрыть нельзя; выполненный с долгом
    закрывается при выполнении прочих условий, payment ledger не меняется.
12. Complete идемпотентен/конкурентен; сбой audit откатывает; сохраняются actor/time.
13. Complete vs issue create/reopen в обоих порядках commit: согласованное состояние.
14. Complete vs новый Appointment/return plan, invalidation/exception review и
    revoke authority: нет закрытого заказа с незаконно добавленной незакрытой работой.
15. Reopen сохраняет старый CompletionRecord и signatures, ничего не обнуляет;
    reclose создаёт новую запись; старый replay не закрывает повторно.
16. Invalidate документа с причиной: старые bytes/подписи исторические, новые не
    наследуют их; если заказ закрыт — reopen атомарно. Старый Retry не оживляет документ.
17. Readiness/detail/list/dashboard едины; деньги/counts не размножаются дочерними JOIN.
18. Миграции fresh/repeat/upgrade M6 сохраняют old columns/rows; два seed не меняют
    подписанные snapshots, PNG bytes, exceptions, completion/reopen историю и старые данные.
19. Component tests: preview, partial текст, own slots, refuse/review, draft при 409,
    неизвестный результат, double-submit, retry type=button, canvas clear/cancel/resize
    с допустимыми mocks. Mocks canvas не объявлять проверкой реального телефона.

Реальные конкурентные тесты — независимые соединения/барьеры PostgreSQL, не sleep
вместо наблюдаемого перекрытия. Существующие регрессии M1–M6 не ослаблять/не пропускать.

## 11. Завершение работы и отложенная приёмка

По окончании кода последовательно выполнить lint, format:check, typecheck, unit,
integration, build и git diff --check на закреплённых версиях. Сохранить реальные
stdout/stderr/exit codes и связь с проверенными исходниками, без secrets/PNG в логах.
После исправлений повторить затронутые проверки; полный gate в конце, не после
каждой правки отчёта. Исторические FAIL/причины сохранить, не повышать timeout ради PASS.

Development-миграции допустимы после test-успеха, проверки правильного target и
контрольного сравнения прежних данных. Не запускать development seed для создания
подписей/закрытий, не сбрасывать пользователей/volumes. Fixture cleanup только свой.
Если dev работал — восстановить, указать реальные процессы. Startup не считать UI PASS.

Обновить README, DECISIONS, DOMAIN_RULES, PROGRESS. В существующий список финальной
приёмки добавить, не удаляя отложенные M5/M6 проверки:
- обычный и многокомандный визит → реальные штрихи мышью/пальцем → reload → закрытие;
- partial/issue → подписи частичного результата → отсутствие final close → follow-up
  с остатком → resolve → отдельные подписи follow-up → закрытие;
- отказ клиента → pending exception → проверка диспетчера → закрытие только при готовности;
- новая проблема после complete → reopen с сохранением подписи/истории, затем новое решение;
- 390/1280, физический телефон/rotation/canvas, ошибки/retry, защищённый content.
В этом задании браузер НЕ запускать, пометки UI: DEFERRED BY USER, не PASS.

Финал: что реализовано, новые миграции/решения, реальные команды и результаты,
ограничения, оставшаяся проверка, состояние процессов. Короткий отчёт, без реестра
сотен hashes. M7 CODE CHECKS отражает фактический запуск; USER ACCEPTANCE PENDING.
Ни M5, ни M6, ни M7 не становятся ACCEPTED автоматически. После M7 остановиться.
M8, commit, push и deploy не выполнять.
