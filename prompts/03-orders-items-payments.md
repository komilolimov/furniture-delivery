Это задание для Codex, а не готовая реализация. Выполнять отдельным запросом пользователя после проверки M2. Новые уточнения поведения ниже относятся только к M3; это инженерные решения для MVP, не новые требования компании.

Прочитай `AGENTS.md`, `docs/PROJECT_SPEC.md`, `docs/DOMAIN_RULES.md`,
`docs/MILESTONES.md`, `docs/DECISIONS.md`, `docs/PROGRESS.md` и текущий код M1/M2.

## 1. Результат этапа

Диспетчер входит в backoffice, создаёт заказ на доставку мебели или доставку со сборкой,
задаёт клиента, адрес, условия доступа, товары, оценку длительности и общую стоимость.
Добавляет вручную платежи, видит оплачено/остаток/статус оплаты и историю изменений.
После reload и нового соединения с API данные сохраняются.

Реализовать `Order`, `OrderItem`, `Payment`, `ActivityLog`, API, формы, dashboard,
поиск, фильтры и пагинацию. Работать с настоящей PostgreSQL, а не с mock/localStorage.

Не реализовывать M4–M8: визиты, назначения команд на заказы, календарь, планирование,
чек-листы выполнения, статусы «в пути/доставлено/завершено», файлы, подписи, issues,
realtime и перепланирование. Не добавлять пустые таблицы будущих модулей.

## 2. Модель заказа

Добавь миграцию, не переписывая уже применённые M1/M2 migrations.
Названия таблиц/колонок согласуй с существующим проектом.

Поля заказа:
- UUID и читаемый уникальный номер, формируемый сервером;
- customerName, contactName, phoneNumbers, email;
- address, city, country; postalCode при необходимости как обычное поле;
- serviceType: `DELIVERY_ONLY` или `DELIVERY_AND_ASSEMBLY`;
- описание работ и положительное целое `estimatedDurationMinutes`;
- этаж, наличие лифта, доступность подъезда, парковка, ограничения, заметки по доступу;
- отдельные внутренние заметки диспетчера и заметки для команды;
- итоговая стоимость `orderTotalCents`, валюта EUR;
- createdAt/updatedAt и серверные идентификаторы авторов;
- версия для защиты редактирования от устаревших форм.

Обычные inputs, textarea и подходящие переключатели: без карт, геокодинга и CRM.
Контакты храни как снимок данных заказа; отдельный Customer CRUD в M3 не нужен.
Документируй обязательные поля и разумные пределы длины/количества элементов.
Не трактуй отсутствие информации о доступе как подтверждённое наличие удобств.

Номер заказа должен быть уникален и при конкурентном создании. Не использовать
незащищённое `count + 1`; допустим PostgreSQL sequence. Непрерывная нумерация без пропусков не нужна.

В M3 новые заказы находятся в Inbox / To plan. Операционное состояние — read-only;
произвольного PATCH progress/status нет. Оплата не переводит заказ в COMPLETED.
Назначение конкретной команды и scheduledStart не добавлять в Order: это M4.

## 3. Товары

`OrderItem` принадлежит одному заказу и содержит описание, положительное целое
количество, конфигурацию, помещение/ambient, примечания и порядок отображения.
Требование сборки согласуется с типом услуги; правила зафиксировать явно.
Фото и их загрузка отложены до этапа файлов — не имитировать работающий upload.

Добавь создание/редактирование позиций; удаление из текущего состава сделай логическим,
с сохранением истории. Не создавай склад, каталог товаров или расчёт цены заказа из цен позиций.
Стоимость заказа пока задаёт диспетчер вручную.

Обновление заказа вместе с позициями выполняется атомарно. Некорректная позиция не должна
оставить частично сохранённую форму. Item ID из другого заказа не должен позволять изменить
чужую позицию. ID/авторы/даты/производные финансовые поля нельзя подменить через payload.

Для устаревшего `expectedVersion` вернуть 409 и предложить перечитать данные.
Проверка версии должна быть атомарной, а не только SELECT перед независимым UPDATE.
Документируй, какие операции увеличивают версию заказа; idempotent replay не создаёт новую редакцию.

## 4. Деньги и журнал оплат

Следуй `docs/DOMAIN_RULES.md`, разделу «Оплата»:

```text
orderTotalCents >= 0
paidCents = SUM(amountCents для Payment со status RECORDED)
balanceCents = orderTotalCents - paidCents
```

Все суммы — безопасные целые центы EUR. Выбери и документируй верхнюю границу,
совместимую с выбранным типом PostgreSQL и безопасным диапазоном JavaScript.
Проверять диапазон в DTO/runtime validation и применимых DB constraints.
Явно обрабатывай тип результата SQL SUM/TypeORM, не допускай потери точности при преобразовании.

Статус вычисляет сервер:
- `NOT_REQUIRED`: total = 0;
- `UNPAID`: total > 0 и paid = 0;
- `PARTIALLY_PAID`: 0 < paid < total;
- `PAID`: paid = total.

Не принимать `paidCents`, `balanceCents` или `paymentStatus` из формы как изменяемые поля.
Не допускать отрицательных сумм, дробных центов, переплаты или уменьшения total ниже paid.
При total = 0 положительный платёж невозможен.

Frontend показывает евро. Преобразовывай десятичную строку в целые центы без промежуточного
умножения дробного Number на 100. Для MVP можно принимать точку или запятую как один
десятичный разделитель без разделителей тысяч; максимум два дробных знака.
Например, `650,50` -> 65050; неоднозначный формат и `1.005` отклоняются, не округляются молча.
Backend получает integer cents. Проверку frontend нельзя считать заменой серверной.

Payment:
- UUID, orderId, положительный amountCents;
- календарная дата оплаты `paidOn` (YYYY-MM-DD, PostgreSQL date), отдельно от createdAt;
- метод `CASH`, `BANK_TRANSFER`, `CARD`, `OTHER`, optional note;
- `RECORDED` / `VOIDED`;
- createdBy/createdAt из сервера;
- idempotencyKey и fingerprint нормализованного исходного запроса;
- voidedBy/voidedAt/voidReason для аннулирования ошибочной записи.

`CARD` — только ручная отметка способа уже полученной оплаты. Не подключать эквайринг,
не принимать номера карт, CVV, банковские секреты. Возвраты денег, налоги, инвойсы и мультивалютность вне M3.
Дата оплаты — календарная дата, не смешивать её с UTC timestamps создания/аннулирования.

Исходные сумма/дата/метод платежа не редактируются. Исправление: VOID с обязательной причиной,
затем новая корректная запись. Физического DELETE платежа нет. VOID отменяет учётную запись,
а не означает возврат денег клиенту. UI должен объяснять это различие.

## 5. Идемпотентность и конкурентность

Сначала авторизация, затем DB-backed атомарная операция.
Создание Payment, VOID Payment и изменение стоимости Order используют одну стратегию:
блокировка родительской строки Order в транзакции, чтение актуального журнала,
проверка инвариантов, сохранение данных и ActivityLog до commit.
Все пути записи обязаны придерживаться этой стратегии.

Используй только manager/repositories текущей транзакции для входящих в неё операций.
Блокировка через in-memory Map/mutex или отключение кнопки недостаточны.
Не создавать отдельный DataSource. Документируй isolation level и порядок блокировок.

Для создания платежа:
- scope ключа: конкретный orderId; unique constraint `(orderId, idempotencyKey)` в БД;
- тот же ключ и тот же нормализованный payload возвращают существующий Payment без новой записи/истории;
- тот же ключ с другим payload возвращает 409;
- проверка существующей операции производится до повторной проверки доступного остатка;
- replay после VOID возвращает существующую VOIDED-запись, не создаёт оплату заново;
- успешный replay возвращает актуальную запись, не обещает прежнее состояние итогов заказа;
- пользователь должен иметь актуальные права и на повтор операции.

Frontend создаёт один ключ на одну попытку внесения платежа и сохраняет его для повтора
того же запроса после сетевой ошибки. Не генерировать новый ключ на каждый Retry.
При создании намеренно нового платежа — новый ключ. Не сохранять чувствительные данные
форм в browser storage. После перезагрузки с неопределённым результатом сначала перечитать журнал.

Пример обязательного теста: total=100000, paid=0, два параллельных платежа по 60000
с разными ключами. Успешен только один; второй получает business conflict, итог paid=60000.
Отдельно проверить платеж одновременно с уменьшением total и повторное VOID.
Повторное VOID не меняет баланс повторно и не дублирует ActivityLog.

## 6. ActivityLog и доступ

ActivityLog записывается в той же транзакции, что успешное бизнес-действие:
создание/редактирование заказа, изменения товаров, запись/аннулирование платежа.
Храни автора, действие, целевую запись, время, причину при необходимости и минимально
достаточное описание изменения. Не писать весь request body автоматически.
Не логировать пароли, токены, cookie, credentials; не дублировать PII в технических логах.

Отклонённое действие не оставляет запись об успешно выполненном изменении.
Повтор идемпотентного запроса не дублирует историю. Не делать event sourcing.
Не предоставлять публичные mutation endpoints для редактирования/удаления истории.

ADMIN и DISPATCHER управляют заказами/товарами/ручными платежами.
CREW_MEMBER в M3 не получает доступ к новым backoffice endpoints, финансовым итогам,
платежам, внутренним заметкам, истории или dashboard. Его текущий M2 интерфейс сохраняется.
Доступ к назначенным работам появится в M4/M5; сейчас не выдавай все заказы «временно».

Применяй текущие глобальные auth, CSRF/Origin и runtime validation.
Явные request/response DTO; не возвращать TypeORM entities целиком.
Вложенные маршруты проверяют принадлежность item/payment указанному Order.
Server-side authorization обязательна и для read endpoints/SSR, а не только mutation.

## 7. Backoffice UI

Используй текущие layout, navigation, компоненты и стили без визуальной переписи M2.
Добавь:
- `/backoffice/orders`: список, поиск по номеру/клиенту/городу, фильтры услуги и оплаты,
  server-side pagination, документированная сортировка с устойчивым tie-breaker;
- создание заказа и редактирование обычными формами;
- `/backoffice/orders/[id]`: данные клиента, доступ, товары, стоимость, журнал оплат, история;
- на backoffice dashboard: реальные количества заказов Inbox и финансовые итоги
  без вымышленных визитов, просрочек или завершённых доставок.

Суммы заказов/оплат не называть бухгалтерской выручкой. Счётчики и агрегаты считать сервером
по всему явно указанному набору, а не по строкам текущей страницы.
Избегать умножения сумм при JOIN товаров и платежей; проверить заказ с несколькими позициями
и несколькими платежами. Разграничить статистику всего dashboard и фильтрованного списка.

После mutation перечитать/обновить актуальные detail/list/dashboard данные.
Без WebSockets. Добавь loading/empty/error/retry, ошибки у полей, понятный 409,
состояние отправки формы и подтверждение VOID с причиной.
Проверить 390 px и 1280 px, включая длинные имена/адреса и таблицу платежей.

## 8. Seed

Добавь небольшой набор (например, 8–12) вымышленных заказов с товарами:
разные услуги, UNPAID/PARTIALLY_PAID/PAID/NOT_REQUIRED и пример VOIDED-платежа.
Все заказы пока Inbox, без фиктивных завершений и назначений.
Используй устойчивые идентификаторы seed, повторяемые ключи платежей и транзакции.

Повторный/конкурентный seed не создаёт дубликаты, не меняет пользовательские поля,
не восстанавливает VOIDED-платежи и логически убранные позиции, не добавляет повторную историю.
Не «восстанавливай» обязательные demo суммы поверх ручных правок.
Существующие пользователи, пароли, роли, disabled-состояния, команды и членство сохраняются.
Seed запрещён в production, запускается отдельно от boot и migrations.

## 9. Проверки

Unit: parsing cents, limits, derived payment states, request validation, frontend states.
Integration на существующей отдельной Compose test БД, не на development:

1. Создание, чтение и изменение заказа с товарами; чтение новым соединением.
2. Неизвестные/защищённые поля, отрицательные/дробные/слишком большие cents, неверные quantities.
3. Атомарность формы: invalid item не оставляет частично сохранённого Order.
4. ADMIN/DISPATCHER разрешены; anonymous/CREW_MEMBER запрещены; payload/API/SSR не раскрывают финансы crew.
5. Payment item/order ownership, CSRF, актуальность role/disabled account из M2.
6. Два последовательных и два конкурентных одинаковых запроса оплаты: одна запись и один audit event.
7. Один idempotencyKey с другим payload: 409.
8. Конкурентные разные платежи, ведущие к переплате: только допустимый результат.
9. Конкурентная оплата и изменение стоимости: инвариант paid <= total всегда сохранён.
10. VOID с причиной, запрет пустой причины, повтор VOID, replay исходного Payment после VOID.
11. Остаток и все четыре paymentStatus, включая total=0.
12. Устаревшая версия формы: 409 без перезаписи более нового состояния.
13. Пагинация/поиск/фильтры и корректные агрегаты с несколькими items/payments.
14. Двойной/конкурентный seed и сохранность ручных изменений M1/M2/M3.
15. Rollback бизнес-операции при невозможности записать её ActivityLog.

Конкурентные тесты должны действительно перекрывать транзакции отдельных соединений
и подтверждать конфликт/ожидание, а не вызывать запросы последовательно под видом concurrency.
По возможности используй управляемую синхронизацию вместо хрупких фиксированных sleeps.

Выполни lint, format:check, typecheck, test, test:integration, build,
применение новой миграции и повторный запуск миграций. Проверь реальный Next proxy.
Сохрани регрессии M1/M2 и не меняй их ожидания, чтобы скрыть сломанное поведение.

Browser smoke: dispatcher создаёт заказ, добавляет позиции, записывает оплату,
видит остаток после reload, аннулирует ошибочную запись, видит историю.
CREW_MEMBER не получает backoffice через прямой URL или API.
Для сценария не выводить credentials в отчёт. Используй разрешённые браузерные инструменты;
недоступность фиксировать BLOCKED, не обходить ограничения среды.
