## 1. Цель и границы

Получить настоящий сценарий:
диспетчер планирует и подтверждает визит → сотрудник назначенной команды видит его
на телефоне → отмечает выезд, прибытие и начало работы → выполняет свои задачи,
фиксирует доставленные/собранные количества, заметки, фото и проблемы → завершает
именно участие своей команды с результатом и, при необходимости, запросом повторного
приезда → диспетчер видит сохранённый результат и оставшуюся работу.

Включить Today / Upcoming / Open / Completed, детали своего назначения, checklist,
накопленные количества товаров, фактические timestamps, заметки, фото, документы
диспетчера, issues, частичный/неуспешный результат, потребность повторного приезда.

НЕ включать автоматический поиск свободных слотов, маршрутный оптимизатор,
estimatedFinishAt и полноценную панель прогнозирования задержек (M6), подписи и
финальное закрытие Order (M7), realtime / offline queue / PWA / GPS (M8 или вне MVP),
уведомления клиентам, новые платёжные функции, новый auth, Redis и микросервисы.
Не устанавливать обязательное число тестов: проверять поведение, а не счётчик.

Сначала серверная модель, миграции, правила и конкурентные проверки; затем файлы и
issues; затем интерфейс и сквозные проверки. Это части одного M5, не новые этапы проекта.
Не заменять реализацию всей системы псевдоданными или изменением статусов только в UI.

## 2. Сохранность M1–M4

До изменений проверить Git status/diff, существующие миграции, entities, parsers,
транзакции, права и компоненты. Не сбрасывать tracked/untracked изменения, не делать
автоматический stash, clean, reset, checkout или commit. Проверить, что секреты,
uploads и тестовые артефакты исключены из Git. Не читать старый приватный demo-password.

Сохранить Next.js / NestJS / TypeORM / PostgreSQL, pnpm monorepo, один DataSource factory,
`synchronize: false`, session/Origin/CSRF, строгие contracts и текущие версии.
Новые миграции добавляются после M4; применённые файлы не переписываются.
Недеструктивно расширить старые строки defaults: NOT_STARTED, PENDING и нулевые
количества НЕ означают, что работа была выполнена. Не менять прежние business-поля,
платежи, confirmation, сроки, снимки задач и авторов.

Не перезаписывать .env. Для нового storage-config достаточно безопасного default и
.env.example с placeholders/описанием. При необходимости разрешены только действительно
нужные upload/image dependencies с проверкой совместимости, точными версиями и
обновлением единственного lockfile. Не обновлять остальные пакеты ради нового модуля.

## 3. Единица работы и доступ

### 3.1. CrewAssignment, а не Order

Основная карточка сотрудника — CrewAssignment. Она ссылается на существующие
Appointment и Order. Одна команда имеет общий checklist и общий результат назначения;
четыре её сотрудника не создают четыре копии задач/прогресса. Автор каждого действия
сохраняется индивидуально. Любой текущий активный участник команды может выполнять её
назначение; отдельную роль бригадира сейчас не вводить.

Несколько команд одного визита действуют независимо. Команда A не меняет checklist,
статус или итог команды B и не завершает весь визит своим действием.

### 3.2. Отдельный crew API

Не открывать CREW_MEMBER доступ к существующим backoffice GET/PATCH orders, payments,
dashboard, planning и task templates. Сделать отдельные crew DTO и проекции: никаких
`...orderEntity` с последующим удалением нескольких секретных полей.

Crew получает: номер заказа, плановое окно Europe/Rome и confirmation, своё назначение,
клиента, контактное лицо, необходимые телефоны/email, адрес/условия доступа, услугу,
workDescription, crewNotes, описание/конфигурацию/ambient/notes товаров, количества,
свои task snapshots, разрешённые документы/фото, execution notes и issues заказа.

НЕ получает суммы, paid/balance/paymentStatus, payment records, internalNotes,
сырой ActivityLog, sessions/users secrets, storage paths, idempotency fingerprints.
Существующие Appointment.notes считать внутренними до явного решения об их видимости;
не превращать их молча в инструкции crew. Для инструкций использовать уже выделенные
crewNotes. Финансовые поля не должны присутствовать ни в JSON, ни SSR HTML, ни ошибке,
ни ответе mutation/replay. Бизнес-контакты и shared evidence заказа доступны только
в рамках разрешённого назначения, а не через глобальный поиск всех клиентов.

На каждом запросе проверять текущие session, user.active/role, активное членство,
принадлежность Assignment текущей команде и все вложенные связи. Чужой или снятый
Assignment/Item/Issue/Attachment не раскрывать через предсказуемый ID: безопасный 404;
запрещённая роль/операция — 403, отсутствие сессии — 401. Это относится также к download,
thumbnail и повторному запросу уже выполненной операции.

Решение M5: текущие участники могут читать завершённые назначения своей команды;
бывший участник теряет этот доступ после смены членства. Новый участник получает
доступ к истории своей новой команды, не к персональной истории старой.
Отключённая Crew остаётся читаемой текущим участником, как в M2. Новый выезд disabled
Crew запрещён; активным пользователям разрешено закончить и документировать уже начатую
работу. Disabled user не получает такого исключения. Отменённое до начала назначение
не даёт доступа к клиентским данным, даже если известен старый URL.

Файлы/заметки/issues с CREW_VISIBLE можно читать через доступный Assignment того же
Order, включая материалы предыдущего визита. BACKOFFICE_ONLY недоступны crew даже
если он назначен на этот Order. Назначение на один заказ не открывает другой.

## 4. Исполнение: состояния, действия и время

Сохранить lifecycle M4 `CrewAssignment.status = ASSIGNED | CANCELLED` и добавить
отдельный executionStatus; не смешивать отмену брони с фактом выполнения.

| executionStatus | Смысл |
| --- | --- |
| NOT_STARTED | Команда ещё не начала этот выезд |
| ON_THE_WAY | Команда выехала |
| ARRIVED | Прибыла на адрес |
| IN_PROGRESS | Начала работу у клиента |
| COMPLETED | Закончила свою часть этого визита |
| PARTIALLY_COMPLETED | Попытка закончена, часть работы осталась |
| BLOCKED | Попытка закончена без возможности продолжить |

Lifecycle CANCELLED допустим только при executionStatus=NOT_STARTED: зафиксировать
это ограничение и не позволять старому M4 path отменить начатую/закончённую работу.

Обычный путь: NOT_STARTED → ON_THE_WAY → ARRIVED → IN_PROGRESS → COMPLETED.
Из IN_PROGRESS разрешён PARTIALLY_COMPLETED. Решение M5: из ON_THE_WAY, ARRIVED
или IN_PROGRESS разрешён BLOCKED с причиной, чтобы поломка по дороге или отсутствие
доступа не требовали фиктивного начала сборки. BLOCKED здесь терминальный неуспешный
результат, а не пауза; команда после него не считается занятой текущим выездом.

Никаких произвольных PATCH executionStatus. Явные actions проверяют переход и права.
Обратные переходы, «сбросить выезд», переоткрытие законченного назначения и редактирование
его результата не входят в M5. Дополнение — новая заметка/фото/issue с собственным
автором и временем; прежний отчёт не меняется. M6 создаст следующий Appointment.

depart/arrive/start/finish получают timestamp сервера после получения нужных locks;
не принимать actual timestamps/actor из payload. Хранить departedAt, arrivedAt,
actualStartAt, actualEndAt отдельно от plannedStartAt/plannedEndAt. У BLOCKED по дороге
arrivedAt/actualStartAt остаются null. Ровно один timestamp на первое успешное действие,
повтор его не переписывает; хронология валидируется. Фактическое завершение на следующий
день разрешено, даже если плановый визит M4 ограничен одной Rome-датой.

Решение M5 для нового выезда: только актуальное ASSIGNED назначение, Appointment не
CANCELLED, клиентское время CONFIRMED, Crew active и плановая Rome-дата сегодня.
Ранний выезд внутри дня допустим. Визит на другой день сначала перепланирует диспетчер;
продолжение уже начатого визита не ограничивать датой или рабочим окном.
При запросе depart проверять показанную Appointment.version, чтобы нельзя было начать
по экрану, устаревшему после переноса/правки условий. Отдельно проверить актуальные права.

Не отклонять фактически выполненные действия из-за неоплаты, открытого issue,
выхода за рабочий день или пересечения с последующим плановым визитом.
Для already-started назначения они не должны блокировать сохранение actualEnd.
Запись факта не переписывает план и не исправляет календарь задним числом.

Одна Crew не может одновременно иметь два назначения в ON_THE_WAY/ARRIVED/IN_PROGRESS,
даже если их плановые интервалы не пересекались. Защитить БД и транзакцией; применим
partial unique index по crew_id на активные executionStatus и соответствующие тесты.
После BLOCKED/PARTIALLY_COMPLETED/COMPLETED команда больше не находится в active execution.

Минимальный индикатор: активный выезд после plannedEnd — «возможно задержка / нет
завершения», а не доказанное время окончания. Следующий заказ сам не переносится.
Пока старое назначение активно, второе depart той же Crew получает явный конфликт.
Плановая бронь M4 не становится обещанием фактической доступности; показать активную
работу в backoffice. Полноценные расчёты риска/ETA/слотов остаются в M6.

## 5. Checklist и работа нескольких сотрудников

Существующий Task snapshot — источник задания. Не регенерировать его при старте,
переносе, загрузке экрана или изменении шаблона. Добавить исполнение PENDING/DONE/SKIPPED,
version, doneBy/doneAt и причину там, где нужна. Логически снятые в M4 задачи не выполнять.

Только своя активная IN_PROGRESS assignment может менять её задачи. Команда видит
required, severity и priority; порядок — priority и стабильный ID. Severity не является
порядком и не меняется сотрудником. Сотрудник не меняет name/description/required.

Required допускает только PENDING/DONE. Optional можно SKIPPED с причиной. До finish
разрешено вернуть DONE/SKIPPED в PENDING с причиной, сохраняя прежнее действие в истории.
Нельзя отметить «не выполнено» в ответ на stale toggle без проверки version.

COMPLETED требует все активные required DONE, а optional — DONE либо SKIPPED с причиной.
PARTIALLY_COMPLETED/BLOCKED не требуют фиктивных DONE: остающиеся PENDING сохраняются
в отчёте вместе с причиной и remainingWork. «Проверить целостность» может быть DONE
при найденном повреждении: это выполненная проверка, а повреждение — отдельный Issue.

Два сотрудника одной команды не теряют изменения друг друга: version и проверка под
блокировкой. Повтор той же команды не создаёт вторую историю и не меняет автора.
Finish против последнего task update проверяет согласованное состояние под общим lock.

## 6. Доставка и сборка товаров

На существующем OrderItem добавить accumulated deliveredQuantity, assembledQuantity
и отдельную fulfillmentVersion. Начальное значение 0. Не создавать складскую систему.

Инварианты для активного товара:
`0 <= assembledQuantity <= deliveredQuantity <= quantity`, все значения целые.
Для requiresAssembly=false assembledQuantity остаётся 0; это не означает незавершённую
работу. Сборка требуется только товарам requiresAssembly=true.
DELIVERY_ONLY не допускает assembledQuantity > 0.

Crew в IN_PROGRESS передаёт абсолютный новый результат с expectedFulfillmentVersion,
а не «прибавить один». Общий результат позиции относится к заказу, не суммируется
повторно по командам/визитам. UI явно пишет «всего по заказу», показывает предыдущие
значения, остаток и сохраняет черновик при 409. Запретить неявное обнуление второго поля
при изменении первого. Запрос и транзакция не заменяют quantity из заказа.

Корректировка вниз до завершения назначения требует причины; диапазоны сохраняются.
Все изменения идут под Order lock, с записью автора, Assignment и before/after в историю.
Не позволять сотруднику после finish редактировать старый факт. Поздняя корректировка
через отдельный диспетчерский workflow не входит в M5; не добавлять скрытый обход БД.

Полное выполнение checklist/кнопка finish НЕ выставляют автоматически delivered и
assembled равными quantity. Количество «доставлено» не доказывает сборку.

Команда может закончить свою часть, когда другая ещё работает; COMPLETED assignment
не требует полного объёма всех товаров всего заказа. Полный объём проверяется при
агрегации Order, независимо от результата отдельной команды.

## 7. Совместимость с редактированием M3/M4

Все запреты ниже реализовать в существующих backend mutation paths, не только в UI.
Проверять их в одной транзакции с изменением. Закрыть гонки start vs reschedule/cancel.

После первого depart любого назначения Appointment запрещены обычный перенос времени,
полная отмена визита, смена состава команд и переписывание снимков задач этого визита.
Решение M5: динамическое изменение состава уже выехавшего визита пока не поддерживается;
добавочную работу оформляют другим Appointment. Notes можно дополнить отдельно.
До depart M4 сохраняет прежнее поведение, включая перенос ID и cancellation history.
Обычная отмена не превращает начатую работу в «никогда не было».

После первого depart по Order заморозить его материальные условия: адрес/услугу/объём
работ, доступ и структуру/описание/quantity/configuration/ambient/requiresAssembly товаров.
Это явное ограничение M5 вместо скрытой перезаписи фактической истории. Изменения контактов,
crew/internal notes, item notes и оплат остаются возможны с прежними проверками и audit.
Точное множество защищённых полей записать в DECISIONS и покрыть тестами. При отказе
сохранять draft и объяснять ограничение, не предлагать физически удалить историю.

Решение M5: после начала не сбрасывать confirmation начатого визита обычной правкой
контактов/заметок. Будущие неначатые визиты по-прежнему используют правила M4. Новая
потребность и новый визит не должны переносить уже состоявшийся приезд на завтра.

Отключение Crew/правка availability сохраняются по правилам M4: без удаления брони
или фактов. Дополнение actualEnd не обязано вписываться в плановую доступность.
Цена и платежи не изменяют executionVersion и не делают форму checklist устаревшей.
Результаты исполнения не меняют paid/balance и не создают Payment.

## 8. Заметки, проблемы и повторный приезд

### 8.1. Заметки

Append-only execution note: Order, Appointment/Assignment provenance, optional Item,
text, author, UTC createdAt. Видны разрешённым участникам этого заказа и диспетчеру.
Не использовать internalNotes для crew-текста. Исторические значения не заменять;
ошибочную заметку уточняют новой. Текст непустой, до 4000 символов. Без HTML исполнения.
Создание идемпотентно; безопасное отображение длинного текста и переводов строк.

### 8.2. Issue

Order issue с provenance Appointment/Assignment, type, description, reportedSource
CREW/CUSTOMER, optional item IDs, notes, фото, author, timestamps, version.
Список MVP: DAMAGE, MISSING_PARTS, WRONG_PRODUCT, QUANTITY_MISMATCH, ACCESS_PROBLEM,
CUSTOMER_UNAVAILABLE, OTHER. Типы — документированное допущение, не новый редактор каталога.

Crew создаёт issue для своего доступного заказа с активной либо законченной попыткой;
нельзя отправить проблему для чужого заказа/товара/файла. Пустое описание недопустимо.
reportedSource=CUSTOMER означает «со слов клиента», а не авторизованный клиентский аккаунт.
Проблема может относиться к нескольким товарам того же заказа либо ко всему заказу.

OPEN/RESOLVED. ADMIN/DISPATCHER разрешает с обязательным resolution и своим timestamp;
reopen — отдельное действие с причиной. Crew не может скрыть/resolve проблему. Операции
с versions, audit, безопасным повтором. Решение проблемы не меняет фактические количества,
finish report, payment или return request. Finished assignment не закрывает Issue.

Добавить backoffice список/фильтр открытых issues и раздел в заказе/визите; crew — форму
и разрешённое чтение. Не отдавать crew сырой финансовый ActivityLog вместо issue timeline.

### 8.3. FinishReport и ReturnVisitRequest

Одно терминальное завершение Assignment создаёт неизменяемый FinishReport: outcome,
summary/reason, remainingWork, task-results snapshot, текущий снимок quantities с явной
пометкой «накопленно по заказу», author, actualEndAt, ссылки на известные issues/фото.
Не приписывать этому выезду накопленный результат предыдущих бригад. Платежей в снимке нет.

При PARTIALLY_COMPLETED/BLOCKED причина и описание оставшегося/невозможности работы
обязательны. Для COMPLETED — краткое резюме; незакрытый issue допустим и виден отдельно.
При returnVisitRequired=true обязательны reason и remainingWork; сохранить отдельную
потребность повторного визита с Order/Assignment provenance и статусом OPEN. Один finish
не создаёт несколько одинаковых запросов. Требование нельзя убрать простым повтором
finish с изменённым payload. Если нужно повторно приехать, выбор исхода не закрывает Order.

M5 фиксирует потребность и показывает её диспетчеру. Не создавать следующий Appointment,
не копировать старые выполненные задачи, не рассчитывать слот и не считать потребность
закрытой при resolve Issue. Связывание/обработка повторного приезда относится к M6.
Нельзя использовать один boolean Order, который вторая команда может очистить, потеряв
незакрытую потребность первой. `returnVisitRequired` вычисляется по открытым запросам.

После finish разрешены новые приложения-дополнения: заметки, фото, issues; исходный
FinishReport остаётся прежним. Не заявлять неизменность всей карточки заказа, только
зафиксированного отчёта и его результатов. Подписи не создавать и не имитировать.

## 9. Фотографии и документы

### 9.1. Назначение и visibility

Диспетчер загружает JPEG/PNG/WebP или PDF в Order, при необходимости связывает с Item.
Для документов visibility явно BACKOFFICE_ONLY / CREW_VISIBLE, default BACKOFFICE_ONLY.
Предупредить в UI, что crew-visible документ должен содержать только рабочую информацию.
Не обещать автоматическое обнаружение финансовых данных внутри пользовательского файла.

Crew загружает только изображения как доказательства работы своего Assignment:
DELIVERY, ASSEMBLY, DAMAGE, MISSING_PARTS, OTHER; type выбирается обязательно.
Можно привязать к Order, Item или Issue в том же Order, с provenance Assignment.
Новые execution notes/issues/photos от crew разрешены после depart (в том числе после
терминального finish), не для ещё не начатого или отменённого назначения.
Crew evidence — CREW_VISIBLE. Для Issue/return report использовать те же Attachment,
не сохранять независимые base64-копии в JSON. Нельзя прикрепить BACKOFFICE_ONLY файл
к публичному для crew response так, чтобы возник обход visibility.

Backoffice может логически отозвать файл с причиной. Метаданные/audit и ссылка в отчёте
сохраняются как withdrawn; удалённый/отозванный контент crew больше не читает. Crew не
удаляет уже отправленные доказательства. Не делать незаметную замену содержимого по ID.

### 9.2. Storage и валидация

Локальный storage adapter для demo, вне Next public и всех статических web-каталогов.
Непредсказуемое серверное имя, controlled extension, приватный storage key; исходное имя
только как ограниченный display name. Не принимать URL для скачивания сервером,
абсолютный путь, ../, произвольный storage key или symlink от клиента.
Хранилище не внутри build output: файлы переживают restart/build. Test storage отдельно.

Лимиты как настраиваемые консервативные defaults: изображение до 10 MiB, PDF до 20 MiB,
одно вложение на HTTP upload; UI загружает несколько по очереди. Не более 100 READY/active
файлов и 250 MiB на Order; quota проверяется под Order lock, включая pending reservations,
если они есть. Ограничить параллельную декодировку изображений и размеры multipart-полей.
Это решения M5, объяснить их в README.

Сервер проверяет разрешённый формат по содержимому, размер до полного чтения в память
и декодируемость изображения, ограничивает число pixels (например 40 MP), rejects
повреждённые/неподдерживаемые файлы. SVG/HTML/JS/архивы/исполняемые файлы не принимать.
Картинки перекодировать безопасной библиотекой, нормализовать ориентацию и убрать EXIF/GPS.
Не доверять browser MIME или расширению. HEIC не обещать: при неподдержке дать понятную
ошибку и предложить JPEG/PNG/WebP; реальную камеру не считать проверенной эмуляцией.

PDF — только загрузка диспетчером, проверка формата, ограниченный download как attachment;
не встраивать в origin приложения активный PDF preview. Проверка сигнатуры PDF не равна
антивирусной проверке. В README явно отметить отсутствие AV/CDR и ограничение локального
тестового проекта; не называть такую загрузку полностью безопасной для публичного production.

Multipart сохраняет существующие Origin/CSRF/session проверки, не становится исключением.
Авторизацию/базовые ограничения проводить до приёма большого тела, а актуальное право и
принадлежность повторно проверять перед публикацией готового файла.

### 9.3. Доступ и согласованность

Метаданные и bytes выдавать только через авторизованный handler. Проверять доступ к
заказу/назначению, visibility и withdrawal при каждом download/preview, включая HEAD/Range,
если эти методы поддерживаются. Не публиковать uploads через static middleware, Next
image optimizer или долгоживущий публичный URL. Для protected images подходит обычный
same-origin img с session-cookie; кэш должен быть private/no-store. После logout новый
запрос по прежнему URL не возвращает контент. Уже полученные bytes отозвать невозможно.

Правильные Content-Type, nosniff и безопасный Content-Disposition; без управляющих
символов из исходного имени. В ответах не показывать физические пути/SQL/stack traces.

Файловая система и PostgreSQL не являются одной транзакцией. Спроектировать минимальную
схему staging → validated storage → READY metadata либо PENDING/READY/FAILED с явным
recovery. Тяжёлую обработку/передачу файла не держать внутри длительного Order lock.
Успех только когда содержимое и запись действительно доступны; public queries не отдают
незавершённый файл. Обычная ошибка БД/storage/audit очищает только собственные временные
данные и не оставляет ложный READY. При неизвестном исходе COMMIT не удалять финальный
файл, не проверив состояние БД: можно уничтожить уже сохранённое вложение.

Upload получает idempotency key; fingerprint включает неизменяемые metadata и хеш
исходных bytes. Одинаковый повтор возвращает тот же Attachment, другой payload — 409.
Два конкурентных одинаковых uploads не создают две записи/копии. При смене версии
image processor прежний запрос не должен неожиданно стать другим из-за нового re-encode.
После lost response UI сохраняет исходный File/key до проверенного результата; после
reload сначала перечитывает галерею. Не хранить файлы/формы/tokens в browser storage.

Падение процесса между файловой операцией и commit может оставить orphan; документировать
состояния и безопасную ручную диагностику/очистку с dry-run, не добавлять сложную очередь.
Не запускать автоочистку development storage и не удалять файлы, которые могут быть in-flight.
В тестах: storage error, DB/audit failure, retry, concurrent retry, ошибка/неизвестный исход
финализации. Существующие READY uploads и документы от ошибочного cleanup не страдают.

## 10. Транзакции, versions и повтор действий

Сохранить относительный порядок планирования M4: Order → Appointment → Crew в стабильном
порядке → Assignment/Task/Item. Все пути исполнения, отмены, переноса и finish обязаны
согласовываться, а не иметь отдельные несовместимые стратегии.

При авторизации mutations учитывать M2 User → Crew и реальные FK locks при audit.
Не добавлять вслепую `FOR UPDATE User` после Crew/Order. При необходимости короткого
shared User lock до business locks обосновать lock mode и совместимость с FK/checks.
Внутри транзакции снова прочитать актуальную роль/членство перед действием. Зафиксировать
момент принятия решения о правах и тестировать смену membership/disable одновременно
с execution. Уже полученные браузером данные не считаются технически отзываемыми.

Серверные execution/task/fulfillment versions независимы от финансового Order.version.
Желательно собственная executionVersion назначения; события, влияющие на его финальный
отчёт (status/task changes), повышают её. Stale finish не принимает автоматически новую
version из refetch. Изменение quantities проверяется по fulfillmentVersion текущей позиции.
При любом общем формате version предусмотреть, чтобы платёж не ломал checklist-форму.

Каждая мутация с повторяемой отправкой (action, task, quantity, note, issue, finish,
upload) должна иметь безопасный retry: сохранённый operation key+fingerprint либо
доказуемую идемпотентность конкретной операции. Для обратимого checklist/quantities
недостаточно «текущее значение уже такое»: старый retry после нового изменения не
должен откатить новое состояние. Нужна сохраняемая receipt уникального command.
Это может быть узкая таблица execution receipts в том же модуле; не строить event bus.

Проверка receipt после актуальной авторизации/ownership, но до stale-version и transition
validation. Тот же key+payload возвращает текущий разрешённый response с результатом
прежнего действия без новой версии/истории; изменённый payload с ключом — 409.
Ключ scoped как минимум actor/assignment/action, точную схему записать. Никогда не
возвращать прежний финансовый/crew response пользователю после потери доступа.

Все business changes и audit/receipt коммитятся атомарно. Ошибка audit отменяет действие.
READ COMMITTED с recheck после locks для записи; согласованные read-проекции для агрегации.
В SQL constraints закрепить инварианты enum/FK/unique/quantities/timestamps, где применимо.
Тесты гонок используют реальные соединения и наблюдаемый барьер, не случайный sleep.

## 11. Прогресс Appointment/Order и backoffice

Не превращать planning status в ручной execution status. Сохранить отдельные confirmation,
Needs attention, paymentStatus, openIssueCount и returnVisitRequired. У старых неначатых
заказов работают M4 INBOX/PLANNED/ASSIGNED; прошедшее время само по себе их не завершает.

Расширить представление Order.progress для исполнения, с единым серверным resolver,
используемым detail/list/dashboard и фильтрами. Предлагаемые дополнительные значения:
IN_PROGRESS, PARTIALLY_COMPLETED, REQUIRES_ATTENTION, AWAITING_REVIEW.

Правила приоритета M5:
1. Есть active execution любого назначения → IN_PROGRESS; дополнительные issues/return
   badges сохраняются, точный ON_THE_WAY/ARRIVED/IN_PROGRESS показан по командам.
2. Нет active execution и выполнены все условия workReadyForReview → AWAITING_REVIEW.
3. Весь объём работ/назначений завершён, но готовность блокируют только открытый issue
   или return request → REQUIRES_ATTENTION, не «частично доставлено».
4. Объём ещё неполон (количества/задачи/назначения) и есть PARTIALLY_COMPLETED outcome,
   выполненная задача, успешное завершённое участие либо ненулевой физический результат →
   PARTIALLY_COMPLETED. Открытые issues/return видны отдельно.
5. Есть завершённая неуспешная попытка/проблема без выполненной работы → REQUIRES_ATTENTION.
   BLOCKED с нулевыми количествами не называется «доставлено».
6. Работы/проблем ещё не было → прежний расчёт INBOX/PLANNED/ASSIGNED.
Ни один terminal outcome не должен провалиться обратно в INBOX только из-за фильтра
«ещё выполняющиеся назначения». Все сочетания явно покрыть table-driven tests.

workReadyForReview для M5 означает: есть выполненная работа; каждый неотменённый визит
имеет назначения; все действующие назначения завершены COMPLETED; их required tasks DONE,
optional DONE/SKIPPED; весь активный объём доставлен и нужная сборка выполнена; openIssueCount=0,
нет открытого ReturnVisitRequest. Будущий неначатый/Unassigned визит блокирует готовность.
Историческая незакрытая partial/blocked попытка не становится автоматически покрытой новым
визитом: связать и разрешить remaining scope будет M6. Не скрывать это ограничение M5.

AWAITING_REVIEW — предлагаемое промежуточное имя: работа выглядит выполненной, финальное
подтверждение ещё не оформлено. Order.COMPLETED не присваивается в M5 вообще: подписи и
проверка финального закрытия относятся к M7. Unpaid не препятствует готовности физической работы.

Appointment выводит агрегированный execution summary и статусы каждой команды. Одна
COMPLETED при второй NOT_STARTED/IN_PROGRESS не завершает общий визит. Нельзя убрать
завершённые назначения из расчёта, отфильтровав только ASSIGNED execution enum ошибочно.

Диспетчер видит actual times рядом с планом, completed/required counts, quantities,
заметки, галерею, issues и return requests. Обновить календарь, order detail, список,
фильтры и dashboard: не только crew UI. Фильтр Issues независим от progress; counts/sums
не размножаются JOIN по tasks/photos/issues. Финансовые суммы M3 остаются прежними.
Refresh/focus/refetch после commit, без ложного обещания realtime между устройствами.

## 12. Экран сотрудника и API

Рекомендуемые страницы: `/crew`, `/crew/assignments`, `/crew/assignments/[id]`.
Сохранить доступ к карточке своей команды M2. Не требовать отдельного мобильного приложения.

Today — назначения плановой Rome-даты сегодня, включая выполненные сегодня по плану.
Upcoming — будущие неначатые/незавершённые назначения. Open — незавершённые, в том числе
прошлые, плюс partial/blocked с видимой потребностью разбора (без кнопки «продолжить старый
визит»). Completed — успешные COMPLETED assignments. Подписать, что это работа команды,
не окончательно закрытые заказы. Views могут пересекаться; не использовать first page Orders.

В списке: дата/время, номер, клиент, город, услуга, свой execution status и confirmation.
Серверная пагинация со стабильным порядком и реальным total, bounds как в M3. На сервере
день Europe/Rome; устройство Asia/Tokyo не меняет Today/Upcoming. Дать manual Refresh.

В details: контакт/телефон, адрес и условия доступа, товары с delivered/assembled/remaining,
checklist, документы, галерея, заметки, issues, finish. Только допустимые действия с понятным
следующим шагом. Системный file chooser и необязательный camera capture hint; без обязательного
getUserMedia. Должен работать обычный выбор файла при отсутствии камеры.

Finish — отдельная форма: результат, summary/reason, remainingWork, повторный приезд с
причиной, текущие проблемы. Кнопка «Finish my team's visit», не «Complete order».
Один submit не выполняет незапрошенные платежи, подпись, перенос или resolve issues.

Состояния loading/empty/error/Retry/401/403/404/409, сохранение drafts при безопасном retry,
запрет двойного submit, защита от позднего ответа старого Assignment. Появление платежа
или новая загрузка фоновых данных не затирают открытый checklist/finish draft.
Offline не заявлять: неполученное подтверждение сохранения показывается как неизвестный
результат, не как зелёный успех. После возврата сети перечитать persisted состояние.

Пример route layout (адаптировать к фактическим conventions, без ослабления ролей):
- GET `/crew/assignments`, GET `/crew/assignments/:id`;
- POST `.../:id/actions/depart|arrive|start|finish`;
- POST `.../:id/tasks/:taskId/result`, `.../:id/items/:itemId/fulfillment`;
- POST `.../:id/notes`, `.../:id/issues`, `.../:id/attachments`;
- GET `.../:id/attachments/:attachmentId/content`;
- backoffice Order execution/issue/attachment reads и explicit issue resolve/reopen,
  attachment upload/withdraw. Crew никогда не использует backoffice mutation response.

Не принимать authorId/crewId/orderId/result timestamps как источник полномочий из body.
Каждый вложенный ID проверять по доступному Assignment и Order. В details завершённого
назначения distinguish frozen finish snapshot от живого accumulated Order state.

## 13. Обязательные проверки

### Сервер/БД

1. Один сотрудник видит только текущую команду; чужие ID в list/detail/task/item/issue/file
   не раскрывают данные; смена membership/role/disable сразу влияет на новый запрос.
2. Crew JSON/SSR/mutations/replay/errors/downloads не раскрывают финансовых/internal данных;
   существующие backoffice endpoints всё ещё запрещены crew.
3. Последовательность depart/arrive/start/finish, недопустимые переходы, cancelled/unconfirmed,
   disabled Crew vs disabled user, переход через местную полночь без фиктивных timestamps.
4. Два сотрудника одной команды одновременно depart/finish: один фактический эффект;
   два заказа одной Crew одновременно пытаются active execution: один конфликт.
5. Depart против переноса/отмены/изменения материальных полей: один согласованный результат,
   без выехавшей команды на уже отменённый/перенесённый адрес; stale plan version отвергнута.
6. Последний checklist update против finish; optional skip и required no-skip; чужие tasks;
   retry старого DONE после нового PENDING не перезаписывает новое состояние.
7. Две команды меняют общие количества: нет удвоения/потери данных; bounds и version;
   assembled>delivered, >quantity, negative/fractional, assembly у DELIVERY_ONLY запрещены.
8. «Доставлено всё, собрано не всё» не даёт workReadyForReview; finish одной команды при
   второй незавершённой не завершает Order/Appointment; future Unassigned блокирует готовность.
9. Late actualEnd сохраняется при конфликте с последующим планом; план/следующий заказ
   не сдвигаются; новая работа той же Crew до finish прежней блокируется.
10. BLOCKED без выполненной мебели не показывается как delivered; partial/return без причины
    не принимаются; два разных return requests не затирают друг друга.
11. Issue create/resolve/reopen, version/retry, multi-item ownership; resolve не сбрасывает
    quantities/return requirement и не закрывает Order.
12. Ключи и повторы, concurrent create, rollback audit и stale forms; для реальных гонок
    независимые DB connections, bounded waits и наблюдаемая очередь locks.
13. Auth/session/CSRF для multipart; после logout/потери назначения старый download URL
    не даёт bytes; private file нельзя прочитать через другой public parent или preview.
14. Поддельный MIME/расширение, unsupported/повреждённый/слишком большой файл, pixel limits,
    traversal, filename header injection, безопасный PDF download, quota race и duplicate upload.
15. Ошибка storage/metadata/audit и retry не оставляют ложный READY и не удаляют ранее
    сохранённые файлы; concurrency file retry; raw filesystem paths не попадают в ответы.
16. Согласованные detail/list/calendar/dashboard; суммы прежние при нескольких командах,
    товарах/платежах/фото/issues. Неначатые M4 orders сохраняют прежний planning progress.
17. Миграция на существующих M1–M4 данных и повтор; seed дважды не сбрасывает выполненное,
    quantities, issue resolution, файлы, return requests или history.
18. Текущие M1–M4 regression tests и production build реально повторно запущены.

### Браузер

Реальный Next proxy → Nest → отдельная test PostgreSQL schema и отдельный test storage.
Новые credentials только для fixture, без старого пароля и без секретов в отчёте.

Сценарий A: dispatcher создаёт заказ с доставкой+сборкой и визит с двумя Crew, подтверждает;
сотрудник A проходит состояния, записывает частичные количества, checklist и фото; его finish
не закрывает работу B. Сотрудник B видит только свои задачи, записывает оставшийся результат;
после reload количества общие и не дублируются, Order максимум AWAITING_REVIEW, без подписи.

Сценарий B: повреждение/недостающая деталь, фото товара, issue, частичный finish с return
reason/remainingWork; диспетчер видит результаты и запрос. Resolve issue не удаляет потребность
приезда. Попытка обычного переноса начатого визита получает объяснимый отказ; не потерян draft.

Сценарий C: private/crew-visible document, file chooser, неверный формат, oversized,
lost response и retry без дублей, остановка только test API и восстановление, 409 двух вкладок,
logout и старый file URL. Никаких destructive browser actions в development данных.

Проверить 390 и 1280 px, клавиатуру/labels, длинные контакты/заметки, loading/empty/error,
сохранение drafts. Проверить Today/Upcoming при timezone устройства Asia/Tokyo.
Эмуляция телефона/file upload не равна физической камере: её проверку указать отдельно.

## 14. Seed, документация и сдача

Обычный db:seed не должен создавать actual work, завершать старые назначения, добавлять
случайные даты/фото/issues и массово менять существующую базу. Новые test fixtures —
изолированы и воспроизводимы, время контролируется в tests, а не глобально в приложении.
Существующие исходники/таблицы сохранить; новые столбцы — только документированные defaults.
Test storage cleanup удаляет только уникальный каталог своего теста.

README обновить: crew path, actions/outcomes, shared quantities, file limits/visibility,
local storage backup, restart persistence, partial/blocked meaning, отсутствие offline,
AV/CDR, signatures/realtime и полное закрытие позже. Новый файл storage не означает
защиту от всех угроз production; текущие M2/M3 ограничения сохраняются.

DECISIONS: расширения модели, state table, доступ и privacy, lock order и versions,
finish snapshots, file commit/recovery, разрешённые зависимости, progress resolver,
точные границы M5/M6/M7 и запрет правки материальных условий после depart.
PROGRESS: только реально выполненные команды, результаты и оставшиеся ограничения.
Исторические PASS не выдавать за новые; пользовательскую приёмку не назначать автоматически.

Обязательные команды: lint, format:check, typecheck, test, test:integration, build,
миграция/повтор, seed/повтор, browser smoke и применимые регрессии. BLOCKED честно указать.
Не раскрывать секреты и не выполнять commit/push/deploy или M6. В конце написать, какие
процессы запущены, как открыть сценарий и что именно осталось непроверенным.

## 15. Справочные источники для реализации

Требования продукта — локальные документы проекта; рекомендации безопасности не заменяют
эти требования и не означают сертификации. Для конкретных API сверять установленную версию.

- PostgreSQL 17, explicit locking: `https://www.postgresql.org/docs/17/explicit-locking.html`
- OWASP, permissions on every request и static resources:
  `https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html`
- OWASP, file upload validation/storage/limits:
  `https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html`

Критерий завершения M5: оба интерфейса показывают одну сохранённую историю реальной работы,
но сотрудник не видит лишние данные; частичное выполнение не маскируется под полный заказ,
а повтор/конкуренция/ошибка загрузки не дублируют результаты и не уничтожают историю.
