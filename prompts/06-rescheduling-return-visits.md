## 1. Рабочий результат

Диспетчер видит затянувшуюся работу и затронутые будущие визиты; запрашивает подходящие
окна сегодня/в следующие дни либо выбирает другую команду; проверяет предложенный
вариант и явно подтверждает перенос. Команда может сообщить оценку окончания работы.
После частичного выполнения диспетчер планирует отдельный повторный визит того же заказа,
связывает его с оставшейся работой и затем подтверждает выполнение этой потребности.

Реализовать последовательно в рамках одного M6, без промежуточной браузерной блокировки:
1. Оценка окончания, вычисление риска, поиск окон, серверные и конкурентные тесты.
2. Применение предложения, обработка return request и связи оставшихся задач.
3. Backoffice/crew формы, календарные индикаторы, component tests, итоговые проверки.
После каждой части кратко фиксировать реально готовое; продолжать до завершения M6.

Не включать: автоматический каскад переносов, оптимизацию маршрутов, GPS/карты,
реальное дорожное ETA, уведомления/SMS/email, подписи/Order.COMPLETED, realtime,
offline/PWA, новые платежи, Redis/очереди/микросервисы, Premium calendar или drag-and-drop.

## 3. План, оценка и факт

Расширить существующий CrewAssignment nullable estimatedFinishAt — либо использовать
уже существующее эквивалентное поле. Оценка относится к конкретной команде в визите,
не к заказу целиком: разные команды могут освободиться в разное время.

Оценку вводит текущий активный участник своей команды или ADMIN/DISPATCHER.
Разрешить её для ON_THE_WAY/ARRIVED/IN_PROGRESS. Она означает ожидаемый конец всей
работы этой команды в этом визите, а не время прибытия или продолжительность переезда.
Требовать пояснение, сохранять server actor/updatedAt и историю изменений.
Дата/время — Europe/Rome с тем же строгим преобразованием в UTC, что и M4.
Новая оценка должна быть позже серверного now; переход через полночь допустим.
Очистка оценки — отдельное явное действие с причиной, а не побочный эффект формы.

Смена оценки не изменяет plannedStartAt/plannedEndAt, confirmation, задачи, количества
или actual timestamps. Не допускать, чтобы поздний Retry откатил более новую оценку.
Переиспользовать version/receipt patterns; если нужна отдельная estimateVersion,
добавить её локально, без общего рефакторинга системы версий.

После finish фактический actualEndAt имеет приоритет; последняя оценка остаётся историей.
Отклонять редактирование оценки завершённого/отменённого назначения. Отключённая Crew
может документировать уже начатую работу по правилам M5; disabled user — нет.
Фактическое опоздание ВСЕГДА можно сохранить: его нельзя отклонять из-за других броней.

## 4. Панель рисков и прогноз освобождения

Рассчитывать на чтении с serverNow/dataAsOf, без cron/job и записи audit при каждом GET.
Раздельно показать:
- визит не начат, его начало прошло: «нет отметки о выезде / требуется проверка»;
- работа активна и plannedEnd прошёл: «возможно задержка / нет завершения»;
- оценка окончания прошла, но работа активна: «оценка устарела»;
- следующий неначатый визит этой команды не помещается после её ожидаемого освобождения.
Не превращать эти признаки в executionStatus, auto-cancel или доказанное опоздание клиента.

Для прогнозирования использовать консервативное освобождение команды:
- active с актуальной оценкой: max(plannedEndAt, estimatedFinishAt) + stored buffer;
- active без оценки, но ещё не прошедший plannedEnd: plannedEndAt + buffer, с явной
  пометкой «по плану, оценка команды не получена»;
- active после plannedEnd без актуальной оценки: окончание НЕИЗВЕСТНО;
- terminal: max(plannedEndAt, actualEndAt) + buffer. Раннее завершение само по себе
  не освобождает заранее обещанный плановый резерв; позднее учитывается.
Сохранённые буферы разных назначений не заменять новым default.

Для неизвестного окончания не обещать время «точно свободно завтра». Показать причину
и предложить обновить оценку или выбрать другую команду. В поиске не выдавать для
такой команды выбираемые варианты до новой оценки/finish. Это консервативное решение MVP,
а не утверждение, что команда обязательно занята весь будущий диапазон.

Риск рассчитывать для каждой затронутой команды и будущего визита; многокомандное
событие не дублировать. Не сдвигать цепочку бронирований. Показать источник риска,
план, оценку/факт, buffer, затронутый визит и время расчёта. Все границы — Europe/Rome.

## 5. Поиск свободных окон: чтение, не резервирование

Backoffice получает кнопку Find available time из неначатого визита и return request.
Параметры: контекст операции, earliest local date/time, диапазон дат, длительность,
явно выбранные crewIds. Defaults MVP: 14 Rome-дней, максимум 42; сетка начала 15 минут,
до 20 результатов с признаком ограничения. Ручной ввод точного времени M4 сохраняется.
Не выдавать ограниченный список за все возможные варианты и не искать бесконечно.

Режимы: выбранный набор команд совместно; для одиночной команды — альтернативные
активные команды. Для нескольких команд сначала выбирают альтернативный набор,
затем ищут общее окно: не подменять две команды одной и не перебрать все комбинации.
Область/специализацию показать диспетчеру. Не выдумывать автоматическое сопоставление
адреса свободному тексту serviceArea или расстояниям без соответствующих данных.

Кандидат должен:
- начинаться не раньше заданной границы и serverNow; «завтра» — следующая местная дата;
- целиком вместе с buffer каждой команды входить в её рабочее окно одной Rome-даты;
- учитывать перерывы, выходные, недоступность, disabled crew и все пересекающие резервы;
- учитывать прогноз/фактическое позднее освобождение из §4;
- быть допустимым для всех выбранных команд одновременно;
- учитывать буфер предыдущего и нового визита, включая вставку перед следующим;
- исключать только переносимый Appointment из его собственных резервов, не остальные
  визиты того же Order. IDs и права на этот контекст проверить сервером.

Использовать существующий M4 availability predicate, не дублировать правила в UI.
Расширить общую проверку временных бронирований прогнозом M6: при сохранении нового
или изменённого окна заново проверить известное освобождение; при неизвестном
окончании затянувшейся работы вернуть объяснимый конфликт/необходимость оценки.
Это относится и к обычной форме M4, иначе она обойдёт проверку M6.
Не блокировать metadata-only заметки, факт finish и разрешённую запись оценки.
Новая оценка может пересечь уже сохранённые будущие брони: сохранить правду и показать
риск, а не отклонять оценку и не удалять/менять брони.

Сортировка детерминирована: начало, минимальная смена команд, стабильные ID.
Указать basis PLAN/ESTIMATE/ACTUAL, dataAsOf, команды, start/end, buffers и пояснение.
Оценка — прогноз, а не гарантия фактического окончания; показывать это даже для
прошедшего проверку варианта. Пустой результат отличать от ошибки API; объяснять
отсутствие окон/неизвестное окончание/ограничение диапазона.

Поиск не создаёт appointments, временных броней, hold-token, audit или новых таблиц
предложений. При выборе пользователь явно подтверждает изменение; запись идёт
через действующий серверный use case с повторной проверкой под блокировками.

## 6. Применение переноса или переназначения

Показать before/after: заказ, визит, старое/новое время, старые/новые команды,
причина, длительность и необходимость согласования клиента. Только явный submit.
Никакой автозаписи по клику на карточку варианта или при истечении plannedEnd.

- Переносим только Appointment, у которого ни одна команда не выехала.
- Сохраняем Appointment ID. При тех же командах сохраняем assignment/task IDs и snapshots.
- При смене команды используем существующий lifecycle M4: старое назначение логически
  отменяется, новое создаётся; provenance задач переносится корректно, история не удаляется.
- Смена времени сбрасывает подтверждение клиента. Смена только команды при том же
  согласованном окне следует принятому правилу M4 и не сбрасывает время автоматически.
- NEEDS_CONFIRMATION с назначенными командами резервирует время до явного решения.
- Завершённый или начатый визит не переносим, не отменяем задним числом и не обнуляем.
- Неудачный submit ничего не меняет. Исходная бронь не исчезает при конфликте нового окна.

Нужны expectedVersion, reason и безопасный retry. Для новых M6-команд сохранять
идемпотентность через имеющийся receipt pattern. Повтор после потерянного ответа не
повышает version дважды и не восстанавливает старое время после последующего переноса.
Другой payload с тем же ключом — конфликт. Повтор всегда заново проверяет доступ.
Платежи и финансы не копируются/не пересчитываются из количества визитов.

## 7. Повторный визит: отдельная работа, тот же Order

Переиспользовать ReturnVisitRequest M5. Для terminal PARTIALLY_COMPLETED/BLOCKED без
такого запроса разрешить диспетчеру явно создать его с причиной/remainingWork;
если запрос исходного назначения уже есть, показать его, а не создавать дубликат.
Request может существовать и после COMPLETED, если команда явно попросила дополнительный приезд.

Решение MVP: один request → не более одного текущего follow-up Appointment;
один follow-up Appointment обслуживает один request и может иметь несколько команд.
Несколько request одного Order пока не объединять в один визит. Сохранить историю
всех попыток/связей, не только перезаписываемый latestAppointmentId.
Это ограничение уменьшает сложность; расширение many-to-many сейчас не делать.

Использовать эквиваленты OPEN / PLANNED / RESOLVED (точные имена согласовать с текущим
кодом). OPEN и PLANNED означают незакрытую потребность, а не выполненную работу.
Version, серверные actor/time, причина и audit обязательны.

### 7.1. Планирование остатка

Диспетчер видит неизменяемый исходный FinishReport, актуальные количества, проблемы,
причину/remainingWork и незакрытые task snapshots исходной попытки. Он явно задаёт
объём следующего визита, длительность и команды; поиск слота использует §5.
Не вычислять длительность автоматически из количества или текста remainingWork.

Новый Appointment принадлежит тому же Order и ссылается на request/источник.
Исходный визит, отчёт, фото, quantities и старые задачи не переписывать. Новый визит
получает новые assignments/tasks, NOT_STARTED и NEEDS_CONFIRMATION.

Для задач перенести только незавершённый scope. Старые DONE и optional SKIPPED не
становятся заново PENDING. Required незавершённую работу нельзя молча исключить:
сохранить связь sourceTaskId → новая задача и явно назначить её выбранной команде.
Не дублировать одну carried task автоматически каждой команде многокомандного визита.
Переназначение ещё неначатого follow-up обязано сохранить эти связи и required scope.

Не применять автоматически полный набор M4 required templates к follow-up, возвращая
выполненные задачи. Добавить узкий режим создания return visit с явным scope и
серверной валидацией. Повторную проверку безопасности/целостности можно явно добавить
как НОВУЮ задачу текущего выезда, с пояснением; это не сброс старой DONE.

Остаток товаров показывается из общего accumulated результата OrderItem. Если для
request нужны конкретные целевые количества, хранить их как абсолютные цели по
выбранным item IDs в пределах заказа; не создавать второй склад/копию товаров.
Не снижать текущие totals и не засчитывать результат повторно по визитам.
Для текстовой работы (ремонт/проверка) задавать явную задачу, а не выдумывать quantities.
Сохранять snapshot принятого scope, чтобы последующие изменения не переписали план молча.

Создание Appointment + assignments/tasks + связь request + переход в PLANNED + audit
атомарны. Одинаковый retry не создаёт второй визит; два диспетчера с разными ключами
не создают два текущих follow-up одного request. Закрепить инвариант БД и транзакцией.

### 7.2. Жизненный цикл и повтор неудачного приезда

- Отмена ещё не начатого follow-up освобождает резерв и возвращает request в OPEN
  в той же транзакции. Cancelled попытка и её связь остаются в истории.
- Перенос follow-up меняет тот же новый Appointment; request остаётся PLANNED.
- Пока какая-либо команда follow-up ещё не закончила, нельзя создать следующую попытку.
- Когда все назначения follow-up terminal, но работа частична/блокирована или снова
  нужен приезд, request возвращается в OPEN. История попытки и новые причины сохраняются.
  Новый план создаёт ещё один Appointment, а не переоткрывает законченный.
- Для явно связанного follow-up флаг another visit в finish должен продолжать текущий
  request, а не плодить дубли для того же remaining scope. Отчёт каждой команды сохраняется
  отдельно и неизменно. Исходную reason/remainingWork не затирать: уточнение — история.
- Если все команды завершили успешно, request ещё НЕ RESOLVED. Показать «работа повторного
  визита выполнена — требуется проверка диспетчера». Само бронирование не решает потребность.
- Диспетчер явно resolve с пояснением: все назначения связанной текущей попытки COMPLETED,
  required scope выполнен, целевые quantities достигнуты и нет нового return-флага этой
  попытки. При незавершённой работе сервер отклоняет resolve. Crew не закрывает request.
- Resolve Issue не закрывает request; resolve request не закрывает Issue.
- Не добавлять кнопку «забыть потребность» для обхода невыполненного required scope.

### 7.3. Прогресс после успешного повторного приезда

Уточнить общий M5 resolver, иначе старые PARTIALLY_COMPLETED/BLOCKED и PENDING tasks
будут навсегда запрещать AWAITING_REVIEW. Историческая попытка может считаться покрытой
только через явную RESOLVED-связь и выполненный перенесённый scope. Сам исходный
executionStatus/Task/FinishReport не меняется; в UI показать ссылку на покрывающий визит.

Все оставшиеся непокрытые required tasks/requests, будущие активные визиты, неполные
общие количества и открытые issues продолжают блокировать готовность. Несколько request
считаются независимо: закрытие одного не скрывает другой. Если повторная попытка тоже
была неудачной, её pending scope должен попасть в следующий план; замыкание покрытия
проверять без циклов и без автоматического списания невыполненных задач.

Максимальный итог M6 — AWAITING_REVIEW. Подписи/окончательное Order.COMPLETED — M7.
Платежи не меняются от повторного приезда, неоплата не стирает физический результат.

## 8. Транзакции, права и повторная проверка

Изучить ФАКТИЧЕСКИЙ lock order M5, включая повторную проверку User/Session, Order,
Appointments, Crew и дочерних объектов. Расширить его согласованно для estimate,
reschedule, request planning/cancel/resolve и finish follow-up. Один manager транзакции.
Не вводить обратный Crew → чужой Order/User lock; несколько Crew брать в стабильном
порядке. После ожидания перечитывать нужные резервы, estimates, availability и execution.
Серверное время получать после ожидания locks, не доверять client now.

Предложение не гарантирует место. Между показом и submit могли измениться брони,
оценка, доступность, подтверждение или старт работы. При несовместимости — 409 без
частичных изменений; UI сохраняет draft, предлагает обновить список и не подставляет
новую version автоматически в старый payload. History/receipt коммитятся с изменением.

ADMIN/DISPATCHER — поиск всех команд, risk board, перенос и управление return request.
Crew — оценка собственного назначения и разрешённое чтение своего follow-up/scope.
Никаких финансов, внутренних заметок, чужих заказов или private attachments в новых
crew DTO/SSR/mutation/replay/error responses. Связь с прежним визитом не даёт новых
прав на его BACKOFFICE_ONLY материалы. Вложенные IDs проверять на один Order.

## 9. Интерфейс без нового приложения

Расширить текущие calendar/appointment/order/backoffice execution components:
- risk panel на planning: дата, фильтры команд, источник риска, Refresh/dataAsOf;
- карточка назначения: план/оценка/факт рядом, форма новой оценки и причина;
- Find available time: today/завтра/диапазон, длительность, команды, результаты,
  пустой/unknown/error состояния; выбор открывает preview, не сразу изменяет данные;
- форма apply: before/after/reason/confirmation, pending/retry/409 с сохранением ввода;
- return queue или раздел заказа: OPEN/PLANNED/RESOLVED, исходная попытка, remaining
  scope, Plan return visit, цепочка попыток и подтверждение завершения потребности;
- crew follow-up: только новые задачи и разрешённый контекст предыдущей работы,
  общие quantities и понятное remainingWork; никаких backoffice actions.

Сохранить Day/Week/List, multi-team фильтры и мобильный List. Статусы/риски не определять
только цветом. Обновление — после mutation, Refresh и focus, без обещания realtime.
Новые тексты на принятом языке UI. Component tests — loading/empty/error/stale/drafts,
select preview vs submit, отсутствие старых DONE в checklist нового визита.

## 10. Проверки M6 на изолированной test-БД

Проверить поведение, не добиваться заранее заданного количества тестов.
Обязательные cases (реальные PG транзакции/барьеры для гонок):

1. Estimate не меняет plan/actual/confirmation; stale/replay не откатывают новую оценку.
2. Активная работа без finish не завершается по часам; неизвестная/устаревшая оценка
   не создаёт выбираемые «гарантированно свободные» предложения.
3. Plan 09:00–12:00, estimate 14:00, buffer 30 → следующая бронь 13:00 в риске;
   допустимый кандидат не раньше 14:30 при прочих свободных условиях. Перенос сам не происходит.
4. Actual finish 14:10 +30 → не раньше 14:40 (при сетке 15 минут кандидат 14:45).
5. Общая граница допустима; buffer с обеих сторон, перерывы, weekends, unavailability,
   disabled crew, несколько команд, другие визиты того же заказа, empty result/limits.
6. Rome today/завтра, DST gap/fold и 23/25-часовые дни; timezone процесса не меняет слот.
7. Поиск read-only. Один найденный слот у двух диспетчеров: один apply, второй conflict.
8. Estimate/finish/availability меняются между search и apply: актуальная перепроверка;
   конфликт одной команды откатывает многокомандную операцию полностью.
9. Depart против reschedule/cancel: начавшийся визит не переписывается; результат
   согласован при обоих порядках commit. Actual finish не запрещается из-за опоздания.
10. Один request, два разных ключа планирования — только один текущий follow-up;
    одинаковый ключ — тот же результат без дублей; replay после cancel/нового плана
    не воскрешает прежний визит. Другой payload того же ключа отклоняется.
11. Return plan сохраняет прежние reports/evidence/IDs/totals/payments; DONE не переносятся,
    required pending связаны, смена команд нового визита не теряет carried scope.
12. Cancel follow-up → OPEN, без удаления истории; started follow-up нельзя отменить.
13. Failed follow-up → OPEN и следующая попытка с новым ID, без двух активных планов,
    без duplicated request на каждый finish и без потери причин/невыполненных задач.
14. Request нельзя resolve только по факту планирования; успешная попытка разрешается
    явно. Resolve Issue/request независимы, counts не обнуляют соседние потребности.
15. Успешно покрытая старая partial/blocked попытка не блокирует AWAITING_REVIEW;
    непокрытая, новый return-флаг, неполный item, open issue или будущий визит блокируют.
16. RBAC/ownership/актуальное членство и сессия, CSRF, safe error/replay; audit failure
    откатывает бизнес-операцию. Новые joins не умножают финансовые итоги.
17. Миграции fresh/повтор/поверх M5 сохраняют данные. Повтор seed сохраняет оценки,
    request lifecycle, связи/задачи попыток, execution, evidence, роли и платежи.

## 11. Сдача и отложенная приёмка

По завершении исходников выполнить последовательно lint, format:check, typecheck,
unit, integration, build и git diff --check на закреплённом runtime. Проверить регрессии
M1–M5, особенно finish/return, projection, receipts и общий booking path.
Во время разработки запускать targeted tests; итоговый общий набор не повторять после
каждой правки документации. После изменения кода результаты должны относиться к новой версии.
Сохранить безопасные логи/exit codes; не ослаблять assertions/timeouts ради PASS.
Невыполненное по окружению — BLOCKED, тестовый сбой — FAIL с причиной/исправлением.

Обычные данные не использовать для destructive QA. Не создавать новые demo-пароли
или пользователей development. Cleanup — только собственные test schema/storage.
Если восстанавливается dev-запуск, указать процессы и не выдавать startup logs за UI PASS.

Обновить DECISIONS, DOMAIN_RULES при уточнении return coverage, README и PROGRESS.
В существующем списке финальной проверки сохранить B/C/камеру M5 и добавить:
1. Изменение оценки → риск следующего визита → выбор окна/команды → preview → перенос
   с историей и NEEDS_CONFIRMATION; поздний факт не переписывает старый план.
2. Partial finish → request → новый follow-up со scope → выполнение → явный resolve
   → AWAITING_REVIEW при прочих выполненных условиях, без изменения исходного отчёта.
3. Слот занят между показом и сохранением → отказ без потери draft и исходной брони.
4. Отмена неначатого и повторная неудача follow-up → request снова открыт, история полна.
Браузер НЕ запускать в этом задании, результаты пометить DEFERRED BY USER, не PASS.

Итоговый ответ: что реализовано; какие файлы/миграции; фактические команды и результаты;
ограничения; что проверить в конце; состояние процессов. Не печатать большие hash-реестры.
M5 — прежние проверки + отложенная UI-приёмка; M6 — фактический implementation/code статус
и UI/user acceptance PENDING. Не отмечать ACCEPTED без отдельного подтверждения.
После M6 остановиться. M7/M8, commit, push и deploy не выполнять.
