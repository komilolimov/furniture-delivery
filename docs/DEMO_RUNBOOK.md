# Изолированная демонстрация M8

Команды выполняются из корня репозитория на Node.js 24.22.1 и pnpm 10.34.8.
Это синтетический MVP: запуск demo не означает пользовательскую приёмку M5–M8.
Результаты прежних проверок и отложенные UI-сценарии остаются в `PROGRESS.md`.

## Подготовка окружения

Нужны установленные зависимости, Docker Engine и Compose v2.
Существующий `.env` сохраняется; demo-команды его читают, но не записывают.
В нём должны быть явно настроены `TEST_DATABASE_HOST`, `TEST_DATABASE_PORT`,
`TEST_DATABASE_NAME`, `TEST_DATABASE_USER`, `TEST_DATABASE_PASSWORD`.
Пароли не передавайте в аргументах команд и не копируйте в отчёты.

```bash
pnpm install --frozen-lockfile
docker compose config --quiet
docker compose --profile test up -d --wait postgres-test
```

Цель — отдельный Compose `postgres-test`, обычно `127.0.0.1:5433`,
с именем БД, оканчивающимся на `_test`. Development PostgreSQL остаётся отдельно.
Demo принимает только явную локальную test-конфигурацию; fallback на development нет.
Каждый run получает отдельную schema и private storage; чужие fixtures сохраняются.
Запуск в `NODE_ENV=production` отклоняется.

## Создание набора данных

Выберите новый run ID: 4–40 символов, первая буква `a–z`, далее `a–z`, `0–9`, `_`, `-`.
Во всех командах ниже заменяйте `demo-manual-01` согласованно.

```bash
pnpm demo:prepare --run demo-manual-01
```

Root-команды `demo:prepare`, `demo:start`, `demo:verify` сами собирают contracts.
Отдельный предварительный запуск сборки contracts не требуется.
Prepare применяет миграции и создаёт данные только в своей новой schema.
Бизнес-состояния подготавливаются через существующие доменные операции.

Создаются 40 заказов, 10 команд, 40 сотрудников и два backoffice-пользователя
(`ADMIN` и `DISPATCHER`). Для всех 42 аккаунтов генерируются отдельные случайные пароли.
Путь к private-файлу аккаунтов выводится командой, сами пароли в stdout не выводятся:
`.demo-runs/demo-manual-01/credentials.local.json` — режим `0600`.
Откройте этот файл локально для входа; не отправляйте его содержимое в чат или Git.
Каталоги run/storage имеют режим `0700`; файлы состояния и manifest — `0600`.

`baseDate` нового run — сегодняшний день в `Europe/Rome`.
Необязательный `--base-date YYYY-MM-DD` допускает только эту же сегодняшнюю дату.
В первые две минуты дня, до `00:02 Europe/Rome`, новый prepare честно отклоняется:
сценарий задержки требует реально прошедшего времени, fake clock не используется.
Повтор старого run сохраняет его исходную дату; для демонстрации нового дня создайте новый ID.

```bash
pnpm demo:prepare --run demo-manual-01
```

Повтор подготовленного run читает существующие ресурсы без повторного исполнения работ.
Он не сдвигает визиты и не перезаписывает ручные правки, пароли, платежи или подписи.
Незавершённый/ошибочный prepare не возобновляется автоматически: сохраните диагностику,
затем явно очистите только принадлежащий ему run либо выберите новый ID.

## Запуск и вход

Остановите обычный `pnpm dev` через `Ctrl+C`, если он занимает порты `3000/3001`.
Demo откажется стартовать на занятом порту; автоматически останавливать dev он не будет.

```bash
pnpm demo:start --run demo-manual-01
```

Это foreground-запуск: оставьте терминал открытым.
Откройте `http://127.0.0.1:3000/login` и используйте аккаунт из private-файла.
По запросу пользователя видимый demo-баннер убран. Изоляция demo schema/storage,
проверки владельца и маркировка CLI/manifest сохранены.
Frontend работает через существующий Next proxy к API своей test schema/storage.
Авторизация, актуальные роли/членства, Origin/CSRF и защита файлов сохраняются.
Локальный HTTP demo использует локальную cookie-политику приложения.

Next использует собственный каталог `apps/web/.next-demo/<run-id>`.
Обычный `.next` не используется параллельно с demo-сборкой.
Состояние run содержит идентичность собственных supervisor/child-процессов.
Остановка сверяет PID, время старта, рабочую папку и команду, защищаясь от повторного PID.

## Данные и три демонстрационных сюжета

Откройте `.demo-runs/demo-manual-01/manifest.json` локально.
Он содержит номера/UUID заказов, ссылки backoffice/crew, назначения и три сюжета.
Manifest фиксирует исходную подготовку; после ручных изменений актуален ответ API.
Начальное распределение: INBOX 8, PLANNED 4, ASSIGNED 9, IN_PROGRESS 3,
PARTIALLY_COMPLETED 6, AWAITING_REVIEW 6, COMPLETED 3, REQUIRES_ATTENTION 1.

1. `two-crews-close`: два независимых отчёта команд, общие количества без удвоения,
   синтетический snapshot/подтверждения и явное решение о закрытии.
2. `delay-return`: активная оценка и риск следующего визита, частичное выполнение,
   защищённый материал/issue и явный scope повторной работы с визитом на завтра.
   Поиск, preview, применение переноса и дальнейшее исполнение проверяются вручную.
3. `issue-reopens`: issue после закрытия сохраняет историю и переоткрывает заказ;
   разрешение issue не закрывает его автоматически, нужен новый readiness/complete.

Фото и изображения подписей сгенерированы для теста; это не реальные клиенты/подписи.
Расширенные рабочие окна demo — явная синтетическая настройка, не график компании.

## Повторяемая программная проверка

Используйте отдельный новый ID: verify отказывается перезаписывать существующий run.

```bash
pnpm demo:verify --run demo-verify-01
```

Проверка создаёт полный набор из 40 заказов, изменяет синтетический INBOX-заказ,
повторяет prepare и сравнивает все строки доменных таблиц и private-файлы, включая материалы.
Также измеряются три намеренных чтения dashboard. Это не browser E2E и не event-storm.
Run остаётся подготовленным; удаление требует отдельной явной команды cleanup.

Сохранённый запуск `.tmp/m8/20261026T192023Z/35-demo-verification.{json,log}`:
exit `0`, полный набор 40/10/40+2, ручная правка и все row/file digests сохранены;
три чтения dashboard — 152/96/96 мс. Это наблюдение одного запуска, не SLA.
Запуск `37-demo-lifecycle-start` подтвердил собственные PID/cwd/listeners и изолированные
HTTP health/login readiness; `38-demo-lifecycle-stop` и `39-demo-lifecycle-cleanup` — exit `0`.
Эти журналы в том же каталоге; они не подтверждают браузерную или телефонную приёмку.
После окончательной privacy-правки проверены новые clean frozen install/build/verify
`72–74`, затем start/stop/cleanup `75–77`, все exit `0`. Перед install собственные
node_modules/.next/dist проверочной копии удалены, .env/private runs отсутствовали;
код совпал с final-ready manifest. Child log сохранён отдельно как
`.tmp/m8/20261026T192023Z/clean-demo-application.log` без credentials.
Точные команды, code hashes и итоговые 474/210/proxy/load результаты — в PROGRESS.

## Остановка, очистка и возврат к development

Выполните stop из второго терминала; альтернативно завершите foreground start через `Ctrl+C`:

```bash
pnpm demo:stop --run demo-manual-01
pnpm demo:cleanup --run demo-manual-01
pnpm demo:cleanup --run demo-verify-01
pnpm dev
```

Cleanup допускается только для остановленного run с совпадающими owner-маркерами.
Удаляются только его schema, storage, credentials/manifest/log и `.next-demo/<run-id>`.
Не применяйте `down -v`, `volume prune` или удаление общих каталогов для очистки demo.
До cleanup при необходимости сохраните отдельно **отредактированный от секретов**
`.demo-runs/<run-id>/application.log`: cleanup удаляет этот private child-log.
Отдельные проверочные command logs/PID evidence в `.tmp/m8/...` cleanup не удаляет.
При возврате `pnpm dev` восстанавливает обычный dev-запуск и generated Next types.

## Ограничения и сохранность

Backup/restore: **NOT VERIFIED**. Для M5 нужны согласованные копии PostgreSQL и private
filesystem storage; одной БД недостаточно. M7 PNG подписей хранятся в PostgreSQL.
Private-файл demo-аккаунтов храните отдельно и защищённо, если сохраняете весь run.
План сохранения/восстановления (**не выполнялся**):

1. Штатно остановить приложения, чтобы во время копирования не менялись ни строки БД,
   ни private файлы. PostgreSQL volume не удалять.
2. Сделать логический dump PostgreSQL подходящим `pg_dump` и отдельно защищённую копию
   private storage. Для одного demo сохранить также его manifest/state/credentials,
   версии исходников, owner markers и настройки путей. Пароли не передавать в argv
   и не включать в общедоступный архив или журнал. База содержит PNG подписей M7;
   storage содержит фотографии и документы M5 — нужны обе части одного состояния.
3. Восстанавливать сначала в отдельную локальную test-БД/schema и новый private storage,
   не поверх development. Проверить права файлов, ownership и явные target-настройки.
   Проверить количество записей, protected GET фото/документа/подписи, readiness/history
   и входы на вымышленных аккаунтах. Только после этого фиксировать restore как PASS.
   Перенос demo на другой workspace потребует проверки его ownership; CLI не обходит guard.

SSE — best effort в одном процессе, без durable replay/outbox и поддержки реплик.
HTTP/1 браузер ограничивает соединения одного origin: большое число вкладок может
перейти на ограниченный periodic refresh. Offline и внешних интеграций нет;
юридическая оценка подписей находится вне этого MVP.
M5 B/C, реальные камера/телефон, touch/canvas и отложенные UI-сценарии M6–M8
остаются для финальной проверки. Пользовательская приёмка автоматически не объявляется.
