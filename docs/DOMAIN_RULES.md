# Предметная модель и проверяемые правила

Это целевая модель MVP. Не создавать все таблицы в M1.
Допущения ниже требуют демонстрации и последующего согласования с компанией.

## 1. Границы сущностей

| Сущность | Ответственность |
| --- | --- |
| User | Учётная запись, роль, активность |
| Crew | Команда, специализация, область, доступность |
| CrewMember | Членство пользователя в команде |
| ExternalParticipant | Контакт внешнего участника, без обязательного login |
| Order | Клиент, адрес, объём работ, сумма и агрегированное выполнение |
| OrderItem | Товар, количество, конфигурация, требования доставки/сборки |
| Appointment | Один визит по заказу, запланированное окно и подтверждение клиента |
| CrewAssignment | Участие команды в визите и прогресс именно этой команды |
| TaskTemplate / Task | Шаблон и зафиксированное задание назначения |
| Payment | Ручная запись об оплате и её исправление через void с причиной |
| Issue | Проблема и её разрешение независимо от выполнения |
| Attachment | Защищённый файл и его назначение: order/item/issue/signature |
| Signature | Подписант, время, визит и подписанный результат |
| ActivityLog | Автор, изменение, причина и время |
| CrewAvailability | Рабочие окна и исключения недоступности |

Схематично: Order 1:N Appointment; Appointment 1:N CrewAssignment;
Crew 1:N CrewAssignment; CrewAssignment 1:N Task; Order 1:N OrderItem/Payment/Issue.
Товар и назначение, указанные в задаче/проблеме, должны относиться к тому же заказу.

## 2. Что означает статус

Не смешивать четыре измерения: операционный прогресс, оплату, issues и повторный визит.
Операционный прогресс назначения:

`ASSIGNED → ON_THE_WAY → ARRIVED → IN_PROGRESS → COMPLETED`

Из IN_PROGRESS допускаются PARTIALLY_COMPLETED и BLOCKED с обязательной причиной.
CANCELLED доступен диспетчеру в допустимом контексте. Прямые произвольные PATCH статуса запрещены:
каждое действие проверяет разрешённый переход, полномочия и обязательные поля.
MVP не поддерживает незаметный пропуск шагов; исключительное исправление диспетчером
требует причины и записи в историю.

Прогресс визита агрегируется из назначений; прогресс заказа — из объёма работ и визитов.
Завершение одной команды не завершает визит другой команды.
Возвращаемое API представление должно включать отдельно progress, openIssueCount,
returnVisitRequired и paymentStatus.

«Доставлено» — отдельный результат по товарам/задачам доставки.
Для услуги со сборкой это не завершение заказа.
Частичные количества отражаются явно: deliveredQuantity и assembledQuantity
не могут превышать orderedQuantity; assembledQuantity не превышает deliveredQuantity.
Обновления должны быть защищены от повторной отправки и конкурентной потери изменений.
В MVP можно хранить текущие накопленные количества с версией и записью изменения в истории,
не создавая складскую подсистему. Backend принимает абсолютный новый результат,
а не незащищённую команду «прибавить ещё один».

## 3. Заказ и визит

Перенос ещё не начавшегося визита обновляет тот же Appointment и его назначения атомарно.
Старое/новое время, старые/новые команды, причина и автор остаются в ActivityLog.
Отмена отличается от переноса. Дублировать Order запрещено.

Если команда уже выполнила часть работы и уехала, визит закрывается с частичным результатом.
Для оставшейся работы создаётся НОВЫЙ Appointment того же заказа с незавершёнными задачами.
Нельзя переносить завершённый визит на завтра, стирая факт сегодняшнего приезда.

До начала работ можно менять состав назначений. После начала состава с выполненной
историей не удалять: дополнительную команду добавлять новым назначением.
Полная перепривязка уже начавшегося визита не входит в MVP.

## 4. Время, доступность и конкуренция

- Начало строго раньше конца. Длительность положительна и задаётся в минутах.
- Плановые начало/конец, actualStart/actualEnd и estimatedFinishAt — отдельные поля.
  Фактическое опоздание не переписывает первоначальное обещанное время.
- Рабочие интервалы считать в Europe/Rome, хранить моменты в UTC.
  Неоднозначное/несуществующее местное время при DST не нормализовать молча.
- MVP назначает команду целиком; разделение одной команды на параллельные подгруппы исключено.
  Во избежание скрытого двойного бронирования сотрудник имеет не больше одной активной команды.
- Окна разных команд могут пересекаться. Одна команда не имеет двух пересекающихся резервов.
- Проверяемый резерв: [start, end + travelBuffer). Общая граничная точка разрешена
  после учёта буфера. Буфер настраиваемый; это не рассчитанное дорожное ETA.
- Все команды многокомандного визита должны быть свободны на его полное окно.
- Недоступные/отключённые команды нельзя назначить заново; старую историю сохранять.

Все операции изменения расписания используют один backend use case и транзакцию.
Нужна защита от гонок, а не только предварительный SELECT.
Предлагаемый простой подход: блокировать строки старых и новых команд в стабильном порядке,
затем заново проверить интервалы внутри транзакции и сохранить изменение с expectedVersion.
Все пути записи обязаны использовать одинаковую блокировку. Другой корректный DB-backed
подход допустим после документирования и конкурентного теста.
Две одновременные попытки занять один интервал не должны обе завершаться успешно.
Потеря актуальности редакции — HTTP 409 с предложением перечитать данные.

Фактическое время не подчиняется ограничению планового резервирования:
если работа действительно затянулась, записать правду и показать риск следующего визита,
а не отклонять actualEnd из-за пересечения с запланированной работой.

## 5. Задержки и перепланирование

Нет actualEnd и превышен plannedEnd — «возможно задержка/нет обновления»,
а не автоматическое подтверждение опоздания или завершения.
Команда может указать expected finish и причину. При расчёте риска учесть буфер и следующую работу.
Предложения используют рабочие окна, недоступность, существующие резервы и длительность визита.
Для активной затянувшейся работы с неизвестным окончанием не выдавать следующий слот
как гарантированно свободный: сначала нужна оценка/проверка диспетчера.

Перенос выполняется только после подтверждения диспетчером.
Предложенный слот не является бронью: перед сохранением повторно проверить доступность.
Если новое время не согласовано с клиентом, confirmationStatus = NEEDS_CONFIRMATION.
Чтобы другой диспетчер не занял уже предложенное командой окно, такая запись резервирует время
до явной отмены или переноса; автоматического срока истечения в MVP нет.

## 6. Оплата

`orderTotalCents >= 0` и все суммы — безопасные целые значения в EUR.
`paidCents = сумма Payment с status RECORDED`.
`balanceCents = orderTotalCents - paidCents`.
Статусы: NOT_REQUIRED при total=0, UNPAID при paid=0 и total>0,
PARTIALLY_PAID при 0<paid<total, PAID при paid=total.

Возвраты, переплаты и мультивалютность не входят в MVP; отклонять их явно.
Нельзя уменьшить total ниже уже оплаченного без отдельного исправления платежей.
Payment имеет amount>0, дату, метод, автора и optional note.
Исправление — void с причиной, не физическое удаление записи.
Создание платежа — транзакция с блокировкой заказа и идемпотентным ключом операции;
повторный запрос не создаёт двойную оплату. Эти правила должны быть протестированы в M3.

Неоплата сама по себе не препятствует фиксации фактически выполненной доставки.
Не вводить запрет закрытия из-за задолженности без явного бизнес-требования.
Не хранить номера банковских карт и банковские секреты.

## 7. Issues, фото и подписи

Проблемы разрешаются отдельным действием с автором, временем и пояснением.
Завершение назначенной работы не закрывает issue автоматически.
Права на файл проверяются через его заказ/визит, а не только факт авторизации пользователя.
Для файлов ограничить размер, разрешённые типы и проверять содержимое/метаданные;
не доверять имени и Content-Type от клиента. Не допускать выполнения загруженного файла.

Подпись сохраняется с идентификатором визита, подписантом, timestamp и снимком результата,
включая известные проблемы. Нельзя после подписания молча менять подписанный снимок.
Это фиксация подписи для демо; не заявлять о юридической силе или сертификации.
Отказ/отсутствие подписи фиксировать как исключение с причиной и проверкой диспетчера,
не имитировать подпись клиента.

## 8. Полное завершение заказа

Заказ может быть COMPLETED только если:
обязательный объём доставки/сборки выполнен, обязательные задачи закрыты,
все относящиеся к заказу активные назначения завершены/корректно отменены,
нет нерешённых issues, нет незакрытой потребности повторного визита,
и получены требуемые подтверждения либо диспетчером оформлено исключение с причиной.

Повторная команда завершения не должна дублировать подписи, платежи или историю переходов.
Если после полного завершения обнаружена новая проблема, явно переоткрыть заказ
с причиной и сохранить прежнее завершение в истории.


## 9. Уточнения M6: прогноз и покрытие повторной работы

Оценка относится к назначению команды, а не всему заказу. Она не меняет план, факт,
подтверждение клиента, задачи и количества. Новая оценка позже серверного now после
ожидания блокировок; очистка и обновление требуют причины, автора, времени и отдельной
estimateVersion. Поздний повтор команды не возвращает прежнюю оценку.

Освобождение active с актуальной оценкой: max(plannedEnd, estimate) + сохранённый buffer.
До plannedEnd без оценки используется план с явной пометкой. После plannedEnd без
актуальной оценки окончание UNKNOWN: нельзя обещать выбираемый свободный слот даже
на завтра. Terminal использует max(plannedEnd, actualEnd) + buffer. Ранний finish не
сокращает обещанный резерв. Ранний выезд в разрешённую плановую дату занимает команду
с min(plannedStart, departedAt), поэтому поиск не предлагает ей работу до планового начала
уже активного визита. Предложения не бронируют; запись вновь проверяет общий
predicate под блокировками команд. Менять факты ради свободного слота запрещено.

Один ReturnVisitRequest относится к исходному назначению, хранит неизменную причину и
remainingWork; OPEN и PLANNED оба означают незакрытую потребность. Один request имеет
не больше одной текущей попытки; один follow-up Appointment обслуживает один request,
может включать несколько команд. Все попытки сохраняются. Новый план создаёт новый
визит того же Order, не переоткрывает завершённый и не переносит старые DONE/optional
SKIPPED в PENDING. Обязательная незавершённая задача передаётся ровно одному назначению
с sourceTaskId и стабильным returnScopeKey; принятый scope сохраняется неизменным.
Переназначение неначатой работы сохраняет provenance и всю обязательную работу.
Новые проверки безопасности задаются явно с пояснением, а не полным набором шаблонов M4.
Цели товаров абсолютны в общих OrderItem totals. Недостигнутые цели неудачной попытки
нельзя опустить или уменьшить в следующей. Длительность вводит диспетчер.

Отмена неначатой попытки возвращает OPEN атомарно с освобождением резерва. Пока есть
нетерминальная команда текущего follow-up, следующая попытка запрещена. После всех
terminal при partial/blocked, недостигнутых целях или новом return-флаге request снова
OPEN. Return-флаг follow-up продолжает этот request; дополнительные причины остаются
в истории, первоначальная reason/remainingWork не заменяются. Успех не закрывает
потребность автоматически. Явный RESOLVED доступен диспетчеру лишь после COMPLETED всех
команд, DONE required scope, достижения целей и отсутствия нового return-флага.
Решение issue не меняет request; решение request не меняет issue.

Историческая partial/blocked попытка покрывается только явной RESOLVED-цепочкой.
Её статусы, задачи, количества, фотографии и FinishReport не переписываются. Незавершённая
задача считается покрытой только достижимым по sourceTaskId выполненным потомком этой
проверенной цепочки; циклы и потеря required scope запрещены. Прежние непокрытые задачи,
другие OPEN/PLANNED requests, неполные количества, открытые issues, будущие неначатые
назначения и визиты без команд продолжают блокировать готовность. Максимум M6 —
AWAITING_REVIEW; финальное закрытие и подписи остаются следующим этапам.


## 10. Решения тестового MVP M7: подтверждения и окончательное закрытие

Это уточнения MVP, не утверждение о согласованной юридической процедуре. Один общий
immutable snapshot относится к Appointment после terminal всех ASSIGNED команд и хотя бы
одного фактического выезда. Отменённая до начала работа не требует подтверждений.
Снимок строит backend под Order/Appointment locks: собственные immutable FinishReport
quantities каждой команды не складываются и не заменяются последующими totals.
Общий документ не содержит финансов, internal notes или BACKOFFICE_ONLY материалов.
Canonical JSON/SHA-256 идентифицирует содержание, не удостоверяет личность.

Один customer slot на снимок, один staff slot на каждое реально участвовавшее назначение.
Staff подтверждает только текущий активный участник своей команды, с именем из БД;
отключённую Crew можно подтвердить после фактической работы, disabled User нельзя.
Customer name/relation — заявленные данные, capturedBy — настоящий сотрудник/диспетчер.
Consent не включён заранее, имя без PNG не является подписью. Подписать можно partial
или blocked результат; факт исполнения не зависит от signature/absence.

Одно неизменяемое подтверждение SIGNED или ABSENCE на slot. Refused/Absent/Unable to sign
с причиной не становится SIGNED. Одно отдельное неизменяемое решение исключения этого
slot — APPROVED/REJECTED, только диспетчер с пояснением/временем. Pending/rejected блокируют
закрытие. Для исправления снимка/подписи/исключения целиком инвалидировать документ с
причиной и готовить новую редакцию, без переноса старых подтверждений. История сохраняется.

PNG ограничен 256 KiB до/после обработки, 2048×1024/2 097 152 pixels; metadata удаляются,
недействительные/animated/blank/transparent/однотонные рисунки отвергаются. Bytea, metadata,
receipt и audit атомарны в PostgreSQL, без второй файловой системы подписей. Свежие права
проверяются после decode и на каждом чтении. Crew image access — клиент и своё назначение
того же визита; иное назначение/follow-up не открывает чужой росчерк. Обычные DTO не несут
PNG/base64. Публичных URL, browser storage и генерации подписей реальным людям нет.

Physical readiness берётся из M6 resolver с покрытием RESOLVED chains. Confirmation
readiness дополнительно требует текущий снимок и каждый SIGNED/EXCEPTION_APPROVED slot
каждого фактического визита, включая исторические partial/blocked. Исключение не обходит
qty/tasks/issues/returns, будущие/active/unassigned визиты и неизвестное покрытие.
Задолженность не относится к физической готовности. Complete order — явное действие
диспетчера под Order lock с expectedVersion и повторным полным пересчётом. Неизменяемый
CompletionRecord хранит основание решения и IDs подтверждений/coverage. Единственный
currentCompletionId определяет COMPLETED; без него применяется прежний прогресс M6.
Каждая effective signature/absence/review/invalidation повышает Order revision, не
конфликтуя с независимыми signer slots одного immutable snapshot.version.

Reopen снимает только текущий marker, сохраняя CompletionRecord, event, подписи и факты.
Следующее закрытие — новый record. Новый/reopened issue закрытого заказа сохраняется
по прежним правам и атомарно reopen с источником/причиной; resolve issue не закрывает
снова. Invalidate обязательного снимка также reopen. Планирование/новый return scope
требует сначала явного reopen. Оплата/VOID/допустимая цена/contact/notes не reopen и не
переписывают подписанный документ; материальные данные остаются защищены M5.
Все действия сериализуются User → Order → дочерние locks, с fresh auth и receipt перед
проверкой старой версии. Старый replay возвращает исходный operation ID и текущее
разрешённое состояние, не создаёт новый PNG/record и не возрождает прежний marker.
